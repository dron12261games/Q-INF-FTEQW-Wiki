# Директивы уровня материала

> [⬅ Вернуться к оглавлению вики](../README.md)

> [Индекс справочника директив .shader](./README.md)

Файл `.shader` описывает материал как один верхнеуровневый блок `{ }` с общими свойствами поверхности и нулём или несколькими вложенными блоками-стадиями `{ }`. Верхний уровень отвечает за поведение материала целиком: порядок отрисовки, отсечение граней, флаги неба и тумана, подключение стандартных карт и другие общие настройки. Вложенные стадии настраивают уже отдельные проходы рендера — какие текстуры использовать, как их смешивать и как анимировать координаты. Эта страница покрывает только те ключевые слова, которые пишутся сразу внутри внешнего блока материала и реально распознаются парсером `gl_shader.c` как директивы верхнего уровня.

## Директивы

### cull
`cull disable|none|twosided|front|back|backside|backsided`

* **mode** — какой набор граней отбрасывать до растеризации.

#### Описание и логика работы
`cull` управляет тем, будет ли поверхность видна только с лицевой стороны или с обеих сторон. Значения `disable`, `none` и `twosided` отключают отсечение и заставляют материал рисоваться с двух сторон. `front` переключает отрисовку на задние стороны, а `back`, `backside` и `backsided` — на стандартное отсечение задних граней. Если указан неизвестный текст, парсер ведёт себя так же, как для `front`.

Для листвы, ткани, сеток и тонких плоскостей почти всегда нужен двусторонний режим. Для обычных стен и пола двусторонность нежелательна: она повышает цену рендера и может сделать заметными изнанки полигонов.

#### Практические сценарии использования
```
textures/wiki/cloth_banner
{
    cull twosided      // полотнище видно и спереди, и сзади
    {
        map textures/wiki/cloth_banner.tga
    }
}
```

### skyparms
`skyparms farbox height nearbox`

* **farbox** — имя набора из шести текстур skybox'а.
* **height** — числовой параметр купола/неба, который парсер читает как число.
* **nearbox** — второй строковый аргумент; текущий материалный парсер его принимает, но основная логика неба строится прежде всего вокруг дальнего бокса.

#### Описание и логика работы
`skyparms` помечает материал как небо и автоматически переводит его в очередь `sort sky`. Главный практический эффект — движок начинает обращаться с поверхностью как с фоном сцены, а не как с обычной геометрией. Первый аргумент задаёт набор текстур skybox'а; второй считывается как числовой параметр высоты; третий сохраняет Quake III-совместимый синтаксис.

Это директива верхнего уровня: ставить её внутри стадии нельзя. Она обычно сочетается с `surfaceparm sky` по привычке из экосистемы Q3, но именно `skyparms` уже само по себе включает небесный режим материала.

#### Практические сценарии использования
```
textures/wiki/sky_day
{
    skyparms env/skies/day 512 -
    {
        map $whiteimage    // сама стадия обычно несущественна; важнее skyparms
        rgbGen identity
    }
}
```

### fogparms
`fogparms (r g b) depth`

* **r g b** — цвет тумана в виде тройки компонент.
* **depth** — плотность/дистанция тумана; ноль и отрицательные значения заменяются безопасным значением по умолчанию.

#### Описание и логика работы
`fogparms` задаёт цвет и глубину тумана для материала. После чтения цвет нормализуется, а дистанция преобразуется во внутренний коэффициент плотности; если указать `0` или отрицательное число, движок подставляет стандартное значение вместо недопустимого. Дополнительно материал получает поведение, эквивалентное запрету динамического света и теней: туманные поверхности не предназначены для обычной затеняемой геометрии.

На практике такую директиву используют для специализированных туманных объёмов, подводных плоскостей или особых world-материалов. Она влияет на весь материал, поэтому её не имеет смысла дублировать по стадиям.

#### Практические сценарии использования
```
textures/wiki/fog_green
{
    fogparms ( 0.20 0.45 0.25 ) 192
    surfaceparm nodraw
    {
        map $whiteimage
        blendfunc blend
        rgbGen const ( 0.20 0.45 0.25 )
    }
}
```

### surfaceparm
`surfaceparm keyword`

* **keyword** — одно слово, переключающее один из поддерживаемых флагов поверхности.

#### Описание и логика работы
В FTEQW `surfaceparm` — это контейнерная директива: сам синтаксис один и тот же, а смысл определяется следующим словом. Важно не путать общую экосистему Quake III с тем, что именно меняет текущий рендерный парсер: `gl_shader.c` реально переключает только часть значений `surfaceparm`, перечисленных ниже. Остальные традиционные слова могут оставаться полезными для компиляторов карт, gamecode или редакторов, но не меняют ветвление этого конкретного кода.

Именно поэтому значения вроде `nonsolid`, `trans`, `water` и `slick` часто встречаются в `.shader`-файлах, однако в материальном парсере FTEQW они не имеют собственной отдельной ветки обработки на этом уровне. Их можно продолжать использовать ради совместимости с пайплайном контента, но в этой статье отдельно разбираются только значения, которые действительно видны в коде данного парсера.

#### Частые значения surfaceparm, реально влияющие на разбор материала

#### surfaceparm nodraw
`surfaceparm nodraw`

* **keyword** — скрывает собственную геометрию материала.

`nodraw` помечает поверхность как не предназначенную для обычного видимого рендера. Это удобно для служебных плоскостей, объёмов тумана, невидимых масок и материалов, которые существуют ради побочных эффектов. Если нужен скрытый носитель только для логики, `nodraw` — базовый выбор.

#### surfaceparm nodraw2
`surfaceparm nodraw2`

* **keyword** — альтернативная форма `nodraw`.

`nodraw2` приводит к тому же внутреннему флагу, что и `nodraw`. Практический смысл — совместимость с пайплайнами, где одно из слов может быть интерпретировано внешними инструментами по-особому.

#### surfaceparm nodlight
`surfaceparm nodlight`

* **keyword** — запрещает влияние динамического света на материал.

Такой флаг полезен для чисто утилитарных или специальных поверхностей, которые не должны подсвечиваться вспышками, фонарями и прочими динамическими источниками. Это особенно уместно на экранах, служебных масках и некоторых fullbright-эффектах.

#### surfaceparm noshadows
`surfaceparm noshadows`

* **keyword** — запрещает обработку теней на материале.

Этот флаг нужен там, где материал должен оставаться визуально стабильным и не участвовать в обычной схеме теней. Частый случай — декоративные или вспомогательные поверхности, которые не должны затемняться как полноценная мировая геометрия.

#### surfaceparm sky
`surfaceparm sky`

* **keyword** — помечает материал как небесный.

`sky` включает флаг небесной поверхности. Сам по себе он не задаёт набор текстур skybox'а, поэтому на практике обычно соседствует с `skyparms`. Полезно понимать различие: `surfaceparm sky` сообщает, что это небо, а `skyparms` ещё и настраивает сами ресурсы/параметры неба.

#### surfaceparm noimpact
`surfaceparm noimpact`

* **keyword** — отключает следы попаданий и родственные отметки.

В текущем парсере `noimpact` сводится к тому же флагу, что и `nomarks`. Практический результат: на поверхности не должны оставаться обычные следы от оружия и похожие decals/marks.

#### surfaceparm nomarks
`surfaceparm nomarks`

* **keyword** — запрещает mark-эффекты.

Это прямое и наиболее очевидное слово для отключения отметок на поверхности. Особенно полезно на воде, деформируемой геометрии, небе и иных материалах, где следы пуль или взрывов выглядят неправильно.

#### surfaceparm hasdiffuse
`surfaceparm hasdiffuse`

* **keyword** — принудительно заявляет наличие базовой диффузной карты.

Флаг рассчитан прежде всего на forced-shader и похожие сценарии замены материалов. Он помогает движку не потерять ожидание диффузной карты в случаях, когда исходный материал сам по себе не создавал её автоматически.

#### surfaceparm hasnormalmap
`surfaceparm hasnormalmap`

* **keyword** — принудительно заявляет наличие normal map.

Используется как служебная подсказка для систем, которые подменяют или наследуют другой материал. Нужен реже, чем обычный `normalmap`, но полезен, когда набор карт должен считаться существующим даже без их явного вывода из исходного шейдера.

#### surfaceparm hasgloss
`surfaceparm hasgloss`

* **keyword** — принудительно заявляет наличие gloss/specular-данных.

Это аналогичный служебный флаг для случаев, когда материал должен считаться поддерживающим блеск или specular-канал несмотря на способ подмены/наследования.

#### surfaceparm hasfullbright
`surfaceparm hasfullbright`

* **keyword** — принудительно заявляет наличие карты самосвечения.

Полезно при замещении материалов, когда fullbright-канал нужен шейдерной логике, но не был заранее выведен в исходном наборе текстур.

#### surfaceparm haspaletted
`surfaceparm haspaletted`

* **keyword** — принудительно заявляет наличие paletted-данных.

Специализированный флаг для материалов, которые должны обрабатываться как имеющие палитровый источник.

#### surfaceparm hastop / hasbottom / hastopbottom
`surfaceparm hastop`

* **keyword** — любой из трёх синонимов включает наличие top/bottom overlay-каналов.

Все три слова сводятся к одному внутреннему флагу. Их применяют там, где материал должен считаться совместимым с верхней/нижней перекраской модели или с дополнительными overlay-картами.

#### Практические сценарии использования
```
textures/wiki/trigger_fog
{
    surfaceparm nodraw      // геометрия служебная
    surfaceparm nomarks     // следы пуль не нужны
    surfaceparm nodlight    // динамический свет не влияет
    {
        map $whiteimage
        blendfunc blend
        rgbGen const ( 0.10 0.20 0.35 )
    }
}
```

### nomipmaps
`nomipmaps`

* **Аргументы отсутствуют.**

#### Описание и логика работы
`nomipmaps` отключает мип-уровни у материала. Важно, что этот же код одновременно включает и поведение `nopicmip`, то есть материал не только перестаёт использовать mipmaps, но и защищается от пользовательского снижения детализации через `picmip`-подобные настройки. Поэтому директива заметно жёстче, чем один только `nopicmip`.

Её применяют для пиксель-арта, интерфейсных элементов на моделях, экранов, вывесок и любой поверхности, где размытие на расстоянии нежелательно. На крупных мировых текстурах использовать её стоит осторожно: она легко вызывает мерцание и aliasing.

#### Практические сценарии использования
```
textures/wiki/monitor_ui
{
    nomipmaps
    {
        map textures/wiki/monitor_ui.tga
    }
}
```

### nopicmip
`nopicmip`

* **Аргументы отсутствуют.**

#### Описание и логика работы
`nopicmip` запрещает глобальным настройкам качества понижать разрешение текстуры материала. В отличие от `nomipmaps`, эта директива не отключает сами mipmaps — она лишь гарантирует, что источник останется в полном разрешении. Это компромиссный вариант, когда нужна защита от чрезмерного даунскейла, но фильтрацию на расстоянии всё ещё хочется сохранить.

Типичные случаи — важные панели интерфейса в мире, signage, мелкие надписи и HUD-подобные элементы, встроенные в модель или карту.

#### Практические сценарии использования
```
textures/wiki/control_panel
{
    nopicmip
    {
        map textures/wiki/control_panel.tga
    }
}
```

### polygonoffset
`polygonoffset [scale]`

* **scale** — необязательный множитель силы смещения; если не указан, используется обычная единичная величина.

#### Описание и логика работы
`polygonoffset` просит рендер слегка сместить материал по глубине, чтобы он не конфликтовал с почти совпадающей геометрией под ним. Главная задача — борьба с z-fighting на decals, накладках, дорожной разметке, трещинах и других «тонких» поверхностях, лежащих поверх стены или пола. Числовой аргумент масштабирует интенсивность смещения.

Если смещение сделать слишком большим, накладка начнёт визуально «висеть» над поверхностью. Если слишком маленьким — мерцание останется. Поэтому обычно начинают с `polygonoffset` без аргумента и усиливают только при необходимости.

#### Практические сценарии использования
```
textures/wiki/wall_crack_decal
{
    polygonoffset 1
    sort decal
    {
        map textures/wiki/wall_crack_decal.tga
        blendFunc blend
    }
}
```

### sort
`sort portal|sky|opaque|decal|litdecal|seethrough|unlitdecal|banner|underwater|blend|additive|nearest|ripple|deferredlight|number`

* **value** — именованная очередь отрисовки либо числовой эквивалент Quake III sort-приоритета.

#### Описание и логика работы
`sort` задаёт, когда материал будет рисоваться относительно других поверхностей. Это критично для прозрачности, decals, порталов и неба: даже верная стадийная смесь не спасёт, если весь материал попал в неправильную очередь. Поддерживаются как именованные значения, так и числовые уровни Q3-совместимого диапазона.

Наиболее практичные значения: `portal`, `sky`, `opaque`, `decal`/`litdecal`, `seethrough`, `unlitdecal`, `banner`, `underwater`, `blend`, `additive`, `nearest`.

Для прозрачных материалов `sort blend` или `sort additive` почти так же важны, как и [`blendfunc`](02-shader-stage-directives.md#blendfunc) на самих стадиях. Неправильная сортировка даёт классический набор артефактов: прозрачные полигоны «режут» друг друга или рисуются в странном порядке.

#### Практические сценарии использования
```
textures/wiki/holo_panel
{
    sort blend
    cull none
    {
        map textures/wiki/holo_panel.tga
        blendfunc add
        rgbGen identity
    }
}
```

### deformvertexes
`deformvertexes type ...`

* **type** — вид деформации: `wave`, `normal`, `bulge`, `move`, `autosprite`, `autosprite2`, `projectionShadow`, `text0`...`text7`.
* **...** — набор аргументов зависит от выбранного типа деформации.

#### Описание и логика работы
`deformvertexes` включает геометрическую деформацию всего материала. В текущем парсере поддерживаются волна, шум по нормали, bulge, направленное смещение, оба autosprite-варианта, projection shadow и служебные текстовые варианты `textN`. Можно указать несколько строк `deformvertexes` подряд — они накапливаются. Дополнительно материал автоматически получает защиту от marks, потому что следы попаданий на деформируемой поверхности обычно бессмысленны.

Полный разбор аргументов каждого подвида вынесен на отдельную страницу про деформацию вершин. Здесь важно помнить границу ответственности: сама директива ставится на уровне материала, а не внутри стадий.

#### Практические сценарии использования
```
textures/wiki/flag
{
    cull none
    deformvertexes wave 64 sin 0 4 0 0.7
    {
        map textures/wiki/flag.tga
    }
}
```

### portal
`portal`

* **Аргументы отсутствуют.**

#### Описание и логика работы
`portal` переводит материал в очередь `sort portal`. Это короткая форма для поверхностей, которые должны рендериться как порталы, зеркала или окна в другой рендер-буфер. Само по себе слово не задаёт ни искажение, ни отражение, ни refraction-карты — оно лишь сообщает, что поверхность относится к портальному типу рендера.

Часто `portal` сочетают с `portalfboscale`, пользовательскими программами или другими FTE-специфичными средствами. Даже если стадия выглядит как обычная текстура, очередь `portal` радикально меняет смысл материала в рендер-пайплайне.

#### Практические сценарии использования
```
textures/wiki/mirror_plane
{
    portal
    cull none
    {
        map $whiteimage
        rgbGen identity
    }
}
```

### entitymergable
`entitymergable`

* **Аргументы отсутствуют.**

#### Описание и логика работы
`entitymergable` разрешает движку считать материал пригодным для объединения нескольких сущностей в более крупные batches. Это оптимизационная подсказка: визуально она ничего не меняет, но может снизить стоимость рендера на множестве повторяющихся объектов.

Лучше всего директива подходит для простых однотипных украшений, где одинаковый материал висит на большом числе инстансов. На эффектах со строгой индивидуальностью состояния пользы меньше.

#### Практические сценарии использования
```
textures/wiki/foliage_cluster
{
    entitymergable
    cull none
    {
        map textures/wiki/foliage_cluster.tga
        alphaFunc ge128
    }
}
```

### clutter
`clutter model spacing scalemin scalemax zofs anglemin anglemax`

* **model** — модель, которую нужно разбрасывать по поверхности.
* **spacing** — желаемый шаг размещения экземпляров.
* **scalemin** — минимальный множитель масштаба.
* **scalemax** — максимальный множитель масштаба.
* **zofs** — смещение по высоте.
* **anglemin** — минимальный угол поворота в градусах.
* **anglemax** — максимальный угол поворота в градусах.

#### Описание и логика работы
`clutter` — FTE-расширение для автоматического «засева» поверхности мелкими объектами вроде травы, камешков или мусора. Директива не рисует clutter сама по себе одной текстурной стадией; она добавляет к материалу описание набора случайно размещаемых моделей. Плотность и дистанция затем дополнительно зависят от клиентских настроек clutter-системы.

Это хороший вариант, когда хочется связать визуальную подстилку мира и распределение декора прямо через материал поверхности. Чем меньше `spacing`, тем гуще будет засеивание; диапазоны масштаба и угла помогают скрыть повторяемость.

#### Практические сценарии использования
```
textures/wiki/grass_ground
{
    clutter models/foliage/grass_a.md3 96 0.8 1.3 0 0 360
    {
        map textures/wiki/grass_ground.tga
    }
}
```

### deferredlight
`deferredlight`

* **Аргументы отсутствуют.**

#### Описание и логика работы
`deferredlight` переводит материал в специальную очередь `sort deferredlight`. Это узкоспециализированный FTE-режим для тех материалов, которые должны попадать не в обычный проход геометрии, а в буфер предосвещения/отложенного освещения.

Для стандартных world-материалов директива почти никогда не нужна. Она уместна там, где автор сознательно строит advanced lighting pipeline и понимает, как материал будет использоваться дальше в цепочке рендера.

#### Практические сценарии использования
```
textures/wiki/light_volume
{
    deferredlight
    {
        map $whiteimage
        rgbGen identity
    }
}
```

### affine
`affine`

* **Аргументы отсутствуют.**

#### Описание и логика работы
`affine` — подсказка backend'у использовать affine-style interpolation hint на всех проходах материала. Это не художественный эффект, а низкоуровневый намёк рендеру; исторически он мог быть полезен на определённом железе или для специфичного ретро-вида искажения.

В современных контентах директива требуется редко. Но если проект сознательно имитирует старую неточную перспективу текстур, `affine` даёт способ закрепить такое поведение на уровне конкретного материала.

#### Практические сценарии использования
```
textures/wiki/retro_floor
{
    affine
    {
        map textures/wiki/retro_floor.tga
    }
}
```

### fullrate
`fullrate`

* **Аргументы отсутствуют.**

#### Описание и логика работы
`fullrate` запрещает для материала half-rate shading и просит backend шейдить его в полном темпе. Это техническая директива качества: особенно логична для текста, UI-подобных панелей, тонких линий и иных поверхностей, где упрощённый режим может заметно портить картинку.

На обычных шероховатых стенах разницу можно не увидеть, а вот на чёткой графике и интерфейсных оверлеях она оправдана чаще. Цена — потенциально более дорогой рендер на соответствующих backend'ах.

#### Практические сценарии использования
```
textures/wiki/sign_text
{
    fullrate
    nopicmip
    {
        map textures/wiki/sign_text.tga
    }
}
```

### diffusemap
`diffusemap path`

* **path** — путь к базовой цветовой карте материала.

#### Описание и логика работы
`diffusemap` заполняет стандартный слот базовой текстуры материала без явного развёртывания ручной стадии. Это FTE-расширение, удобное для материалов, которые полагаются на встроенные generic-программы и связанный набор карт. Директива особенно хороша в компактных PBR-/normalmap-ориентированных описаниях.

Если материал собирается целиком из набора top-level map-директив, именно `diffusemap` обычно служит главной цветовой картой. Для обычного многопроходного Q3-стиля по-прежнему можно использовать и привычные стадии с `map`.

#### Практические сценарии использования
```
textures/wiki/panel_metal
{
    diffusemap textures/wiki/panel_metal_d.tga
    normalmap textures/wiki/panel_metal_n.tga
    specularmap textures/wiki/panel_metal_s.tga
}
```

### normalmap
`normalmap path`

* **path** — путь к карте нормалей.

#### Описание и логика работы
`normalmap` заполняет стандартный bump/normal-слот материала. Текстура трактуется как normal map и предназначена не для прямого вывода на экран, а для шейдерного освещения. Без подходящей шейдерной логики сама по себе директива не создаёт «рельеф» магически во всех режимах, но подготавливает данные для тех путей рендера, которые normal mapping поддерживают.

Её естественная пара — `diffusemap`; нередко рядом идёт и `specularmap`. На наследуемых или подменяемых материалах близкий эффект можно дополнительно страховать через `surfaceparm hasnormalmap`.

#### Практические сценарии использования
```
textures/wiki/brick_relief
{
    diffusemap textures/wiki/brick_relief_d.tga
    normalmap textures/wiki/brick_relief_n.tga
}
```

### specularmap
`specularmap path`

* **path** — путь к карте specular/gloss-данных.

#### Описание и логика работы
`specularmap` заполняет слот блеска материала. Это карта, которую шейдеры используют для управления интенсивностью бликов и/или связанными specular-характеристиками. В паре с diffuse/normal-картами она завершает классический набор «окрашенный металл/камень/пластик с управляемыми бликами».

Если материал должен считаться имеющим specular-канал в forced-shader сценариях, схожую роль на уровне флагов выполняет `surfaceparm hasgloss`, но обычным рабочим способом остаётся именно `specularmap`.

#### Практические сценарии использования
```
textures/wiki/console_frame
{
    diffusemap textures/wiki/console_frame_d.tga
    normalmap textures/wiki/console_frame_n.tga
    specularmap textures/wiki/console_frame_s.tga
}
```

### fullbrightmap
`fullbrightmap path`

* **path** — путь к карте самосвечения.

#### Описание и логика работы
`fullbrightmap` задаёт карту участков, которые должны выглядеть самосветящимися независимо от обычного освещения сцены. Это удобно для ламп, экранов, неоновых вывесок, приборных индикаторов и футуристических панелей.

Такая карта не отменяет необходимость в основном `diffusemap`: обычно она лишь добавляет emissive-компонент к базовому материалу. При наследовании материалов похожую информацию можно продублировать служебным `surfaceparm hasfullbright`.

#### Практические сценарии использования
```
textures/wiki/neon_panel
{
    diffusemap textures/wiki/neon_panel_d.tga
    fullbrightmap textures/wiki/neon_panel_f.tga
}
```

### uppermap
`uppermap path`

* **path** — путь к верхней overlay-карте перекраски.

#### Описание и логика работы
`uppermap` задаёт стандартный слот верхнего overlay-слоя, обычно связанного с top-color или подобной системой перекраски модели. Директива полезна для player skins, командных раскрасок и иных ресурсов, где верхняя часть текстуры должна переопределяться отдельно.

С практической точки зрения `uppermap` редко живёт в одиночку: чаще рядом находится `lowermap`, а также базовая `diffusemap`, поверх которой overlays и применяются.

#### Практические сценарии использования
```
models/wiki/player_skin
{
    diffusemap textures/wiki/player_skin_d.tga
    uppermap textures/wiki/player_skin_upper.tga
    lowermap textures/wiki/player_skin_lower.tga
}
```

### lowermap
`lowermap path`

* **path** — путь к нижней overlay-карте перекраски.

#### Описание и логика работы
`lowermap` — парная директива к `uppermap`, отвечающая за нижнюю зону перекраски. Вместе они включают поддержку top/bottom overlay-каналов, что важно для старых Quake-подобных схем персонализации игрока или командных цветов.

Если материал должен считаться совместимым с такой системой даже без явных overlay-карт, похожий флаг можно принудительно объявить через `surfaceparm hastop`, `hasbottom` или `hastopbottom`.

#### Практические сценарии использования
```
models/wiki/marine_skin
{
    diffusemap textures/wiki/marine_skin_d.tga
    uppermap textures/wiki/marine_skin_upper.tga
    lowermap textures/wiki/marine_skin_lower.tga
}
```

### reflectmask
`reflectmask path`

* **path** — путь к маске отражения.

#### Описание и логика работы
`reflectmask` задаёт карту, по которой шейдер решает, какие участки поверхности отражают окружение сильнее, а какие слабее. Это особенно полезно на лаке, влажном камне, полированном металле, стекле с неравномерным блеском и похожих материалах.

Наиболее осмысленна эта директива там, где у материала действительно есть путь отражения: через пользовательскую программу, reflect/refract-совместимый pipeline или общий reflective shading backend'а.

#### Практические сценарии использования
```
textures/wiki/wet_stone
{
    diffusemap textures/wiki/wet_stone_d.tga
    normalmap textures/wiki/wet_stone_n.tga
    reflectmask textures/wiki/wet_stone_r.tga
}
```

### displacementmap
`displacementmap path`

* **path** — путь к displacement/height-карте.

#### Описание и логика работы
`displacementmap` заполняет специальный слот карты смещения. Само наличие текстуры не гарантирует, что любой режим рендера начнёт геометрически теселлировать поверхность; смысл директивы — сделать карту доступной тем шейдерным путям, которые знают, как ею пользоваться.

Часто displacementmap комбинируют с `normalmap` и `offsetmapping`, если нужен выразительный микрорельеф без отдельной высокополигональной геометрии.

#### Практические сценарии использования
```
textures/wiki/carved_stone
{
    diffusemap textures/wiki/carved_stone_d.tga
    normalmap textures/wiki/carved_stone_n.tga
    displacementmap textures/wiki/carved_stone_h.tga
}
```

### transmissionmap
`transmissionmap path`

* **path** — путь к карте пропускания/просвечивания света.

#### Описание и логика работы
`transmissionmap` задаёт текстуру для материалов, у которых часть света должна проходить сквозь толщу и окрашиваться ею — например, листья, ткань на просвет, тонкий воск, кожа или цветное стекло в расширенных шейдерах. Это не обычная альфа-прозрачность и не стеклянная refraction сама по себе, а именно карта передачи света.

Практически директива полезна только в тех программах и backend'ах, которые умеют интерпретировать transmission-канал. В простом fixed-function стиле эффекта может не быть.

#### Практические сценарии использования
```
textures/wiki/thin_fabric
{
    diffusemap textures/wiki/thin_fabric_d.tga
    normalmap textures/wiki/thin_fabric_n.tga
    transmissionmap textures/wiki/thin_fabric_t.tga
}
```

### thicknessmap
`thicknessmap path`

* **path** — путь к карте толщины материала.

#### Описание и логика работы
`thicknessmap` дополняет transmission-ориентированные материалы данными о локальной толщине. В более тонких зонах свет может проходить иначе, чем в толстых, поэтому такая карта помогает делать правдоподобнее листья, уши, ткань, свечной воск и другие полупросвечивающие объекты.

Обычно `thicknessmap` применяют вместе с `transmissionmap`, а не вместо неё. Это продвинутая директива, рассчитанная прежде всего на кастомные или расширенные generic-программы FTE.

#### Практические сценарии использования
```
textures/wiki/leaf_broad
{
    diffusemap textures/wiki/leaf_broad_d.tga
    normalmap textures/wiki/leaf_broad_n.tga
    transmissionmap textures/wiki/leaf_broad_t.tga
    thicknessmap textures/wiki/leaf_broad_thick.tga
}
```

### program
`program name`
или
`program`
`{ ...shader source... }`

* **name** — имя уже зарегистрированной программы.
* **shader source** — встроенный текст программы в отдельном блоке сразу после директивы.

#### Описание и логика работы
`program` подключает к материалу пользовательскую шейдерную программу для текущего активного renderer backend'а. Парсер понимает два режима: ссылка на уже известную программу по имени либо встроенное тело программы в следующем блоке. Материальный уровень поддерживается ради совместимости и по-прежнему работает, хотя для сложных материалов гранулярность стадий иногда удобнее.

Это одна из самых мощных верхнеуровневых директив: она меняет не отдельную картинку, а фактически сам способ расчёта материала. С ней особенно часто сочетаются `diffusemap`, `normalmap`, `reflectmask`, `transmissionmap` и другие top-level texture slots.

#### Практические сценарии использования
```
textures/wiki/custom_metal
{
    program defaultwall#SPECULAR
    diffusemap textures/wiki/custom_metal_d.tga
    normalmap textures/wiki/custom_metal_n.tga
    specularmap textures/wiki/custom_metal_s.tga
}
```

### glslprogram
`glslprogram name`
или
`glslprogram`
`{ ...GLSL source... }`

* **name** — имя заранее известной GLSL-программы.
* **GLSL source** — встроенный GLSL-код в отдельном блоке.

#### Описание и логика работы
`glslprogram` — специализированный вариант `program`, который жёстко ориентирован на OpenGL/GLSL-путь. Он полезен, когда автор материала не хочет полагаться на «текущий backend», а хочет явно потребовать GLSL-реализацию. С точки зрения синтаксиса поддерживаются те же два режима: имя или встроенный блок кода.

Для кросс-рендерерных материалов лучше помнить, что такой шейдер не является универсальным автоматически. Если контент должен одинаково жить и в Direct3D-путях, обычно нужны альтернативы или fallback-логика.

#### Практические сценарии использования
```
textures/wiki/glow_floor
{
    glslprogram glow_floor_prog
    diffusemap textures/wiki/glow_floor_d.tga
    fullbrightmap textures/wiki/glow_floor_f.tga
}
```

### hlslprogram
`hlslprogram name`
или
`hlslprogram`
`{ ...HLSL source... }`

* **name** — имя HLSL-программы для Direct3D 9-пути.
* **HLSL source** — встроенный исходник HLSL.

#### Описание и логика работы
`hlslprogram` делает то же, что `program`, но адресует Direct3D 9-совместимый HLSL backend. Это полезно при переносе контента или при проекте, у которого есть собственный D3D9-ориентированный пакет материалов.

Если один и тот же материал должен существовать в нескольких renderer-путях, рядом могут понадобиться и другие backend-специфичные варианты. Сам по себе `hlslprogram` не создаёт GLSL-эквивалент.

#### Практические сценарии использования
```
textures/wiki/d3d_only_panel
{
    hlslprogram d3d_panel_prog
    diffusemap textures/wiki/d3d_only_panel_d.tga
    specularmap textures/wiki/d3d_only_panel_s.tga
}
```

### hlsl11program
`hlsl11program name`
или
`hlsl11program`
`{ ...HLSL source... }`

* **name** — имя HLSL-программы для Direct3D 11-пути.
* **HLSL source** — встроенный исходник HLSL.

#### Описание и логика работы
`hlsl11program` — вариант той же идеи для Direct3D 11. Выбирать его имеет смысл, когда материал целенаправленно опирается на D3D11-функциональность либо проект хранит разные версии программ под разные backend'ы.

Логика использования совпадает с `program` и `glslprogram`: либо ссылка по имени, либо встроенный блок. Если материал переносится между renderer'ами, стоит продумать fallback и совместимость заранее.

#### Практические сценарии использования
```
textures/wiki/d3d11_glass
{
    hlsl11program d3d11_glass_prog
    diffusemap textures/wiki/d3d11_glass_d.tga
    reflectmask textures/wiki/d3d11_glass_r.tga
}
```

### portalfboscale
`portalfboscale scale`

* **scale** — множитель размера render target'а для portal/mirror/reflection/refraction-путей; отрицательные значения обрезаются до безопасного нуля.

#### Описание и логика работы
`portalfboscale` регулирует разрешение вспомогательного буфера, который используется для порталов, зеркал, отражений и преломлений. Значение меньше `1` позволяет удешевить эффект ценой потери чёткости, а значение `1` стремится сохранить полноразмерную детализацию. Негативные числа не имеют смысла и автоматически прижимаются к нулю.

Это полезный практический рычаг для производительности. Большое зеркало во весь экран при `1.0` красиво, но дорого; маленький водоём или боковой монитор нередко отлично смотрятся и на уменьшенном масштабе.

#### Практические сценарии использования
```
textures/wiki/security_monitor
{
    portal
    portalfboscale 0.5   // render target вполовину экрана для экономии
    {
        map $whiteimage
    }
}
```
