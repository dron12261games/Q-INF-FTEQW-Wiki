# Структура папок игры

> [⬅ Вернуться к оглавлению вики](../README.md)

> Раздел: [Введение](./README.md)

## Зачем это нужно понимать в первую очередь

Прежде чем разбираться с картами, моделями, звуками или скриптами QuakeC, нужно один раз разобраться с самым фундаментальным вопросом: откуда движок вообще берёт файлы игры и как он решает, какую версию файла использовать, если одинаковые по имени ресурсы лежат в нескольких местах сразу. Без понимания этого механизма невозможно ни установить готовый мод, ни собрать свой собственный, ни разобраться, почему после добавления новой текстуры в игре всё ещё отображается старая. FTEQW не хранит все свои данные в одном месте и не требует единственно верного способа их разложить — вместо этого он использует гибкую многоуровневую систему поиска файлов, очень похожую на слоёный пирог: несколько «слоёв» данных накладываются друг на друга, и при поиске любого файла движок проходит слои по очереди, начиная с самого приоритетного, и останавливается на первом же слое, где нашёлся файл с нужным именем. Именно этот механизм лежит в основе модостроения: чтобы заменить, скажем, звук выстрела дробовика, автору мода вообще не нужно трогать оригинальные файлы игры — достаточно положить свой файл с точно таким же именем и путём в папку мода, у которой приоритет выше, чем у базовой игры.

## Базовая иерархия

```
папка_с_движком/              <- это и есть "basedir"
│
├── fteqw.exe                 <- исполняемый файл движка
│
├── id1/                      <- пример "basegame": данные основной игры (Quake)
│   ├── pak0.pak
│   ├── pak1.pak
│   └── ...
│
├── fortress/                 <- пример "gamedir": папка мода поверх id1
│   ├── progs.dat
│   ├── maps/
│   ├── models/
│   └── ...
│
└── myowngame/                 <- пример самостоятельной игры без basegame
└── ...
```

Три ключевых понятия, на которых строится вся система:

- **`basedir`** — корень, в котором движок вообще начинает искать какие-либо данные. По умолчанию это папка, где лежит сам исполняемый файл движка, но её можно переопределить.
- **`basegame`** (например, `id1`, `qw`, `id2`, `baseq3`) — папка с данными *основной* игры, то есть с тем контентом, который считается «фундаментом», поверх которого можно надстраивать моды. Можно указать сразу несколько `basegame`-папок одновременно — тогда движок будет искать файлы во всех перечисленных базовых папках по очереди, в порядке их подключения.
- **`gamedir`** — папка *конкретного мода*, надстроенная поверх `basegame`. Всё, что лежит в ней, имеет более высокий приоритет, чем одноимённые файлы из `basegame`: если и там, и там есть модель `models/player.mdl`, движок всегда возьмёт версию из папки мода, полностью проигнорировав версию из базовой игры.

## Базовая логика и жизненный цикл поиска файлов

Когда игровая логика или сам движок обращаются к какому-либо файлу (например, ищут текстуру `textures/wall01` или звуковой файл `sound/weapons/shotgn.wav`), запрос не идёт напрямую по пути на диске — вместо этого движок последовательно опрашивает цепочку подключённых источников данных в строго определённом порядке приоритета. Обычно порядок такой: сначала активный на данный момент `gamedir` (папка мода), затем все `basegame`-папки в порядке их регистрации, и в самом конце — так называемая «домашняя» папка пользователя, если она вообще подключена. Первый источник, в котором нашёлся файл с точным совпадением имени и относительного пути, и «побеждает» — оставшиеся источники дальше по цепочке даже не проверяются. Именно этот принцип и делает возможным то, что называется «переопределением ресурсов»: положив в папку мода файл `sound/weapons/shotgn.wav`, автор гарантированно подменяет звук выстрела во всей игре, не трогая ни одного байта в оригинальных архивах базовой игры — а если впоследствии этот файл из папки мода удалить, движок снова начнёт брать оригинальную версию из `basegame`, автоматически, без какой-либо дополнительной настройки.

Важная деталь, из-за которой этот механизм иногда неожиданно «не срабатывает» для новичков: источником данных для движка выступает не обязательно «голая» папка с россыпью файлов на диске. Точно таким же полноправным источником может быть архив (`.pak`, `.pk3`, `.pk3dir` и другие форматы — см. раздел [«Архивы и упаковка игрового контента»](../01-archives-packaging/README.md)), подключённый где-то в этой же цепочке приоритета. Для механизма поиска нет никакой разницы, читается ли файл прямо с диска как отдельный документ, или он находится внутри архива — единственное, что имеет значение, это то, в каком месте общей цепочки приоритета оказался тот источник (папка или архив), где данный файл впервые был найден. Отсюда следует практическое правило, которое ежедневно ломает голову начинающим мод-разработчикам: если в папке мода лежит и распакованная версия файла, и одноимённый пакованный архив, порядок между ними определяется отдельными правилами сортировки внутри одного и того же `gamedir` (как правило, «голые» файлы на диске имеют приоритет над архивами внутри той же самой папки), но при этом любой источник из папки мода всегда побеждает любой источник из `basegame`, вне зависимости от того, упакован он или нет.

## Пошаговый туториал: правильно разложить свой первый мод

**Шаг 1.** Найдите (или установите) папку с исполняемым файлом движка (`fteqw.exe` в Windows) — это и есть ваш `basedir`. Всё, что вы будете делать дальше, происходит внутри неё или рядом с ней.

**Шаг 2.** Убедитесь, что рядом с исполняемым файлом лежит папка с данными основной игры, например `id1` — она должна содержать хотя бы `pak0.pak` (эти файлы не входят в исходный код движка и берутся из купленной/скачанной копии оригинальной игры).

**Шаг 3.** Создайте рядом с `id1` новую пустую папку с именем вашего мода, например `mymod`. Эта папка станет вашим `gamedir`.

**Шаг 4.** Внутри `mymod` создайте такую же структуру подпапок, как в `id1` — по крайней мере те, которые вам нужны: `maps/`, `models/`, `sound/`, `textures/`, `progs.dat` (если вы компилируете собственный QuakeC — см. раздел [«QuakeC-скриптинг»](../16-quakec-scripting/README.md)).

**Шаг 5.** Положите в соответствующую подпапку внутри `mymod` файл, который должен «переопределить» оригинальный ресурс — с точно таким же относительным путём и именем, что и в `id1`. Например, чтобы заменить звук выстрела дробовика, файл должен лечь по пути `mymod/sound/weapons/shotgn.wav`.

**Шаг 6.** Запустите движок с параметром, указывающим использовать вашу папку как активный мод: `fteqw -game mymod`. Если всё сделано правильно, в игре будет использоваться контент из `id1` для всего, что не переопределено, и контент из `mymod` — для всего, что переопределено.

**Шаг 7.** Убедитесь, что переопределение сработало, воспользовавшись консольной командой `which <имя_файла>` (см. таблицу ниже) — она покажет, из какого именно источника данных (папки или архива) движок на самом деле взял указанный файл.

## Практический пример 1: минимальный мод, переопределяющий один звук

```
fteqw.exe
id1/
    pak0.pak
mymod/
    sound/
        weapons/
            shotgn.wav
```

Запуск: `fteqw -game mymod`

Разбор: движок находит `basedir` рядом с `fteqw.exe`, подключает `id1` как `basegame` (используется по умолчанию, отдельно указывать не нужно), а параметр `-game mymod` подключает папку `mymod` как активный `gamedir` с более высоким приоритетом. Когда игровая логика запрашивает `sound/weapons/shotgn.wav`, движок сначала проверяет `mymod/` — файл там есть, поэтому он используется, а одноимённый файл внутри `pak0.pak` из `id1` полностью игнорируется. Любой другой звук, отсутствующий в `mymod`, при этом продолжает нормально браться из `id1`.

## Практический пример 2: самостоятельная игра без basegame

```
fteqw.exe
myowngame/
    pak0.pak
    progs.dat
    maps/
        e1m1.bsp
```

Запуск: `fteqw -basegame myowngame`

Разбор: параметр `-basegame` (в отличие от `-game`) полностью заменяет собой список базовых игровых папок, поэтому движок даже не пытается заглянуть в `id1` — это правильный способ поставки полностью самостоятельной игры на основе FTEQW, где никакого «базового» Quake не подразумевается вообще. Такой режим типичен для тотальных конверсий и независимых проектов, которые используют движок как технологическую платформу, а не как надстройку над классическим Quake.

## Практический пример 3: перенос движка на защищённый от записи носитель

```
D:\ReadOnlyGames\FTEQW\fteqw.exe
D:\ReadOnlyGames\FTEQW\id1\pak0.pak
```

Запуск: `fteqw -basedir "D:\ReadOnlyGames\FTEQW" -homedir "C:\Users\Игрок\Documents\myFTEQW"`

Разбор: если сам движок с базовыми данными игры установлен на диск, доступный только для чтения (например, смонтированный образ или сетевой ресурс), необходимо явно указать `-homedir` — отдельную, обязательно доступную для записи папку, куда движок будет сохранять пользовательские настройки, файлы сохранений, скриншоты и демозаписи, не пытаясь писать что-либо рядом с исполняемым файлом. Без такого параметра запуск с носителя без прав на запись приведёт к тому, что настройки и сохранения не будут сохраняться между сессиями.

## Инженерный справочник: параметры и команды, управляющие поиском файлов

#### Параметры командной строки

| Параметр | Аргумент | Описание |
| :--- | :--- | :--- |
| `-basedir` | `<путь>` | Явно задаёт корневую папку, от которой отсчитываются все остальные пути поиска данных (`basegame`, `gamedir`). Полезно для отладки движка из другой директории или запуска с носителя, отличного от того, где лежит исполняемый файл. (По умолчанию: папка, где расположен исполняемый файл движка.) |
| `-basegame` | `<папка>` | Полностью заменяет список подключаемых базовых игровых папок на перечисленные через повторение параметра. Каждое повторение добавляет ещё одну базовую папку с более низким приоритетом, чем предыдущая. (По умолчанию: зависит от собранной версии движка, обычно `id1` для классического Quake.) |
| `-game` | `<папка>` | Подключает указанную папку как активный `gamedir` (мод) поверх базовых игровых данных — с наивысшим приоритетом поиска файлов. При повторении параметра каждая следующая папка добавляется с ещё более высоким приоритетом, чем предыдущая. (По умолчанию: не задан, используется только `basegame`.) |
| `-homedir` | `<путь>` | Явно переопределяет «домашнюю» пользовательскую папку, куда пишутся настройки, сохранения, скриншоты и демозаписи, вместо автоматически определяемой папки операционной системы. (По умолчанию: автоматически определяется ОС, например `%APPDATA%` в Windows.) |
| `-usehome` | `—` | Принудительно включает использование домашней папки, даже если по умолчанию для данной сборки движка она отключена. (По умолчанию: зависит от сборки.) |
| `-nohome` | `—` | Принудительно отключает использование домашней папки — все пользовательские файлы пишутся рядом с исполняемым файлом движка (`basedir`), как в старых версиях Quake. (По умолчанию: зависит от сборки.) |
| `-manifest` | `<файл.fmf>` | Загружает вместо ручных `-basegame`/`-game` единый файл-манифест, описывающий полный набор настроек игры/мода (см. раздел [«Мод-манифест-файл»](../23-mods-manifests/mod-manifest-file.md)). (По умолчанию: не задан.) |

#### Команды консоли

| Команда | Аргументы | Описание |
| :--- | :--- | :--- |
| `+gamedir` | `<папка>` | Работает так же, как `-game`, но задаётся в виде команды консоли, выполняемой на старте (полезно внутри `.cfg`-файлов и ярлыков запуска). (По умолчанию: не задан.) |
| `fs_restart` | `—` | Перечитывает все подключённые источники данных (папки и архивы) заново, без перезапуска самого движка — необходимо после добавления или удаления файлов на диске во время работы движка. |
| `fs_changegame` | `<имя>` | Переключает текущую активную игру или мод на другой, зарегистрированный ранее манифест, без полного перезапуска процесса движка. |
| `fs_changemod` | `<имя>` | Выполняет функцию транзитного онлайн-установщика: скачивает и подключает мод по идентификатору из внешнего каталога модов (например, интеграция с базой карт или модов сообщества). |
| `fs_showmanifest` | `—` | Выводит в консоль полное содержимое текущего активного манифеста — список подключённых папок, архивов и связанных с ними настроек. |
| `fs_flush` | `—` | Сбрасывает внутренний кэш файловой системы движка, заставляя его заново проверить содержимое дисковых источников при следующем обращении. |
| `dir` / `ls` | `<маска>` | Выводит список файлов, найденных по указанной маске во всех подключённых источниках данных одновременно (аналог команды листинга файлов в стиле Quake III). |
| `path` | `—` | Выводит список всех текущих подключённых путей поиска данных в порядке их приоритета — самый быстрый способ понять, что и в каком порядке видит движок прямо сейчас. |
| `flocate` / `which` | `<файл>` | Ищет указанный файл по всей цепочке подключённых источников и сообщает, в каком именно архиве или папке он был обнаружен первым — ключевой инструмент диагностики «почему не применилось моё переопределение». |
| `fs_hash` | `<файл>` | Вычисляет контрольную сумму (хеш) указанного файла — полезно для сверки версий контента между игроками или проверки целостности архива. |

## Домашняя (пользовательская) папка

Помимо папки самого движка, FTEQW может хранить пользовательские файлы (сохранённые настройки, сохранения игры, скриншоты, демозаписи) в отдельной «домашней» папке пользователя операционной системы — это особенно удобно, когда сам движок установлен в защищённое от записи место (например, в системную папку программ или на носитель только для чтения). Такое поведение управляется параметрами `-homedir`, `-usehome` и `-nohome`, подробно описанными в таблице выше; если ни один из них не задан явно, движок сам определяет, стоит ли использовать домашнюю папку, исходя из настроек конкретной сборки и доступности папки для записи.

## Файлы-манифесты как альтернатива ручной настройке

Вместо того чтобы каждый раз вручную перечислять параметры `-basegame`/`-game`, можно один раз описать всю конфигурацию мода/игры в отдельном файле-манифесте (расширение `.fmf`) и просто запускать движок с параметром `-manifest имяфайла.fmf`. Манифест может сразу задать название окна игры, список подключаемых папок данных, стартовые настройки и многое другое — подробно эта возможность описана в разделе [«Моды, сборки и манифесты»](../23-mods-manifests/README.md).

## Системные взаимосвязи

Порядок поиска файлов, описанный на этой странице, — это фундамент, от которого зависит буквально каждая другая система движка. Загрузчик архивов (раздел [«Архивы и упаковка»](../01-archives-packaging/README.md)) регистрирует свои `.pak`/`.pk3`-контейнеры именно как узлы в этой же самой цепочке приоритета, поэтому все правила переопределения одинаково работают что для «голых» файлов, что для файлов внутри архивов. Система автозагрузки контента с сервера (раздел [«Автодокачивание недостающего контента»](../26-content-autodownload/README.md)) при подключении к серверу сверяет именно эту иерархию папок клиента с требуемым списком файлов сервера, определяя, чего не хватает и куда это докачивать. Система сохранения игры (раздел [«Система сохранений»](../22-savegames/README.md)) и запись демозаписей (раздел [«Демозаписи»](../30-demos-recording/README.md)) по умолчанию пишут файлы именно в домашнюю пользовательскую папку, если она подключена, — то есть без понимания механизма `-homedir`/`-nohome` невозможно предсказать, где именно на диске окажется файл сохранения. Наконец, вся система мод-манифестов (раздел [«Мод-манифест-файл»](../23-mods-manifests/mod-manifest-file.md)) — это, по сути, просто удобная текстовая форма записи тех же самых правил `basegame`/`gamedir`, которые в противном случае пришлось бы каждый раз вручную набирать в командной строке.
