# Директивы поведения и появления

> [⬅ Вернуться к оглавлению вики](../README.md)

> [Индекс справочника директив .particles](./README.md)

Эта страница собирает директивы `.particles`, которые управляют не внешним видом частицы, а её появлением, траекторией, реакцией на среду и порождением связанных эффектов. Все имена и режимы ниже сверены по реальному парсеру `engine\client\p_script.c`, без вымышленных ключевых слов. Для удобства здесь сознательно пропущены чисто визуальные директивы вроде `alpha`, `scale`, [`color`](../39-entity-keys-reference/02-light-entity-keys.md#color), [`texture`](01-particle-effect-directives.md#texture), `count`, `die` и `type`, потому что они документируются отдельно. Если в коде директива помечена как устаревшая, это явно указано в её описании.

Отдельно важно: в формате `.particles` нет самостоятельной директивы `orientation` для обычных частиц. Ближайшие по смыслу средства из этой категории — [`stretchfactor`](01-particle-effect-directives.md#stretchfactor), `spawnmode`, смещения `spawn*`/`org*`/`vel*`, а также режимы столкновений и эмиссии.

## Директивы

### randomvel
`randomvel horizontal [vertical]`
`randomvel horizontal verticalMin verticalMax`

* **horizontal** — случайный разброс начальной скорости по двум боковым осям, в игровых единицах в секунду.
* **vertical** — симметричный разброс по оси «вверх/вдоль направления», в игровых единицах в секунду.
* **verticalMin**, **verticalMax** — явный нижний и верхний предел вертикальной компоненты.

#### Описание и логика работы
`randomvel` — сокращённая запись для комбинации `velwrand` и частично `velbias`. По X/Y она всегда задаёт симметричный случайный разброс, а по Z может работать либо как симметричный диапазон, либо как явный интервал `min..max`. Директива особенно удобна для искр, дыма и осколков, когда не нужен полный покомпонентный контроль. Если одновременно заданы `randomvel` и `velwrand`/`velbias`, последние дают более прямой и предсказуемый контроль, поэтому обычно выбирают что-то одно.

#### Практические сценарии использования
```
effect debris_randomvel
{
    count 8
    spawnmode ball
    spawnvel 30 50
    randomvel 60 -20 120
    gravity 700
    die 0.8 1.2
    type spark
}
```

### veladd
`veladd base [max]`

* **base** — доля входного направления/скорости эффекта, передаваемая частице.
* **max** — верхняя граница случайного диапазона; если указана, движок случайно выбирает значение от `base` до `max`.

#### Описание и логика работы
`veladd` масштабирует входной вектор эффекта — например, направление трассы, удара или выброса. Это не абсолютная скорость, а множитель к уже существующему направлению события. При наличии второго аргумента движок хранит разницу как случайную добавку, поэтому итоговая скорость равномерно гуляет внутри диапазона. Чаще всего `veladd` комбинируют со `spawnvel`: первый даёт движение вдоль основного импульса, второй — боковой разлёт по форме спауна.

#### Практические сценарии использования
```
effect bullet_dust_push
{
    count 6
    spawnmode box
    spawnorg 2 2
    veladd 120 220
    gravity 400
    friction 1.5
    die 0.3 0.6
    type normal
}
```

### orgadd
`orgadd base [max]`

* **base** — смещение точки рождения вдоль локальной оси направления, в игровых единицах.
* **max** — верхняя граница случайного диапазона для того же смещения.

#### Описание и логика работы
`orgadd` не ускоряет частицу, а двигает саму стартовую точку спауна вдоль оси эффекта. Это полезно, когда эмиттер должен рождать частицы чуть впереди дула, поверхности или центра взрыва, чтобы избежать самопересечения и визуального клипа. Со вторым аргументом смещение становится случайным в диапазоне `base..max`. В сочетании со `spawnorg` сначала формируется область спауна, а затем вся частица дополнительно выталкивается вдоль направления.

#### Практические сценарии использования
```
effect muzzle_smoke_offset
{
    count 5
    orgadd 6 12
    spawnorg 1 1
    veladd 40
    randomvel 8 4
    die 0.4 0.7
    type normal
}
```

### orgbias
`orgbias x y z`

* **x** — постоянное мировое смещение по оси X, в игровых единицах.
* **y** — постоянное мировое смещение по оси Y, в игровых единицах.
* **z** — постоянное мировое смещение по оси Z, в игровых единицах.

#### Описание и логика работы
`orgbias` добавляет фиксированное смещение уже после вычисления обычного спауна. В отличие от `orgadd`, оно задаётся в мировых координатах и не зависит от направления эффекта. Это удобно для подъёма дыма вверх, опускания пыли к полу или постоянного сдвига всего эмиттера в сторону. Если нужны локальные смещения относительно оси полёта, вместо `orgbias` обычно берут `spawnorg` или `orgadd`.

#### Практические сценарии использования
```
effect torch_smoke_bias
{
    count 3
    orgbias 0 0 6
    randomvel 4 10
    gravity -20
    die 1.5 2.0
    type normal
}
```

### velbias
`velbias x y z`

* **x** — постоянная добавка к скорости по оси X, в игровых единицах в секунду.
* **y** — постоянная добавка к скорости по оси Y, в игровых единицах в секунду.
* **z** — постоянная добавка к скорости по оси Z, в игровых единицах в секунду.

#### Описание и логика работы
`velbias` добавляет неизменную мировую скорость после всех случайных разбросов формы спауна. Это прямой способ сказать «каждая частица всегда получает ещё такой-то толчок», независимо от локальной ориентации эффекта. Полезно для ветра, общего подъёма дыма, осыпания искр по наклонной и подобных случаев. Если нужен именно случайный мировой шум, его удобнее задавать через `velwrand`.

#### Практические сценарии использования
```
effect ash_wind_bias
{
    count 7
    spawnmode box
    spawnorg 24 12
    velbias 20 0 12
    velwrand 8 8 4
    die 1.2 1.8
    type normal
}
```

### orgwrand
`orgwrand x y z`

* **x** — случайный мировой разброс позиции по X, в игровых единицах.
* **y** — случайный мировой разброс позиции по Y, в игровых единицах.
* **z** — случайный мировой разброс позиции по Z, в игровых единицах.

#### Описание и логика работы
`orgwrand` добавляет независимый от `spawnmode` случайный сдвиг в мировом пространстве. Движок выбирает случайный вектор внутри единичного объёма и масштабирует его отдельно по трём осям. Это хороший инструмент для «грязного» распределения, когда стандартных фигур `box`/`ball` недостаточно или когда эффект должен слегка «шуметь» даже при точно заданной форме спауна. Часто применяется вместе с `spawnmode syncfield`, чтобы сохранить общую структуру, но убрать стерильную регулярность.

#### Практические сценарии использования
```
effect ember_world_jitter
{
    count 10
    spawnmode uniformcircle
    spawnorg 18 0
    orgwrand 3 3 1
    spawnvel 12 24
    die 0.8 1.3
    type spark
}
```

### velwrand
`velwrand x y z`

* **x** — случайный мировой разброс скорости по X, в игровых единицах в секунду.
* **y** — случайный мировой разброс скорости по Y, в игровых единицах в секунду.
* **z** — случайный мировой разброс скорости по Z, в игровых единицах в секунду.

#### Описание и логика работы
`velwrand` добавляет случайную скорость в мировых координатах, независимо от локальной оси эффекта. Внутренне движок использует тот же случайный вектор, что и для `orgwrand`, поэтому положение и скорость могут получать согласованный случайный сдвиг. Это удобнее `randomvel`, когда нужен именно мировой разброс, а не локальный разлёт относительно направления выстрела, луча или следа. Хорошо сочетается с `velbias`, если нужен базовый ветер плюс шум.

#### Практические сценарии использования
```
effect steam_turbulence
{
    count 6
    velbias 0 0 24
    velwrand 10 10 18
    friction 0.8
    gravity -30
    die 1.0 1.6
    type normal
}
```

### friction
`friction xyz`
`friction xy z`
`friction x y z`

* **xyz** — одинаковая потеря скорости по всем осям, доля в секунду.
* **xy** — общая потеря скорости по X/Y, доля в секунду.
* **z** — отдельная потеря скорости по вертикали, доля в секунду.
* **x**, **y**, **z** — независимая потеря скорости по каждой оси, доля в секунду.

#### Описание и логика работы
На каждом кадре движок умножает скорость на `1 - friction * frametime`, поэтому `friction` задаёт именно темп затухания, а не мгновенный множитель. Значение `1` примерно означает полную потерю соответствующей компоненты за секунду; большие числа тормозят сильнее, а слишком большие на низком FPS могут приводить к неинтуитивному поведению. Если задать два аргумента, первый применяется к горизонтали, второй — к вертикали. Для осыпающихся искр типична низкая или нулевая горизонтальная потеря и более сильное гашение по Z.

#### Практические сценарии использования
```
effect chip_slide
{
    count 12
    spawnvel 90 40
    randomvel 20 10
    friction 0.4 2.2
    gravity 700
    die 0.5 0.9
    type spark
}
```

### gravity
`gravity value`

* **value** — изменение вертикальной скорости за секунду, в игровых единицах в секунду².

#### Описание и логика работы
`gravity` каждый кадр вычитает из Z-скорости величину `gravity * frametime`. Положительные значения тянут частицу вниз, отрицательные — вверх, что удобно для дыма, пара и магических аур. Масштаб соответствует внутренней физике движка; для «земных» тяжёлых осколков обычно используют сотни единиц, а для лёгкого подъёма — небольшие отрицательные значения. Если у частицы вообще нет скоростных модификаторов, одна только `gravity` уже переводит её в подвижный режим.

#### Практические сценарии использования
```
effect heavy_debris
{
    count 10
    spawnmode ball
    spawnvel 120 180
    gravity 900
    friction 0.6
    die 0.7 1.2
    type spark
}
```

### flurry
`flurry value`

* **value** — величина случайного бокового подталкивания, добавляемого во время полёта, в игровых единицах в секунду.

#### Описание и логика работы
`flurry` не влияет на стартовый спаун, а каждый кадр добавляет случайное отклонение по X/Y к уже летящей частице. Получается турбулентное, «дрожащее» движение, полезное для пламени, искрящейся пыли, снежной крупы и магических шлейфов. Так как Z напрямую не трогается, вертикальный характер движения по-прежнему контролируют `gravity`, `veladd` и прочие базовые директивы. Слишком высокие значения быстро превращают траекторию в шум.

#### Практические сценарии использования
```
effect fairy_trail_flurry
{
    count 5
    velbias 0 0 10
    flurry 18
    gravity -12
    friction 0.2
    die 0.9 1.4
    type normal
}
```

### assoc
`assoc effectName`

* **effectName** — имя другого эффекта, который нужно породить одновременно с текущим.

#### Описание и логика работы
[`assoc`](01-particle-effect-directives.md#assoc) связывает несколько самостоятельных описаний под одним вызовом: когда основной эффект спавнится, движок параллельно вызывает и связанный. Это не наследование и не «подэффект частицы», а именно второй полноценный эффект, живущий по своим правилам. Директива удобна для комбинаций вроде «искры + дым», «ядро + ореол», «осколки + пыль». Если эффект trail-типовый, у ассоциации поддерживается свой trailstate.

#### Практические сценарии использования
```
effect shell_impact_core
{
    count 8
    spawnmode ball
    spawnvel 80 120
    gravity 700
    assoc shell_impact_smoke
    die 0.4 0.8
    type spark
}
```

### inwater
`inwater effectName`

* **effectName** — эффект-замена, который будет использоваться, если исходная точка эффекта находится в жидкости.

#### Описание и логика работы
`inwater` — это переключатель варианта эффекта по содержимому среды. Если точка спауна попадает в `FTECONTENTS_FLUID`, движок один раз подменяет текущий тип на указанный. Это удобно для пар «пуля в воздухе / пузырьки под водой», «огонь / глушёный пар» и подобных ситуаций. Директива не фильтрует уже выбранный эффект по списку сред — для строгих ограничений служат `underwater` и `notunderwater`.

#### Практические сценарии использования
```
effect spark_or_bubbles
{
    count 6
    spawnvel 70 90
    gravity 750
    inwater spark_or_bubbles_underwater
    die 0.4 0.7
    type spark
}
```

### underwater
`underwater [contents ...]`

* **contents** — список типов содержимого: `water`, `slime`, `lava`, `sky`, `fluid`, `solid`, `playerclip`, `none`.

#### Описание и логика работы
`underwater` разрешает спаун только внутри перечисленного содержимого. Если аргументы не указаны, берётся общий фильтр `fluid`, то есть любые жидкие среды. Движок проверяет содержимое в точке спауна и пропускает эффект, если он находится не там, где нужно. Это хороший способ делать строго подводные пузырьки, глушёные взрывы в лаве или особые шлейфы только внутри конкретной среды.

#### Практические сценарии использования
```
effect bubble_column
{
    count 4
    underwater water slime
    velbias 0 0 30
    randomvel 3 10
    gravity -40
    die 1.2 1.8
    type normal
}
```

### notunderwater
`notunderwater [contents ...]`

* **contents** — список типов содержимого: `water`, `slime`, `lava`, `sky`, `fluid`, `solid`, `playerclip`, `none`.

#### Описание и логика работы
`notunderwater` работает зеркально к `underwater`: эффект пропускается, если точка находится внутри перечисленного содержимого. Без аргументов блокируются все жидкости. На практике эта директива нужна чаще, чем `underwater`, потому что позволяет без лишних переключателей защитить искры, дым, пыль и огонь от спауна в воде. Нельзя одновременно логично ограничить один и тот же эффект и `underwater`, и `notunderwater` на один и тот же набор сред.

#### Практические сценарии использования
```
effect dry_spark_only
{
    count 8
    notunderwater
    spawnvel 100 120
    gravity 800
    friction 0.5
    die 0.3 0.6
    type spark
}
```

### spawnmode
`spawnmode mode [param1] [param2]`

* **mode** — форма области появления: `box`, `circle`, `ball`, `spiral`, `tracer`, `telebox`, `lavasplash`, `uniformcircle`, `syncfield`, `distball`.
* **param1** — дополнительный параметр режима; смысл зависит от выбранного `mode`.
* **param2** — второй дополнительный параметр режима; смысл тоже зависит от `mode`.

#### Описание и логика работы
`spawnmode` — центральная директива формы спауна. `box` равномерно разбрасывает частицы в прямоугольном объёме и используется по умолчанию; `ball` — внутри шара; `circle` — по окружности; `uniformcircle` — равномерно по кругу без случайного заполнения; `tracer` и `spiral` предназначены для trail-эффектов; `telebox` и `lavasplash` повторяют классические схемы Quake; `syncfield` создаёт детерминированное поле, а `distball` даёт неравномерное заполнение шара с акцентом на особое распределение расстояний.

Для аргументов есть только режимозависимый смысл. У `spiral` `param1` задаёт длину одного витка вдоль trail, а `param2` — стартовый угол в градусах. У `telebox`/`lavasplash` `param1` меняет коэффициент скорости/формы, а `param2` — шаг дискретной сетки спауна. У `uniformcircle` `param1` служит дополнительным множителем углового шага. У `syncfield` `param1` задаёт вклад «орбитального» смещения, а `param2` — амплитуду пульсации радиуса. У `distball` оба параметра управляют внутренним распределением радиуса; это специальный режим с намеренно неравномерной статистикой, а не обычный шар.

#### Практические сценарии использования
```
effect teleport_shell
{
    count 48
    spawnmode telebox 0.55752 4
    spawnorg 16 24
    spawnvel 120 180
    gravity -80
    die 0.7 1.1
    type spark
}
```

### spawntime
`spawntime seconds`

* **seconds** — минимальный интервал между повторными срабатываниями trail/effect state, в секундах.

#### Описание и логика работы
`spawntime` ограничивает частоту появления эффекта, если у него есть trailstate. Пока таймер активен, повторный вызов просто ничего не спавнит. Это удобно для редких вспышек на непрерывном луче, редких хлопков дыма на постоянном источнике или экономии производительности на слишком частых трассах. Для одноразовых точечных эффектов без состояния директива обычно бесполезна.

#### Практические сценарии использования
```
effect arc_flash_sparse
{
    count 1
    spawntime 0.12
    spawnchance 1
    orgadd 2
    die 0.15 0.2
    type normal
}
```

### spawnchance
`spawnchance chance`

* **chance** — вероятность спауна, обычно в диапазоне от `0` до `1`.

#### Описание и логика работы
Перед созданием частиц движок сравнивает `spawnchance` со случайным числом `0..1`. Значение `1` означает «спавнить всегда» и используется по умолчанию; `0.5` — примерно половина срабатываний; `0` фактически подавляет эффект. Директива полезна для прореживания дорогих эффектов без переписывания их структуры. Практически разумно держаться диапазона `0..1`, хотя код не жёстко ограничивает значения.

#### Практические сценарии использования
```
effect sparse_dust
{
    count 6
    spawnchance 0.35
    spawnmode box
    spawnorg 6 2
    veladd 40
    die 0.25 0.45
    type normal
}
```

### step
`step distance [randomDistance] [extraCount]`

* **distance** — базовый шаг между соседними точками trail-спауна, в игровых единицах.
* **randomDistance** — дополнительная случайность шага; чем меньше число, тем гуще возможные вставки.
* **extraCount** — дробная добавка к общему числу частиц сверх обычного шага.

#### Описание и логика работы
`step` предназначен для trail- и beam-подобных эффектов, где частицы нужно раскладывать вдоль сегмента движения, а не порождать все в одной точке. Внутри движок хранит не только сам шаг, но и производное «частиц на единицу длины», поэтому директива влияет и на плотность, и на регулярность следа. Чем меньше `distance`, тем гуще след. В отличие от `count`, `step` хорошо сочетается с `averageout`, `nospreadfirst` и `nospreadlast`, потому что все они работают именно с линейным распределением вдоль трассы.

#### Практические сценарии использования
```
effect tracer_dense_line
{
    step 12 18 0
    spawnmode tracer
    spawnorg 2 0
    spawnvel 30
    die 0.06 0.1
    type spark
}
```

### cliptype
`cliptype effectName`

* **effectName** — имя эффекта, который должен породиться при столкновении частицы с поверхностью.

#### Описание и логика работы
[`cliptype`](01-particle-effect-directives.md#cliptype) превращает столкновение частицы в триггер нового эффекта. Если имя указывает на тот же самый эффект, частица будет просто отскакивать по собственным правилам; если на другой — исходная частица умирает, а на месте удара запускается новый эффект. В связке с `clipcount` и `clipbounce` можно построить богатые цепочки: искра ударяется о стену и рождает вторичные искры, капля дождя рождает брызгу, раскалённый кусок оставляет облачко пыли.

#### Практические сценарии использования
```
effect ricochet_seed
{
    count 1
    spawnvel 220 260
    gravity 900
    cliptype ricochet_burst
    clipcount 1
    clipbounce 0
    die 0.8
    type spark
}
```

### clipcount
`clipcount multiplier`

* **multiplier** — множитель количества частиц, порождаемых через `cliptype` при ударе.

#### Описание и логика работы
Когда `cliptype` вызывает другой эффект, `clipcount` масштабирует его интенсивность. Внутри движок делит это значение на базовый `count` целевого эффекта, поэтому удобнее воспринимать директиву как «желаемое относительное число спауна на удар». Значение `1` используется по умолчанию. Полезно, когда один и тот же вторичный эффект нужно вызывать то слабо, то мощно, не заводя дубликаты описаний.

#### Практические сценарии использования
```
effect glass_chip
{
    count 1
    spawnvel 180 220
    gravity 850
    cliptype glass_dust
    clipcount 3
    clipbounce 0
    die 1.0
    type spark
}
```

### clipbounce
`clipbounce value`

* **value** — коэффициент реакции на удар о поверхность.

#### Описание и логика работы
Если `cliptype` указывает на сам эффект, `clipbounce` работает как обычный коэффициент отскока: нормальная компонента скорости отражается и масштабируется этим числом. Значение по умолчанию — `0.8`. Если `cliptype` указывает на другой эффект, ненулевой `clipbounce` дополнительно передаёт ему нормаль поверхности, умноженную на этот коэффициент; при нуле передаётся нормализованная старая скорость частицы. Особый случай: отрицательное значение без заданного `cliptype` автоматически трактуется как самоклип, а значение `-2` даёт специальное поведение «убиться и splat-нуть как decal» для подходящих типов.

#### Практические сценарии использования
```
effect shard_bounce
{
    count 6
    spawnvel 140 180
    gravity 900
    friction 0.6
    clipbounce 0.45
    die 1.2 1.8
    type spark
}
```

### bounce
`bounce value`

* **value** — коэффициент отскока частицы от поверхности.

#### Описание и логика работы
`bounce` — короткая запись для случая «эта же частица должна отскакивать сама от себя». По сути директива выставляет `cliptype` в собственное имя эффекта и задаёт `clipbounce`. Использовать её стоит там, где не нужен отдельный вторичный эффект удара, а нужна только простая реакция осколка или искры на геометрию уровня. Если нужен вторичный эффект, лучше сразу писать явные `cliptype` + `clipbounce`.

#### Практические сценарии использования
```
effect pebble_bounce
{
    count 4
    spawnmode ball
    spawnvel 110 150
    gravity 900
    bounce 0.35
    die 1.0 1.4
    type spark
}
```

### emit
`emit effectName`

* **effectName** — имя эффекта, который частица должна порождать в процессе своей жизни.

#### Описание и логика работы
`emit` делает частицу мини-эмиттером. Если `emitinterval` положителен, вторичный эффект появляется периодически из текущей позиции частицы; если интервал отрицателен, движок вместо точечных выбросов запускает trail по перемещению частицы между кадрами. Это одна из самых мощных директив языка: с ней можно делать тлеющие угли, ракеты с дымным шлейфом, капли с хвостом, летящие руны и многое другое. Важное следствие: вторичный эффект наследует текущую позицию и скорость частицы-эмиттера, поэтому `veladd` и `gravity` материнской частицы напрямую влияют на характер дочернего следа.

#### Практические сценарии использования
```
effect ember_emitter
{
    count 3
    velbias 0 0 20
    flurry 10
    emit ember_smoke
    emitinterval 0.08
    die 1.4 2.0
    type normal
}
```

### emitinterval
`emitinterval seconds`

* **seconds** — интервал между дочерними выбросами, в секундах.

#### Описание и логика работы
`emitinterval` определяет, как часто частица с `emit` создаёт вторичный эффект. Положительные значения включают периодический таймер; отрицательные переводят систему в trail-режим между прошлой и новой позицией частицы. Нулевое или очень малое значение заставляет эмиттер срабатывать почти непрерывно, что быстро становится дорогим. Обычно эту директиву подбирают вместе со скоростью материнской частицы и плотностью дочернего эффекта.

#### Практические сценарии использования
```
effect rocket_core_emitter
{
    count 1
    veladd 300
    emit rocket_smoke
    emitinterval 0.03
    emitintervalrand 0.01
    die 0.9
    type normal
}
```

### emitintervalrand
`emitintervalrand seconds`

* **seconds** — случайная прибавка к `emitinterval`, в секундах.

#### Описание и логика работы
После каждого дочернего спауна движок берёт базовый `emitinterval` и добавляет к нему случайную величину от `0` до `emitintervalrand`. Это полезно против слишком механичных ритмов, особенно у магических частиц, тлеющих источников и лёгкого дыма. При нуле интервал становится полностью регулярным. Директива не имеет отдельного смысла без `emit` и положительного `emitinterval`.

#### Практические сценарии использования
```
effect unstable_magic_seed
{
    count 2
    velbias 0 0 8
    emit magic_sparkle
    emitinterval 0.05
    emitintervalrand 0.07
    die 1.2 1.8
    type normal
}
```

### emitstart
`emitstart seconds`

* **seconds** — задержка перед первым дочерним выбросом, в секундах.

#### Описание и логика работы
`emitstart` откладывает первый запуск `emit` после рождения частицы. Это помогает избежать слишком плотного старта, когда хвост не должен начинаться прямо в точке выстрела, или когда материнская частица сначала должна отлететь от источника. Для отрицательного trail-режима директива почти не нужна, а вот для периодических дочерних эмиттеров бывает очень полезна. Значение `0` означает немедленный старт.

#### Практические сценарии использования
```
effect delayed_smoke_seed
{
    count 1
    veladd 220
    emit delayed_smoke
    emitinterval 0.06
    emitstart 0.12
    die 0.8
    type normal
}
```

### spawnorg
`spawnorg horizontal [vertical]`

* **horizontal** — размер области спауна по двум боковым осям локального пространства, в игровых единицах.
* **vertical** — отдельный размер области по оси направления/высоты; если не указан, равен `horizontal`.

#### Описание и логика работы
`spawnorg` задаёт геометрию области рождения, а точный смысл зависит от `spawnmode`. Для `box` это полурасстояние вдоль локальных осей, для `ball` — радиус, для `circle`/`uniformcircle` — радиус окружности, для `telebox`/`lavasplash` — размеры сетки/объёма. Первый аргумент обычно описывает «боковой» размер, второй — вертикальный. Если частица должна рождаться почти в точке, оставляют нули и используют только `orgadd`.

#### Практические сценарии использования
```
effect dust_area_spawn
{
    count 14
    spawnmode box
    spawnorg 20 6
    randomvel 8 6
    gravity 150
    die 0.5 0.9
    type normal
}
```

### spawnvel
`spawnvel horizontal [vertical]`

* **horizontal** — скорость разлёта по боковым осям формы спауна, в игровых единицах в секунду.
* **vertical** — отдельная скорость по оси направления/высоты; если не указана, равна `horizontal`.

#### Описание и логика работы
`spawnvel` даёт частицам локальную скорость, направленную по форме выбранного `spawnmode`: из шара наружу, по окружности, по спирали, вбок у tracer-следа и так далее. Это одна из главных директив для «чувства» эффекта, потому что именно она превращает статичную область спауна в разлёт. Первый аргумент применяется к боковым компонентам, второй — к вертикальной/осевой. В большинстве эффектов `spawnvel` комбинируют с `veladd`: первая отвечает за разбрасывание, вторая — за общий импульс.

#### Практические сценарии использования
```
effect blast_ring
{
    count 20
    spawnmode circle
    spawnorg 24 0
    spawnvel 140 20
    gravity 120
    die 0.4 0.7
    type spark
}
```

### stretchfactor
`stretchfactor factor [minLength]`

* **factor** — коэффициент вытягивания частицы по направлению её скорости.
* **minLength** — минимальная длина вытягивания; полезна для быстрых, но визуально тонких искр.

#### Описание и логика работы
`stretchfactor` относится к поведению частицы в полёте: длина спрайта-искры начинает зависеть от скорости, а не только от статического размера. Это особенно важно для `type spark` и родственных режимов, где частица должна визуально «читатьcя» как след движения, а не как точка. Положительные значения вытягивают частицу пропорционально скорости, а дополнительный `minLength` не даёт коротким импульсам полностью схлопываться. На обычных круговых спрайтах директива либо малополезна, либо почти незаметна.

#### Практические сценарии использования
```
effect ricochet_stretch
{
    count 10
    spawnmode ball
    spawnvel 160 220
    stretchfactor 0.08 6
    gravity 850
    die 0.2 0.4
    type spark
}
```

### spawnparam1
`spawnparam1 value`

* **value** — первый дополнительный параметр текущего `spawnmode`.

#### Описание и логика работы
`spawnparam1` — устаревшая форма прямой записи первого параметра режима спауна. В современном описании тот же результат следует задавать как второй аргумент у `spawnmode`, например `spawnmode spiral 32 0`. Смысл значения зависит от режима: у `spiral` это длина витка, у `syncfield` — вклад орбитального смещения, у `telebox`/`lavasplash` — коэффициент «классической» формы, у `distball` — часть формулы радиального распределения. Использовать напрямую стоит только при поддержке очень старых конфигов.

#### Практические сценарии использования
```
effect legacy_spiral_alias
{
    count 12
    spawnmode spiral
    spawnparam1 32
    spawnparam2 90
    spawnvel 50
    die 0.6 1.0
    type spark
}
```

### spawnparam2
`spawnparam2 value`

* **value** — второй дополнительный параметр текущего `spawnmode`.

#### Описание и логика работы
`spawnparam2` — такой же устаревший алиас для третьего аргумента `spawnmode`. Как и `spawnparam1`, он не имеет универсального физического смысла: в `spiral` это стартовый угол, в `syncfield` — амплитуда радиального пульса, в `telebox`/`lavasplash` — шаг сетки, в `distball` — центр/смещение радиального распределения. Для новой документации и новых скриптов безопаснее всегда писать параметры прямо рядом с `spawnmode`, чтобы не терялась связь между режимом и числами.

#### Практические сценарии использования
```
effect legacy_field_alias
{
    count 20
    spawnmode syncfield
    spawnparam1 12
    spawnparam2 6
    spawnorg 18 18
    die 1.0 1.4
    type normal
}
```

### up
`up value`

* **value** — добавка к `orgbias` по оси Z, в игровых единицах.

#### Описание и логика работы
`up` — устаревший короткий алиас, который просто записывает значение в `orgbias[2]`. Он не меняет ориентацию частицы и не имеет отношения к современному «up-вектору»; фактически это лишь вертикальный сдвиг точки спауна в мировых координатах. Новые эффекты лучше писать через `orgbias 0 0 value`, чтобы поведение было явным и единообразным. Полезен только при переносе старых конфигов.

#### Практические сценарии использования
```
effect legacy_up_bias
{
    count 4
    up 10
    randomvel 6 12
    gravity -20
    die 0.8 1.1
    type normal
}
```

### viewspace
`viewspace [fraction]`

* **fraction** — степень перевода позиции и скорости в пространство камеры: от `0` (не применять) до `1` (полностью view-space).

#### Описание и логика работы
`viewspace` интерполирует положение и скорость частицы в координаты камеры. При записи без аргумента используется полное значение `1`. Это не «физика мира», а специальный пространственный режим для экранных и полуэкранных эффектов: мушечная гарь, HUD-пыль, магические блики перед камерой. Чем выше значение, тем меньше эффект зависит от настоящего мира и тем сильнее «прилипает» к виду игрока.

#### Практические сценарии использования
```
effect visor_speck
{
    count 1
    viewspace 1
    orgbias 6 0 -3
    velbias 0 0 2
    friction 1.5
    die 0.2 0.4
    type normal
}
```

### perframe
`perframe`

#### Описание и логика работы
`perframe` включает специальный режим, при котором внутреннее количество спауна делится на `host_frametime`. Практически это означает «считать интенсивность не за секунду, а за кадр», что особенно заметно у эмиттеров и непрерывных эффектов. Без этой директивы плотность зависит от обычных временных накоплений; с ней эффект может стать заметно гуще на высоком FPS. Использовать стоит осознанно и в основном для совместимости со старыми описаниями или для намеренно кадрозависимых эмиттеров.

#### Практические сценарии использования
```
effect perframe_sparks
{
    count 0.2
    perframe
    spawnvel 60 80
    randomvel 10 6
    die 0.15 0.25
    type spark
}
```

### averageout
`averageout`

#### Описание и логика работы
`averageout` влияет на trail-эффекты: движок подправляет шаг между точками так, чтобы частицы в среднем распределялись от начала до конца сегмента более равномерно. Это особенно полезно для молний, лазеров и других длинных линий, где обычный шаг может давать заметные «дырки» или неравномерный хвост у конца. На точечные вспышки директива не влияет. Обычно сочетается со `step` и режимами `beam`/trail.

#### Практические сценарии использования
```
effect lightning_nodes
{
    step 24 24
    averageout
    spawnmode tracer
    spawnvel 12
    die 0.08 0.12
    type spark
}
```

### nostate
`nostate`

#### Описание и логика работы
`nostate` запрещает использовать trailstate для этого эмиттера. На практике это отключает накопление длины, времени и связанных внутренних состояний между вызовами эффекта. Директива полезна, когда ассоциированный или следовой эффект должен каждый раз стартовать «с нуля», а не тянуть историю прошлого сегмента. Это может помочь и в борьбе с артефактами слишком длинных или слишком умных trail-цепочек.

#### Практические сценарии использования
```
effect reset_each_call
{
    step 20 20
    nostate
    spawnmode tracer
    spawnvel 16
    die 0.06 0.1
    type spark
}
```

### nospreadfirst
`nospreadfirst`

#### Описание и логика работы
У trail-эффектов `nospreadfirst` подавляет случайный разброс для первой порождённой частицы сегмента. Это удобно, когда начало следа должно точно совпадать с дулом, кончиком луча, центром снаряда или местом удара. Все остальные частицы продолжают использовать обычные `spawnorg`, `spawnvel`, `randomvel` и прочие отклонения. На одиночные нетрейловые эффекты польза минимальна.

#### Практические сценарии использования
```
effect tracer_clean_start
{
    step 18 18
    nospreadfirst
    spawnmode tracer
    spawnorg 3 0
    spawnvel 25
    die 0.08 0.12
    type spark
}
```

### nospreadlast
`nospreadlast`

#### Описание и логика работы
`nospreadlast` делает то же самое для последней частицы trail-сегмента. Это помогает аккуратно «пришить» конец следа к точке попадания, концу луча или позиции снаряда на текущем кадре. Обычно максимальный эффект достигается при совместном использовании `nospreadfirst` и `nospreadlast`, когда и начало, и конец линии остаются точными, а разброс сохраняется только внутри сегмента.

#### Практические сценарии использования
```
effect tracer_clean_end
{
    step 18 18
    nospreadlast
    spawnmode tracer
    spawnorg 3 0
    spawnvel 25
    die 0.08 0.12
    type spark
}
```

### rainfrequency
`rainfrequency multiplier`

* **multiplier** — множитель плотности для дождевых/небесных эмиттеров.

#### Описание и логика работы
`rainfrequency` используется не обычными точечными спаунами, а системой атмосферных осадков, которая распределяет частицы по поверхностям неба. По сути это отдельный коэффициент частоты для rain/snow-подобных эффектов. Значение `1` является базовым, большие числа делают выпадение гуще, меньшие — реже. В обычных локальных эффектах директива не даёт заметного результата.

#### Практические сценарии использования
```
effect ash_rain_dense
{
    count 1
```

### placeholder
`placeholder`

#### Описание и логика работы
`placeholder` переводит эффект в специальный режим-заглушку. При попытке использовать такой эффект движок выводит предупреждение и прекращает спаун, что удобно при поэтапной разработке большого набора частиц. Для игрового релиза директива обычно не нужна, но как инструмент контроля незавершённых эффектов она полезна. Внутри парсера это отдельный `spawnmode`, поэтому она реально участвует в логике спауна, а не просто служит комментарием.

#### Практические сценарии использования
```
effect todo_replace_me
{
    placeholder
    count 1
    die 0.1
    type normal
}
```
