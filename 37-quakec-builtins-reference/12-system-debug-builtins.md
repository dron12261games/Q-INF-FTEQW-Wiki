# Системные функции, отладка и cvar

> [⬅ Предыдущая страница](11-server-browser-builtins.md) | [Следующая страница ➡](14-editor-crypto-misc-builtins.md)

> [⬅ Вернуться к оглавлению вики](../README.md)
> [Индекс справочника builtins](../README.md#встроенные-функции-quakec-builtins)

Эта группа builtins отвечает за вывод текста, аварийную диагностику, доступ к cvar и отправку консольных команд в очередь движка. Здесь особенно важно различать контекст выполнения: часть функций рассчитана на серверный SSQC, часть — на локальный CSQC/MenuQC, а некоторые имеют исторические NQ/QW-варианты с разными сигнатурами. Для `print`, `bprint`, `sprint`, `cprint` и `centerprint` главное различие состоит в том, куда именно попадёт сообщение: в локальную консоль, всем игрокам, одному игроку или в центр экрана. Отладочные builtins вроде `error`, `objerror`, [`breakpoint`](#breakpoint), `stackdump`, `coredump` и `crash` стоит вызывать только осознанно, потому что они либо ломают текущий ход выполнения, либо специально провоцируют аварийную ситуацию ради диагностики.

## Функции

### error
`void(string err, ...) error = #10;`

* **err** — `string`, основная часть фатального сообщения об ошибке; дополнительные строковые аргументы конкатенируются движком в один текст.

#### Описание и логика работы

`error` — жёсткий аварийный выход из текущей QuakeC VM с понятным текстом в консоли. В `fteextensions.qc` он описан как builtin, который завершает игру или выполнение с легко заметным сообщением; в MenuQC у него есть legacy-привязка `#2`, а в SSQC используется номер `#10`. Практически это означает: если логика дошла до состояния, после которого продолжать работу уже небезопасно, лучше немедленно остановиться через `error`, чем оставлять мир в повреждённом состоянии. В FTEQW перед выводом сообщения также печатается стек вызовов, что делает builtin полезным не только для аварийного останова, но и для быстрой локализации места, где мод сломался.

#### Практические сценарии использования

```
void() WorldSpawn =
{
    if (!checkextension("DP_QC_CVAR_TYPE"))
        error("This mod requires DP_QC_CVAR_TYPE\n");

    if (!checkextension("DP_QC_CVAR_STRING"))
        error("This mod requires DP_QC_CVAR_STRING\n");
};
```

### objerror
`void(string err, ...) objerror = #11;`

* **err** — `string`, сообщение об ошибке, относящееся к текущей `self`; дополнительные аргументы склеиваются в единый текст.

#### Описание и логика работы

`objerror` нужен для ошибок, привязанных к конкретной entity. В отличие от `error`, который аварийно рвёт выполнение VM целиком, `objerror` печатает сообщение по проблемному объекту и дополнительно удаляет вызвавшую `self`. Именно этим builtin удобно выбраковывать битые сущности на этапе спавна: карта продолжит жить, но конкретный дефектный объект будет убран из мира. В MenuQC встречается legacy-номер `#3`; в серверной логике обычно ориентируются на поведение варианта `#11`, который удаляет текущую entity после отчёта.

#### Практические сценарии использования

```
void() monster_ogre =
{
    if (!self.targetname)
        objerror("monster_ogre without targetname at ", vtos(self.origin), "\n");

    precache_model("progs/ogre.mdl");
    setmodel(self, "progs/ogre.mdl");
};
```

### print
`void(string s, ...) print = #339;`

* **s** — `string`, первая часть выводимого текста; остальные аргументы объединяются в одну строку.

#### Описание и логика работы

`print` выводит текст только в локальную консоль той VM, где он вызван. В серверном SSQC это серверная консоль: игроки ничего не увидят, пока вы отдельно не пошлёте им `bprint`, `sprint` или `centerprint`. В CSQC и MenuQC одноимённый builtin остаётся локальным и пишет лишь в консоль текущего клиента или меню. В `fteextensions.qc` у функции есть старый menu-номер `#4`, а современный общий builtin объявлен как `#339`; в обоих случаях смысл одинаковый — это чисто локальный вывод без рассылки по сети.

#### Практические сценарии использования

```
void(entity player) DebugJoin =
{
    print("Player connected: ", player.netname, " from ", infokey(player, "ip"), "\n");
};
```

### bprint
`void(float msglvl, string s, optional string s2, optional string s3, optional string s4, optional string s5, optional string s6, optional string s7) bprint = #23;`

* **msglvl** — `float`, уровень сообщения для QuakeWorld-стиля вывода: `PRINT_LOW = 0`, `PRINT_MEDIUM = 1`, `PRINT_HIGH = 2`, `PRINT_CHAT = 3`.
* **s** — `string`, первая часть сообщения; остальные строковые аргументы дописываются следом.

#### Описание и логика работы

`bprint` рассылает текст всем подключённым игрокам. Это главное отличие от `print`: `print` остаётся локальным для консоли движка, а `bprint` идёт в клиентские консоли/сообщения всех игроков. В `fteextensions.qc` отдельно описаны две исторические формы: NQ-вариант без `msglvl` и QW-вариант с уровнем сообщения. Для FTEQW полезно помнить именно про QW-модель: клиент может фильтровать такие сообщения по своему `msg` [infokey](03-entity-world-builtins.md#infokey), поэтому системные уведомления лучше слать с `PRINT_HIGH`, а обычный шум — с более низким уровнем.

#### Практические сценарии использования

```
void(entity killer, entity victim) AnnounceFrag =
{
    bprint(PRINT_HIGH, killer.netname, " fragged ", victim.netname, "\n");
};
```

### msprint
`void(float clientnum, string text, ...) msprint = #6;`

* **clientnum** — `float`, локальный индекс клиента/слота, для которого адресуется сообщение в legacy-режиме.
* **text** — `string`, первая часть текста; остальные аргументы конкатенируются по тем же правилам, что и у других print-builtins.

#### Описание и логика работы

`msprint` — устаревший builtin из старого menu/client API. Он адресует вывод одному локальному клиенту по числовому слоту, а не по `entity`, и исторически относится к той же семье «персональных сообщений», что и `sprint`. В современном коде FTEQW его почти всегда лучше заменить на `sprint` или на локальный `print`/`cprint`, потому что `msprint` привязан к legacy-семантике и хуже читается. Использовать его имеет смысл только при сопровождении старого MenuQC/клиентского кода, где уже оперируют клиентскими слотами, а не сущностями.

#### Практические сценарии использования

```
void() Menu_ShowSplitScreenHint =
{
    // Сообщение только для первого локального игрока в legacy menu/client коде.
    msprint(0, "Press ENTER to join the server\n");
};
```

### cprint
`void(string s, ...) cprint = #338;`

* **s** — `string`, первая часть текста для вывода по центру экрана; остальные аргументы объединяются в одно сообщение.

#### Описание и логика работы

`cprint` показывает сообщение в центре экрана локального клиента. Это локальный builtin для CSQC/MenuQC: он не выбирает получателя по `entity` и не делает сетевую рассылку, а просто рисует текст там же, где обычный серверный `centerprint` появился бы на клиенте. Разницу удобно запомнить так: `cprint` — локальный центр-экранный вывод в текущей VM, `centerprint` — серверная отправка центр-экрана конкретному игроку. В MenuQC у `cprint` есть старый номер `#7`, а в CSQC в `fteextensions.qc` указан builtin `#338`.

#### Практические сценарии использования

```
void(float loading) CSQC_ShowDownloadState =
{
    if (loading)
        cprint("Downloading custom assets...\n");
};
```

### sprint
`void(entity client, float msglvl, string s, optional string s2, optional string s3, optional string s4, optional string s5, optional string s6) sprint = #24;`

* **client** — `entity`, игрок-получатель сообщения.
* **msglvl** — `float`, уровень сообщения (`PRINT_LOW`, `PRINT_MEDIUM`, `PRINT_HIGH`, `PRINT_CHAT`) для QW-совместимой фильтрации.
* **s** — `string`, первая часть текста; дополнительные строковые аргументы конкатенируются.

#### Описание и логика работы

`sprint` отправляет текст только одному конкретному игроку. Это его ключевое отличие от `bprint`, который вещает всем, и от `print`, который вообще не выходит за пределы локальной консоли VM. В `fteextensions.qc` описаны NQ-вариант без `msglvl` и QW-вариант с `msglvl`; на практике в FTEQW чаще всего удобно мыслить именно QW-формой, где игрок ещё и фильтрует часть вывода по своему `msg` уровню. Для приватных уведомлений — отказ открыть дверь, персональная подсказка, ответ админ-команды — `sprint` почти всегда правильнее, чем `bprint`.

#### Практические сценарии использования

```
void() trigger_secret_touch =
{
    if (other.classname != "player")
        return;

    sprint(other, PRINT_HIGH, "You found a secret area.\n");
};
```

### centerprint
`void(entity ent, string text, optional string text2, optional string text3, optional string text4, optional string text5, optional string text6, optional string text7) centerprint = #73;`

* **ent** — `entity`, игрок, которому нужно показать сообщение по центру экрана.
* **text** — `string`, первая часть текста; остальные строковые аргументы склеиваются в единый centerprint.

#### Описание и логика работы

`centerprint` — серверный способ показать текст по центру экрана одному игроку. Если нужно адресно предупредить клиента о захвате точки, начале таймера или невозможности использовать предмет, `centerprint` подходит лучше обычного `sprint`, потому что сообщение визуально заметнее. В отличие от `cprint`, здесь получатель задаётся явно через `entity`, а текст идёт по сети от SSQC к выбранному игроку. Обычно этот builtin используют для коротких, важных сообщений, потому что новая centerprint-строка быстро вытесняет предыдущую.

#### Практические сценарии использования

```
void() trigger_exit_touch =
{
    if (other.classname != "player")
        return;

    centerprint(other, "Exit unlocked\nRun to the slipgate!\n");
};
```

### dprint
`void(string s, ...) dprint = #25;`

* **s** — `string`, первая часть отладочного текста; остальные аргументы объединяются в одну строку.

#### Описание и логика работы

`dprint` — отладочный вывод, который в нормальном рабочем режиме не должен заспамливать консоль. По смыслу им пользуются для сообщений, которые нужны только при включённой диагностике, обычно с [`developer 1`](../38-cvars-reference/07-system-misc-cvars.md#developer). В `fteextensions.qc` сохранены исторические NQ/QW-комментарии, но в практической документации FTEQW безопаснее воспринимать `dprint` именно как «debug-only print»: пользователь без developer-режима не должен зависеть от этих сообщений. Если текст нужен игрокам или админам всегда, используйте `print`, `sprint` или `bprint`; если нужен только разработчику мода — `dprint`.

#### Практические сценарии использования

```
void() monster_demon1 =
{
    dprint("Spawning demon at ", vtos(self.origin), "\n");
    precache_model("progs/demon.mdl");
    setmodel(self, "progs/demon.mdl");
};
```

### coredump
`void() coredump = #28;`

* У функции нет аргументов.

#### Описание и логика работы

`coredump` записывает снимок состояния QC VM на диск. В комментариях `fteextensions.qc` прямо сказано, что builtin сохраняет стек, globals и данные сущностей и полезен именно для диагностики сложных проблем, когда простого `print` уже недостаточно. Это тяжёлый инструмент: он создаёт внешний файл и рассчитан на разбор проблемы после факта, а не на обычный игровой поток. Вызывать его стоит только в строго контролируемых debug-ветках, чтобы не захламлять рабочую директорию и не тормозить игру без необходимости.

#### Практические сценарии использования

```
void() DumpWorldState =
{
    if (!cvar("developer"))
        return;

    print("Writing QC core dump to disk\n");
    coredump();
};
```

### crash
`void() crash = #72;`

* У функции нет аргументов.

#### Описание и логика работы

`crash` — преднамеренная авария ради тестирования отладочной инфраструктуры. Даже комментарий в `fteextensions.qc` подчёркивает, что builtin существует как демонстрация того, что программы бывают ошибочны. Для обычной игровой логики он не нужен вообще: его не применяют ни для обработки ошибок, ни для пользовательских сообщений. Использовать `crash` допустимо только в полностью изолированных debug-сценариях, когда вы сознательно проверяете, как ведёт себя debugger, crash-handler или внешний мониторинг.

#### Практические сценарии использования

```
void() Cmd_TestCrash =
{
    if (!cvar("developer"))
        return;

    print("Forcing a QC crash for debugger verification\n");
    crash();
};
```

### stackdump
`void() stackdump = #73;`

* У функции нет аргументов.

#### Описание и логика работы

`stackdump` в текущем FTEQW привязан только к legacy-слоту MenuQC `#73`. Для серверного SSQC этот номер занят `centerprint`, поэтому считать builtin «общим серверным отладчиком» нельзя. В `menu.dat` вызов печатает стек QuakeC в консоль и полезен для локальной диагностики вместе с `developer 1`. Если нужен гарантированный аварийный отчёт именно из SSQC, надёжнее использовать `error` или `coredump`.

#### Практические сценарии использования

```
void() DebugUnexpectedState =
{
    dprint("Unexpected AI state in ", self.classname, "\n");
    stackdump();
};
```

---

### breakpoint
`void() breakpoint = #6;`

* У функции нет аргументов.

#### Описание и логика работы

`breakpoint` генерирует событие для отладчика QC. В `fteextensions.qc` прямо сказано, что FTEQW попытается остановиться в своём debugger, а другие движки могут просто рухнуть с debug-exception. Поэтому builtin нужно воспринимать как инструмент интерактивной разработки, а не как средство обработки ошибок в релизной сборке мода. Самый безопасный паттерн — вызывать `breakpoint` только за защитой вроде `if (cvar("developer"))` и только там, где разработчик реально ожидает остановку.

#### Практические сценарии использования

```
void() DebugTeleportTarget =
{
    if (!cvar("developer"))
        return;

    if (!self.target)
        breakpoint();
};
```

### cvar
`float(string name) cvar = #45;`

* **name** — `string`, имя cvar, которую нужно прочитать как число.

#### Описание и логика работы

`cvar` читает текущее значение консольной переменной и возвращает его как `float`. Если сама переменная строковая, движок всё равно попытается интерпретировать её как число по обычным правилам преобразования. Это простой способ быстро получать числовые настройки геймплея, например [`sv_gravity`](../38-cvars-reference/05-physics-gameplay-cvars.md#sv_gravity), [`skill`](../38-cvars-reference/04-network-server-cvars.md#skill) или собственные переменные мода. Важно не путать builtin с `cvar_string`: `cvar` нужен для числовой логики, тогда как `cvar_string` возвращает исходный текст без потери форматирования.

#### Практические сценарии использования

```
float() GetScaledJumpHeight =
{
    local float gravity;

    gravity = cvar("sv_gravity");
    if (gravity <= 0)
        gravity = 800;

    return 270 * (800 / gravity);
};
```

### cvar_set
`void(string cvarname, string valuetoset) cvar_set = #72;`

* **cvarname** — `string`, имя переменной, которую нужно изменить.
* **valuetoset** — `string`, новое строковое значение.

#### Описание и логика работы

`cvar_set` мгновенно записывает новое строковое значение в cvar. Это builtin именно для изменения уже существующей или заранее ожидаемой переменной, а не для её декларации: если мод хочет завести новую настройку «от своего имени», сначала логичнее использовать `registercvar`. По сравнению с `cvar_setf` эта версия удобна тогда, когда важно сохранить текст как есть: например [`hostname`](../38-cvars-reference/04-network-server-cvars.md#hostname), путь к ресурсу, алиасное имя режима и так далее. Если движок считает cvar приватной или недоступной для изменения из QC, операция может быть проигнорирована, поэтому для чувствительных сценариев полезно заранее проверять метаданные через `cvar_type`.

#### Практические сценарии использования

```
void() EnableLowGravityMode =
{
    cvar_set("sv_gravity", "400");
    bprint(PRINT_HIGH, "Low gravity mode enabled\n");
};
```

---

### cvar_setf
`void(string cvar, float val) cvar_setf = #176;`

* **cvar** — `string`, имя изменяемой переменной.
* **val** — `float`, новое числовое значение.

#### Описание и логика работы

`cvar_setf` делает то же самое, что `cvar_set`, но принимает число и сам переводит его в строковое представление движка. Это удобнее для чисто числовых настроек, потому что не нужно вручную собирать строку через [`ftos`](02-string-builtins.md#ftos) или [`sprintf`](02-string-builtins.md#sprintf). В `fteextensions.qc` builtin отдельно объявлен для SSQC, поэтому чаще всего его используют в серверной логике мода. Если значение в итоге должно выглядеть именно как число и дальше считываться через `cvar`, `cvar_setf` — самый прямой и читаемый вариант.

#### Практические сценарии использования

```
void(float newskill) SetSkillFromVote =
{
    cvar_setf("skill", bound(0, newskill, 3));
    bprint(PRINT_HIGH, "Skill is now ", ftos(cvar("skill")), "\n");
};
```

### cvar_string
`string(string cvarname) cvar_string = #448;`

* **cvarname** — `string`, имя переменной, которую нужно получить в исходном строковом виде.

#### Описание и логика работы

`cvar_string` возвращает текущее значение cvar как строку. В `fteextensions.qc` это описано отдельно от `cvar`, потому что задачи у них разные: `cvar` сразу приводит значение к `float`, а `cvar_string` сохраняет текстовую форму. Это особенно важно для переменных вроде [`hostname`](../38-cvars-reference/04-network-server-cvars.md#hostname), [`sv_mapcheck`](../38-cvars-reference/04-network-server-cvars.md#sv_mapcheck), путей, цветовых кодов и любых значений, где число — не единственный смысл. В реализации FTEQW строковый builtin отдаёт пользовательски видимое текущее значение, включая latched-строку, если движок уже принял отложенное изменение и ждёт момента его применения.

#### Практические сценарии использования

```
void(entity who) ReportHostname =
{
    sprint(who, PRINT_HIGH, "Server name: ", cvar_string("hostname"), "\n");
};
```

### cvar_defstring
`string(string name) cvar_defstring = #482;`

* **name** — `string`, имя cvar, для которой нужно получить значение по умолчанию.

#### Описание и логика работы

`cvar_defstring` возвращает не текущее, а дефолтное значение переменной. Это ключевая разница с `cvar_string`: `cvar_string` показывает, чем cvar является сейчас, а `cvar_defstring` — с какого значения она стартовала как «значение по умолчанию». Builtin особенно полезен в интерфейсах настроек и в админских командах типа «показать, что было переопределено». Если нужно решить, отличается ли переменная от базовой конфигурации, обычно сравнивают `cvar_string(name)` и `cvar_defstring(name)`.

#### Практические сценарии использования

```
void(entity who) ReportGravityOverride =
{
    local string current;
    local string def;

    current = cvar_string("sv_gravity");
    def = cvar_defstring("sv_gravity");

    sprint(who, PRINT_HIGH, "sv_gravity current=", current, " default=", def, "\n");
};
```

### cvar_description
`string(string cvarname) cvar_description = #518;`

* **cvarname** — `string`, имя переменной, для которой нужно получить текстовое описание.

#### Описание и логика работы

`cvar_description` возвращает человекочитаемое описание cvar, если движок или мод действительно зарегистрировали его. Это не замена `cvar_string` и не аналог `cvar_defstring`: builtin не читает значение, а достаёт help-текст для подсказок, меню и справки. Перед показом полезно проверить флаг `CVAR_TYPEFLAG_HASDESCRIPTION` через `cvar_type`, потому что далеко не все переменные снабжены осмысленным описанием. Если описания нет, результат может оказаться пустым, и UI лучше корректно пережить этот случай.

#### Практические сценарии использования

```
void(entity who) ShowCvarHelp =
{
    if (cvar_type("sv_gravity") & CVAR_TYPEFLAG_HASDESCRIPTION)
        sprint(who, PRINT_HIGH, cvar_description("sv_gravity"), "\n");
    else
        sprint(who, PRINT_HIGH, "sv_gravity has no registered description\n");
};
```

### cvar_type
`float(string name) cvar_type = #495;`

* **name** — `string`, имя переменной, чьи метаданные нужно получить.

#### Описание и логика работы

В `fteextensions.qc` используются флаги `CVAR_TYPEFLAG_EXISTS = 1`

#### Практические сценарии использования

```
void(entity who, string name) InspectCvar =
{
    local float flags;

    flags = cvar_type(name);
    if (!(flags & CVAR_TYPEFLAG_EXISTS))
    {
        sprint(who, PRINT_HIGH, "Unknown cvar: ", name, "\n");
        return;
    }

    sprint(who, PRINT_HIGH, name, " = ", cvar_string(name), "\n");

    if (flags & CVAR_TYPEFLAG_READONLY)
        sprint(who, PRINT_HIGH, "This cvar is read-only from QC\n");
};
```

### registercvar
`float(string name, string value, optional float flags) registercvar = #93;`

* **name** — `string`, имя новой cvar, которую мод хочет зарегистрировать.
* **value** — `string`, стартовое значение по умолчанию, применяемое только если такой cvar ещё не существует.
* **flags** — `float` *(optional)*, DP-совместимые биты регистрации; в текущем FTEQW реально распознаются cheat (`16`), archive (`32`), serverinfo (`256`), userinfo (`512`) и private/no-unsafe-expand (`2048`).

#### Описание и логика работы

`registercvar` — builtin для создания НОВОЙ cvar от имени QC. В серверной/общей таблице FTEQW он живёт на `#93`, а legacy-слот MenuQC по-прежнему использует `#42`. Если cvar уже существует — например, была создана движком или заранее выставлена через `set`/`seta`, — вызов становится no-op и возвращает `0`; если переменная действительно создана builtin'ом впервые, возвращается `1`. Это делает `registercvar` подходящим для одноразовой декларации настроек мода, а не для обычного runtime-апдейта, где правильнее `cvar_set` или `cvar_setf`.

#### Практические сценарии использования

```
void() InitModCvars =
{
    // 32 = archive: игрок сможет сохранить переменную через cfg_save / seta.
    registercvar("mymod_hardmode", "0", 32);
    registercvar("mymod_spawnscale", "1.0", 32);

    if (cvar("mymod_hardmode"))
        print("Hard mode is enabled\n");
};
```

### checkextension
`float(string extname) checkextension = #99;`

* **extname** — `string`, имя расширения движка, которое нужно проверить, например `"DP_QC_CVAR_TYPE"`.

#### Описание и логика работы

`checkextension` сообщает, поддерживает ли текущий движок указанное расширение QuakeC API. Это основной защитный builtin для кросс-движкового кода: сначала вы спрашиваете про `DP_QC_CVAR_TYPE`, `DP_QC_CVAR_STRING`, `FTE_QC_CHECKCOMMAND` и так далее, а уже потом вызываете связанные функции. В `fteextensions.qc` прямо рекомендуется использовать его именно как gate перед расширениями, а не как замену compile-time `#ifdef`. Если builtin возвращает `0`, нужно либо выбирать совместимый обходной путь, либо аварийно завершать инициализацию через `error` с понятным сообщением.

#### Практические сценарии использования

```
void() ValidateRequiredExtensions =
{
    if (!checkextension("DP_QC_CVAR_TYPE"))
        error("Missing required extension: DP_QC_CVAR_TYPE\n");

    if (!checkextension("DP_QC_CVAR_STRING"))
        error("Missing required extension: DP_QC_CVAR_STRING\n");
};
```

### logfrag
`void(entity killer, entity killee) logfrag = #79;`

* **killer** — `entity`, игрок или сущность, которой засчитывается убийство.
* **killee** — `entity`, жертва, которая погибла.

#### Описание и логика работы

`logfrag` — служебный QuakeWorld-ориентированный builtin для записи события фрага в серверный лог/статистику. Он не заменяет ваш геймплейный код подсчёта очков и не рассылает сообщения игрокам автоматически: задача builtin — зафиксировать сам факт убийства в той форме, которая нужна журналированию и внешним инструментам. В типичном death-обработчике `logfrag` вызывают рядом с увеличением счёта и рядом с пользовательским объявлением через `bprint`. Если мод ведёт совместимую статистику матчей, builtin полезен; если вам нужно только показать красивое сообщение, одного `bprint` недостаточно для логов, но и `logfrag` без `bprint` ничего игрокам не покажет.

#### Практические сценарии использования

```
void(entity killer, entity victim) FinishPlayerKill =
{
    killer.frags = killer.frags + 1;
    logfrag(killer, victim);
    bprint(PRINT_HIGH, killer.netname, " fragged ", victim.netname, "\n");
};
```

### setpause
`void(float pause) setpause = #531;`

* **pause** — `float`, `1` чтобы поставить сервер на паузу и `0` чтобы снять паузу.

#### Описание и логика работы

`setpause` переключает состояние паузы сервера из QuakeC. В `fteextensions.qc` отдельно оговорено, что builtin управляет именно игровой паузой сервера и не влияет на автоматические паузы интерфейса вроде поднятой консоли. Это полезно для tournament-режимов, scripted intermission-пауз или админских команд мода. Главное ограничение — относиться к нему как к серверному механизму синхронизации: если вы включили паузу, логика мира фактически перестанет течь как обычно, и это нужно учитывать при таймерах и отложенных действиях.

#### Практические сценарии использования

```
float g_match_paused;

void() Cmd_ToggleMatchPause =
{
    g_match_paused = !g_match_paused;
    setpause(g_match_paused);

    if (g_match_paused)
        bprint(PRINT_HIGH, "Match paused\n");
    else
        bprint(PRINT_HIGH, "Match resumed\n");
};
```

### localcmd
`void(string s, ...) localcmd = #46;`

* **s** — `string`, первая часть консольной команды; дополнительные аргументы объединяются в одну командную строку.

#### Описание и логика работы

`localcmd` добавляет текст в очередь консольных команд движка. Ключевой нюанс — команда не выполняется прямо в момент вызова builtin, а откладывается до начала следующего кадра, когда QC уже выйдет из текущего стека. Это делает `localcmd` безопаснее прямой рекурсии в консоль, но одновременно требует не забывать завершающий `\n` и понимать, что результат появится не мгновенно. Использовать builtin стоит осмотрительно: он удобен для `exec`, `map`, `restart`, `set`, `alias` и других консольных команд, но нельзя бездумно скармливать ему сырые пользовательские строки.

#### Практические сценарии использования

```
void() ReloadServerConfig =
{
    print("Queueing exec server.cfg\n");
    localcmd("exec server.cfg\n");
};
```

### abort
`void(optional __variant ret) abort = #211;`

* **ret** — `__variant` (optional), необязательное возвращаемое значение, которое будет принудительно возвращено текущим потоком, если код QC не выполняет это в явном виде; если параметр опущен, подставляется `0`.

#### Описание и особенности работы
Спецификация в `fteextensions.qc` указывает, что данный builtin мгновенно останавливает выполнение

#### Пример использования
```qc
float() RunDeferredOnce =
{
    if (!fork(0.1))
        return 0; // родительский поток продолжает работу

    print("child branch woke up\n");
    abort(1); // останавливаем выполнение текущего фонового потока и возвращаем 1 наружу
    return 0; // этот участок кода никогда не будет достигнут
};
```

### argc
`float() argc = #0:argc;`

* Параметры отсутствуют.

#### Описание и особенности работы
`argc` возвращает количество активных токенов (фрагментов строк) в текущем состоянии глобального системного токенизатора QC. На низком уровне функция `PF_ArgC` считывает значение внутренней переменной `qctoken_count`, которая обновляется каждый раз, когда скрипт выполняет методы [`tokenize`](02-string-builtins.md#tokenize), [`tokenize_console`](02-string-builtins.md#tokenize_console), [`tokenizebyseparator`](02-string-builtins.md#tokenizebyseparator) или смежные builtins. Оригинальный Си-комментарий разработчиков движка лаконично описывает этот метод как *"pointless, but whatever"*, поскольку большинство программистов QuakeC предпочитают считывать количество токенов напрямую как возвращаемое значение самой функции `tokenize(...)`. Тем не менее, `argc()` незаменим в изолированных функциях-обработчиках и колбэках, где у вас нет прямого доступа к результату выполнения парсера, но необходимо в цикле перебрать аргументы через [`argv()`](02-string-builtins.md#argv) для чтения параметров командной строки.

#### Пример использования
```qc
void(string cmdline) DebugTokenDump =
{
    local float i;

    tokenize_console(cmdline);
    for (i = 0; i < argc(); i = i + 1)
        print(sprintf("argv[%g] = %s\n", i, argv(i)));
};
```

### checkbuiltin
`float(__variant funcref) checkbuiltin = #0:checkbuiltin;`

* **funcref** — `__variant`, прямая ссылка на встроенную функцию, доступность которой необходимо проверить в текущей сборке движка; передается без кавычек и круглых скобок, например: `checkbuiltin(`[`drawtextfield`](09-csqc-input-ui-builtins.md#drawtextfield)`)`.

#### Описание и особенности работы
`checkbuiltin` осуществляет динамическую проверку (Feature Detection) того, реализована ли конкретная встроенная функция в запущенном исполняемом файле движка. Это критически важно при написании кроссплатформенного кода под современные расширения формата `#0:name`: если функция объявлена в QC-заголовках, но в текущем ядре (или в контексте конкретной VM) она отсутствует, заблокирована или подменена заглушками `PF_Fixme`/`PF_Ignore`, метод вернет `FALSE`. Использование этого механизма защищает программу от критических падений интерпретатора типа *Bad Builtin* при попытке вызова неподдерживаемого метода на старых клиентах. Позволяет гибко выстраивать логику фоллбэков (fallbacks) для продвинутых визуальных и файловых эффектов.

#### Пример использования
```qc
void() Menu_DrawWrappedTextSafely =
{
    if (checkbuiltin(drawtextfield))
        drawtextfield('32 32 0', '256 48 0', 3, "wrapped text via builtin");
    else
        drawstring('32 32 0', "wrapped text via fallback", '8 8 0', '1 1 1', 1, 0);
};
```

### externrefcall
`__deprecated("Redundant") __variant(float prnum, void() func, ...) externrefcall = #205;`

* **prnum** — `float`, внутренний индекс целевого прогс-контекста (progs context), к которому осуществляется обращение.
* **func** — `void()`, указатель на целевую QC-функцию во внешнем модуле.
* **...** — дополнительные аргументы, которые будут упакованы и переданы в вызываемую функцию через системный стек интерпретатора.

#### Описание и особенности работы
`externrefcall` — это устаревший низкоуровневый встроенный метод для выполнения прямого вызова функции, расположенной в другом прогс-контексте (например, вызов функции MenuQC из контекста CSQC). В современной спецификации движка FTEQW этот метод помечен атрибутом `__deprecated("Redundant")`, так как движок обзавелся встроенной автоматической системой межмодульных вызовов, прозрачной для компилятора. Процедура ядра `PF_externrefcall` выполняет сложную системную операцию: она подменяет активные указатели на аргументы, подготавливает слоты глобальных переменных, переключает контекст через `PR_ExecuteProgram` и затем возвращает состояние интерпретатора обратно в исходный `prnum`. Использование этого метода вручную создает риски порчи стека, поэтому в современном QuakeC-коде от него следует полностью отказаться.

#### Пример использования
```qc
void() LegacyTarget =
{
    print("legacy cross-progs callback\n");
};

void() CallLegacyCompatPath =
{
    // Ручной кросс-модульный вызов функции LegacyTarget;
    // в современном QC этот код заменен на прямое обращение
    externrefcall(-1, LegacyTarget);
};
```
