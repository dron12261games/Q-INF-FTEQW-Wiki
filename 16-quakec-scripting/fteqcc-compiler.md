## Что это даёт геймдизайнеру

Исходный код на QuakeC (файлы `.qc`) — это просто текст, который сам по себе игру не запустит. Чтобы движок мог его выполнить, текст нужно превратить в компактный бинарный файл со специальным байт-кодом — эту работу выполняет компилятор **FTEQCC** (сокращение от «FTE QuakeC Compiler»). Понимание того, как устроена эта сборка, нужно любому автору мода, ведь без неё ни одно изменение в коде логики не попадёт в игру.

## Интерфейс настройки

### Список исходников: файл `progs.src`

Компилятору нужно знать, какие именно файлы `.qc` и в каком порядке собирать. Для этого используется текстовый файл, который по договорённости называется **`progs.src`** для серверной логики (SSQC), **`csprogs.src`** для клиентской логики (CSQC) и **`menu.src`** для логики меню (MenuQC). Пример типичного содержимого:

```c
// Первый непустой/некомментарийный символ файла — # означает "новый стиль" progs.src
#pragma PROGS_DAT "qwprogs.dat"

#include "defs.qc"
#include "subs.qc"
#include "weapons.qc"
#include "world.qc"
#include "player.qc"
```

Директива `#pragma PROGS_DAT "имя_файла.dat"` задаёт имя итогового скомпилированного файла (по умолчанию — `progs.dat`). Директива `#include "файл.qc"` подключает содержимое другого файла с исходным кодом ровно на этом месте — то есть весь проект мода на самом деле собирается как **один большой файл**, просто разбитый на удобные для чтения части, объединяемые в порядке перечисления в `progs.src`. Из-за этого важно подключать файлы в правильном порядке: если один файл использует функцию или поле, объявленное в другом файле, тот файл должен быть подключён раньше (либо соответствующее объявление нужно вынести в общий заголовочный файл — см. [«Стандартные заголовочные файлы для QuakeC»](./standard-header-files.md)).

Дополнительно можно объявлять собственные условные флаги компиляции прямо в `progs.src` (директивами `#define`/`#ifdef`/`#else`/`#endif`, точно как в языке C), чтобы собирать разные варианты мода из одного набора исходников:

```c
#define MONSTERS

#ifdef MONSTERS
#include "monsters.qc"
#else
#include "nomonst.qc"
#endif
```

Ещё одна полезная директива — `#pragma target fte` — явно указывает компилятору собирать код в «расширенном» формате байт-кода FTE (с поддержкой более широких типов данных и возможностей движка), а не в исходном, ограниченном формате байт-кода id Software 1996 года.

### Как запустить компиляцию

Есть два равноценных способа собрать мод:

1. **Прямо внутри самого движка**, без выхода из игры — консольной командой `compile` (по умолчанию собирает `progs.src` из текущей игровой папки в `progs.dat`; можно явно указать другой файл списка исходников, например `compile csprogs.src`). Это удобно тем, что не нужно возиться с отдельной программой — движок содержит в себе версию FTEQCC.
2. **Отдельной программой-компилятором** FTEQCC, запускаемой вне игры (например, из командной строки или через сторонний редактор кода с поддержкой QuakeC) — так собирают более крупные проекты, а также в тех случаях, когда результат сборки нужно куда-то распространять отдельно от исходников.

После правки кода командой **`applycompile`** можно применить только что собранный код «на лету», без перезапуска карты и без отключения игроков — по сути, это быстрое сохранение и мгновенная загрузка игры с новым кодом. Это не проверяет и не переносит новые поля объектов автоматически — подходит для быстрой проверки одной подправленной функции, а не для полной переработки структуры данных мода. Подробнее о живой правке кода без остановки игры — в статье [«Отладка и „горячая“ пересборка логики»](./hot-reload-debugging.md).

## Типичные ошибки компиляции и что они значат

Компилятор останавливает сборку и сообщает об ошибке, если находит нарушение синтаксиса или явную нестыковку типов данных. Разбираться в сообщениях об ошибках — обычный навык, который нарабатывается с практикой, но несколько самых частых причин стоит знать заранее:

- **Пропущенная точка с запятой** — компилятор обычно указывает на строку, которая идёт *после* настоящего места ошибки (потому что до самой точки с запятой он ещё «ждал продолжения» предыдущей инструкции).
- **Несовпадение типов** — например, попытка присвоить `entity`-значение переменной типа `float`, или передать строку туда, где функция ожидает число.
- **Использование неизвестного имени** — обращение к функции, полю или переменной, которая нигде не была объявлена (либо опечатка в имени, либо забыли подключить нужный `#include`, либо файл с объявлением подключён в `progs.src` *после* места использования).
- **Незакрытая фигурная скобка или комментарий** — если где-то в файле не хватает закрывающей `}` или `*/`, ошибка компиляции может показаться в совершенно неожиданном, отдалённом месте файла — стоит перепроверить именно баланс скобок и комментариев.

## Отладка скомпилированного мода

Движок умеет не только компилировать, но и помогать искать причины уже возникших логических ошибок и падений:

- Команда **`breakpoint`** (по имени функции или по файлу и номеру строки) — ставит точку останова выполнения кода; когда движок доходит до этого места, включается пошаговый режим отладки прямо поверх игры (при включённой переменной `developer` и наличии рядом с скомпилированным файлом дополнительного файла с расширением `.lno`, который также создаётся компилятором и хранит соответствие байт-кода номерам строк исходного текста).
- Встроенная функция **`traceon`** позволяет включить такой же пошаговый режим прямо из кода мода, программно, как «точку останова», зашитую в самой логике.
- Если падение игры вызвано ошибкой в коде мода, движок автоматически создаёт **дамп состояния** («coredump») в папке мода — текстовый файл с содержимым локальных переменных всех ещё не завершившихся функций на момент сбоя; такой же дамп можно запросить вручную командой `coredump_ssqc`.

## Примеры

- Автор мода добавляет новую функцию в файл `weapons.qc`, набирает в игровой консоли `compile`, затем `applycompile` — и тут же проверяет новое оружие в текущей тестовой игре, не выходя и не переподключаясь.
- Крупный командный проект держит два варианта `progs.src` — один с `#define MONSTERS` для одиночной игры с монстрами, другой без него для чисто многопользовательского режима, — и оба собираются из одного и того же набора файлов исходного кода.
- При падении сервера с сообщением об ошибке в коде мода разработчик открывает автоматически созданный файл дампа в папке мода и по именам локальных переменных в нём понимает, какая именно функция и с какими данными привела к сбою.
