## Что это даёт геймдизайнеру

Прежде чем пользоваться справочником встроенных функций и стандартными полями объектов, стоит один раз разобраться с самим языком, на котором пишется вся игровая логика — **QuakeC**. Это не язык общего назначения вроде C++ или Python: он был создан специально для описания игровой логики Quake ещё в 1996 году и намеренно устроен просто — без указателей, без сложных структур данных, зато с очень прямой связью между кодом и тем, что происходит в игре. Разобравшись один раз с базовым синтаксисом, вы сможете читать и писать любой код на SSQC, CSQC или MenuQC — все три используют один и тот же язык, различаясь лишь набором доступных функций и тем, на чьей стороне (сервер/клиент/меню) выполняется код.

Важное уточнение сразу: то, что описано на этой странице, — это возможности **компилятора FTEQCC** (см. [«Компилятор FTEQCC»](./fteqcc-compiler.md)), который используется для сборки логики в движке FTEQW. Самый первый, оригинальный QuakeC от id Software 1996 года был заметно беднее — в нём, например, не было циклов `for`, оператора `switch`, тернарного оператора `?:` и многих других удобств, перечисленных ниже. Там, где это важно, мы отдельно отмечаем: «это было и в оригинальном QuakeC» или «это добавил FTEQCC».

Помимо базового синтаксиса, страница также разбирает две связанные темы: набор **расширенных возможностей движка**, которые выходят за пределы возможностей самого языка (скелетная анимация из кода, кооперативная многопоточность, битовые операции и т.д.), и систему **модульных прогс-файлов** — механизм, которым движок подгружает независимые аддон-скрипты поверх уже загруженной основной логики мода. В самом низу страницы находится компактный «Справочник синтаксиса» со всеми ключевыми словами, операторами, литералами и прочими элементами языка — без исключений, включая редкие расширения для режимов совместимости с другими диалектами QuakeC (Reacc, HexenC, FrikQCC, C-стиль).

## Типы данных

В QuakeC всего несколько базовых типов данных — и это фундаментальное отличие от большинства современных языков программирования. FTEQCC дополнительно добавляет набор числовых типов из мира языка C для более точного контроля над разрядностью и знаком — они не входят в самый первый набор оригинального QuakeC 1996 года и почти всегда используются в паре с расширенным (`fte`) форматом байт-кода; часть из них включена по умолчанию, часть требует явного флага компилятора (подробности о флагах `-K`/`-F` — в статье [«Компилятор FTEQCC»](./fteqcc-compiler.md#флаги-компилятора-и-ключевые-слова--f---k)):

| Тип | Что хранит | Пример | Статус |
|---|---|---|---|
| `float` | Число с плавающей точкой (используется и для чисел, и для «условной правды/лжи» — 0 считается ложью, любое другое число правдой) | `float health;` | Оригинал |
| `vector` | Три числа сразу — точка в пространстве или направление (x, y, z) | `vector origin;` | Оригинал |
| `string` | Текстовая строка | `string message;` | Оригинал |
| `entity` | Ссылка на игровой объект (сущность) в мире | `entity target;` | Оригинал |
| `void` | «Пустота» — используется только как тип возвращаемого значения функции, которая ничего не возвращает | `void() Explode;` | Оригинал |
| `int` / `integer` | 32-битное целое число | `int n;` | Расширение, включено по умолчанию |
| `unsigned` | Беззнаковый модификатор целого типа | `unsigned int u;` | Расширение, включено по умолчанию |
| `signed` | Явно знаковый модификатор | `signed int s;` | Расширение, флаг `signed` |
| `long` | Модификатор увеличенной разрядности | `long x;` | Расширение, флаг `long` |
| `short` | 16-битное целое число | `short x;` | Расширение, флаг `short` |
| `char` | 8-битное целое число | `char c;` | Расширение, флаг `char` |
| `double` | 64-битное число с плавающей точкой | `double d;` | Расширение, флаг `double` |
| `_Bool` | Логический тип из C99 | `_Bool ok;` | Расширение, всегда доступно |

Сверх этих типов FTEQCC добавляет ещё один базовый строительный блок — **тип-функцию** (`result_type(types_arguments)`), который используется и как самостоятельный тип переменной (ссылка на функцию с конкретной сигнатурой), и в объявлении самих функций (см. [«Функции»](#функции-два-способа-объявления) ниже):

```c
void() callback;                       // переменная-ссылка на функцию без аргументов
float(entity who) healthgetter;        // ссылка на функцию, принимающую entity и возвращающую float

callback = SUB_Null;                   // можно присвоить ссылку на существующую функцию
healthgetter = GetHealthOf;
```

Кроме простых типов компилятор понимает и составные — `struct`, `union`, `enum`/`enumflags`, а также классы (`class`/`accessor`) с наследованием и методами. Они рассмотрены подробнее в таблице [«Составные типы, перечисления и классы»](#составные-типы-перечисления-и-классы) справочника в конце страницы.

## Переменные и поля объектов

QuakeC различает **обычные переменные** (глобальные или локальные) и **поля объектов** (entity fields) — то, что хранится не «само по себе», а прикреплено к конкретному игровому объекту, как ячейка в его личной анкете.

```c
float   myglobalcounter;   // обычная глобальная переменная — одна на весь мир игры

.float  health;            // ПОЛЕ объекта — у КАЖДОГО объекта своё собственное значение health
.vector origin;             // поле-вектор — тоже у каждого объекта своё
```

Разница видна по точке перед именем: `.float health;` объявляет поле, которое есть у любого объекта в игре (и `self.health`, и `other.health`, и `some_monster.health` — у каждого своё собственное число). Без точки — `float myglobalcounter;` — это одна-единственная переменная на всю игру, общая для всех.

Обращение к полю конкретного объекта пишется через точку после имени объекта:

```c
self.health = self.health - 10;   // отнять 10 очков здоровья у текущего объекта
other.frags = other.frags + 1;    // добавить одно очко второму участнику события
```

## Функции: два способа объявления

Классический QuakeC 1996 года объявляет функцию непривычным для многих других языков образом — тип возвращаемого значения указывается вместе со списком типов аргументов в скобках, а имя функции идёт уже после этого блока, а само тело присваивается функции через `=`, как обычное значение:

```c
// Функция без аргументов, ничего не возвращает
void() SUB_Null =
{
	// тело функции
};

// Функция с двумя аргументами (entity и float), возвращает float
float(entity who, float amount) TakeDamage =
{
	who.health = who.health - amount;
	return who.health <= 0;
};
```

FTEQCC дополнительно понимает и привычный по языку C синтаксис объявления функций — тип, затем имя, затем список аргументов в скобках, а тело идёт сразу в фигурных скобках, без `=`:

```c
// То же самое, но в C-стиле
float TakeDamage(entity who, float amount)
{
	who.health = who.health - amount;
	return who.health <= 0;
}
```

Оба варианта равноценны и порождают полностью одинаковый результат компиляции — можно свободно выбирать любой из них по вкусу или смешивать оба стиля в одном проекте. Разбор C-стиля в компиляторе не зависит от каких-либо специальных флагов и включён всегда. Единственное практическое ограничение касается редкого случая: если компилятор явно переключён в режим, отключающий ключевые слова, специфичные для QC (пресеты вроде строгой C-совместимости), то C-стиль объявления функции **внутри тела другой функции** (то есть как локальное объявление) трактуется лишь как внешняя ссылка на уже существующую функцию, а не как полноценное определение с телом — в обычном режиме работы FTEQCC такого ограничения нет.

Такая же форма объявления — с блоком `{ }`, замененным на специальное значение вместо него — используется для объявления **встроенных функций движка** (builtins из справочника). Здесь допустим только классический QC-стиль:

```c
void(entity e, string s) sprint = #24;   // это builtin: движок сам знает, что делает функция #24
```

Число после `#` — это номер встроенной функции внутри движка; такие функции не имеют тела на QuakeC, их поведение целиком реализовано внутри движка на низком уровне (подробнее — во всех статьях [справочника встроенных функций](../README.md#встроенные-функции-quakec-builtins)). Способ объявления самой функции (QC-стиль или C-стиль) никак не влияет на то, как объявляется builtin — только на функции с телом на QuakeC.

Ссылку на функцию можно хранить и передавать как обычное значение — например, в поле `think`:

```c
self.think = SUB_Null;
self.nextthink = time + 1;
```

## Операторы

Ниже — полный список операторов, которые понимает FTEQCC, сгруппированный по назначению. Столбец «Статус» отмечает, был ли оператор в оригинальном QuakeC 1996 года или добавлен FTEQCC; часть расширений включена по умолчанию, часть требует конкретного флага компилятора (подробности о флагах `-K`/`-F` — в статье [«Компилятор FTEQCC»](./fteqcc-compiler.md#флаги-компилятора-и-ключевые-слова--f---k)).

**Арифметические** — сложение, вычитание, умножение, деление доступны с самого первого QuakeC; остаток от деления, возведение в степень и векторное произведение добавлены FTEQCC:

```c
float total = a + b - c;
float area = width * height;
float rem = 7 % 2;          // остаток от деления — 1
vector n = forward >< up;    // векторное произведение двух направлений
```

| Оператор | Что делает | Пример | Статус |
|---|---|---|---|
| `+` | Сложение чисел/векторов, конкатенация указателей | `a + b` | Оригинал |
| `-` | Вычитание; также унарный минус (смена знака) | `a - b`, `-x` | Оригинал |
| `*` | Умножение; в унарной форме — разыменование указателя | `a * b`, `*ptr` | Оригинал (unary `*` — расширение) |
| `/` | Деление | `a / b` | Оригинал |
| `%` | Остаток от деления | `a % b` | Расширение FTEQCC |
| `*^` | Возведение в степень | `a *^ b` | Расширение FTEQCC |
| `**` | То же, что `*^` (если включён флаг `ssp`, по умолчанию для `-std=gmqcc`) | `a ** b` | Расширение FTEQCC |
| `><` | Векторное произведение (cross product) | `a >< b` | Расширение FTEQCC |

**Побитовые** — работа с числом как с набором отдельных битов, удобно для хранения флагов:

```c
float mask = 0;
mask = mask | FL_ONGROUND;   // включить бит
mask = mask & ~FL_ONGROUND;  // выключить бит
```

| Оператор | Что делает | Пример | Статус |
|---|---|---|---|
| `&` | Побитовое И; в унарной форме — взятие адреса | `a & b`, `&x` | Расширение FTEQCC |
| `\|` | Побитовое ИЛИ | `a \| b` | Расширение FTEQCC |
| `^` | Побитовое исключающее ИЛИ | `a ^ b` | Расширение FTEQCC |
| `~` | Побитовое отрицание | `~x` | Расширение FTEQCC |
| `<<`, `>>` | Битовые сдвиги влево/вправо | `x << 3` | Расширение FTEQCC |

**Логические и сравнения** — были в языке с самого начала, кроме «спейсшип»-сравнения:

```c
if (health > 0 && !self.frozen)
{
	self.canmove = true;
}
```

| Оператор | Что делает | Пример | Статус |
|---|---|---|---|
| `!` | Логическое НЕ | `!x` | Оригинал |
| `&&` | Логическое И | `a && b` | Оригинал |
| `\|\|` | Логическое ИЛИ | `a \|\| b` | Оригинал |
| `==`, `!=` | Равно / не равно | `a != b` | Оригинал |
| `<`, `<=`, `>`, `>=` | Сравнение | `a <= b` | Оригинал |
| `<=>` | «Спейсшип»-сравнение (возвращает -1/0/1) | `a <=> b` | Расширение FTEQCC |

**Присваивание, инкремент/декремент, тернарный** — составные присваивания и инкременты избавляют от многословных записей вида `x = x + 1`:

```c
score += 10;
++lives;
float bonus = won ? 100 : 0;
```

| Оператор | Что делает | Пример | Статус |
|---|---|---|---|
| `=` | Присваивание | `a = b` | Оригинал |
| `+=`, `-=`, `*=`, `/=` | Составное арифметическое присваивание | `score += 10;` | Расширение FTEQCC |
| `&=`, `\|=`, `^=` | Составное побитовое присваивание | `mask \|= FLAG_X;` | Расширение FTEQCC |
| `&~=` | Сброс битов (`mask = mask & ~x`) | `mask &~= FLAG_X;` | Расширение FTEQCC |
| `<<=`, `>>=` | Составной битовый сдвиг | `x <<= 1;` | Расширение FTEQCC |
| `++`, `--` | Инкремент/декремент, префиксный и постфиксный | `++i;`, `i--;` | Расширение FTEQCC |
| `?:` | Тернарный (условный) оператор | `float bonus = won ? 100 : 0;` | Расширение FTEQCC |
| `?:` (короткая форма) | Без среднего операнда — возвращает левую часть, если она истинна | `x ?: fallback` | Расширение FTEQCC |

**Прочие** — доступ к полям/членам, вызов функций, индексация:

```c
v.x = 5;                 // покомпонентный доступ к вектору
entity e2 = arr[3];       // индексация массива
```

| Оператор | Что делает | Пример | Статус |
|---|---|---|---|
| `.` | Доступ к полю объекта; также `.length` (длина массива/строки) и покомпонентный доступ к вектору (`.x`/`.y`/`.z`, `.r`/`.g`/`.b`/`.a`) | `v.x`, `arr.length` | Оригинал (`.length`/компоненты — расширение) |
| `->` | Альтернативная запись доступа к полю через указатель | `ptr->x` | Расширение FTEQCC |
| `::` | Доступ к члену класса/перечисления по области видимости | `Type::member` | Расширение FTEQCC |
| `[]` | Индексация массива | `a[i]` | Расширение FTEQCC |
| `()` | Вызов функции; также приведение типа в C-стиле | `foo(x)`, `(int)x` | Оригинал (для вызова) |
| `,` | Оператор «запятая» — вычисляет оба выражения по порядку | `a = (x(), y())` | Расширение FTEQCC |
| `@` | Переинтерпретация значения как строки (только режим QCCX, флаг `qccx`) | `@x` | Расширение FTEQCC/QCCX |

## Управляющие конструкции

Ветвление `if`/`else` было в языке всегда:

```c
if (self.health <= 0)
{
	self.think = Die;
}
else
{
	self.think = Idle;
}
```

Циклы `while` и `do ... while` также присутствовали в оригинальном QuakeC. А вот классический **цикл `for`** и оператор множественного выбора **`switch`/`case`** — это уже расширения, добавленные FTEQCC (в самом первом QuakeC их эмулировали через `while` с ручными счётчиками, что было заметно неудобнее):

```c
// цикл for — расширение FTEQCC
for (float i = 0; i < 10; i++)
{
	dprint(ftos(i));
}

// switch/case — расширение FTEQCC
switch (self.weapon)
{
case 1:
	self.currentammo = self.ammo_shells;
	break;
case 2:
	self.currentammo = self.ammo_nails;
	break;
default:
	self.currentammo = 0;
}
```

Также доступны `break` (досрочный выход из цикла/switch) и `continue` (переход к следующей итерации цикла), а также редко используемый `goto` с именованными метками — для прямых, безусловных переходов внутри функции.

Кроме них FTEQCC понимает ещё несколько операторов потока управления — все они выключены по умолчанию или доступны только в определённых режимах совместимости, поэтому на практике встречаются редко: `not` (альтернатива `!` сразу после `if`), `until` (цикл/условие «пока не», обратное `while`), `loop` (бесконечный цикл без условия), `thinktime` (задаёт `.nextthink`/`.think` одной инструкцией, диалект HexenC), `state` (смена кадра и функции думанья за один шаг), `asm` (блок инлайн-ассемблера байт-кода), `using` (временный псевдоним имени в области видимости одной инструкции) и `exit` (немедленно завершает выполнение всей программы, диалект Reacc). Полная таблица с примерами и условиями доступности каждого — в разделе [«Редкие ключевые слова потока управления»](#редкие-ключевые-слова-потока-управления) справочника внизу страницы.

## Точка с запятой и блоки кода

Каждое отдельное выражение или объявление в QuakeC завершается точкой с запятой `;` — точно как в языке C. Блок из нескольких инструкций обрамляется фигурными скобками `{ }`. Пропущенная точка с запятой — самая частая причина ошибки компиляции у новичков.

## Кадровые макросы (`$frame`) — анимация «по-старому»

В классических (не скелетных) моделях Quake анимация задаётся не именем, а простым номером кадра модели, хранящимся в поле `.frame`. Чтобы не считать эти номера в уме, файлы моделей (`.mdl`) сопровождаются специальным заголовком с частично-декларативным синтаксисом, который вставляется прямо в исходный код QuakeC через специальный символ `$`:

```c
$frame walk1 walk2 walk3 walk4 walk5 walk6 walk7 walk8

void() walk1 =
{
	self.frame = $walk1;    // $walk1 превратится в порядковый номер кадра при компиляции
	self.nextthink = time + 0.1;
	self.think = walk2;
};
```

Директива `$frame` перечисляет имена кадров подряд, начиная с текущего счётчика (обычно 0), и каждому присваивает следующий номер по порядку. Затем в коде можно использовать `$name_frame` вместо того, чтобы помнить конкретное число — компилятор сам подставит нужное целое значение. Похожие директивы — `$modelname` (указывает, к какой модели относятся следующие `$frame`), `$cd`, `$origin`, `$base`, `$scale`, `$skin` (используются инструментами создания моделей, самим компилятором игнорируются), `$framevalue`/`$framerestore` (вручную задают текущий счётчик кадров), `$framesave`/`$flush` (сохраняют/сбрасывают текущий именованный набор кадров) и `$frame_reset` (сбрасывает счётчик кадров в 0). Этот механизм — наследие самого первого Quake и до сих пор широко используется в классических (не скелетных) монстрах и оружии.

## Расширенные возможности движка для QuakeC

Классический язык QuakeC изначально был довольно ограниченным — он умел работать только с числами, строками, векторами, объектами (`entity`) и функциями, и предоставлял лишь около восьмидесяти встроенных команд. Движок значительно расширяет возможности этого языка, добавляя ему множество дополнительных встроенных функций («билтинов»), привычных по современным языкам программирования и играм. Это часть программного интерфейса, которым пользуется автор мода при написании кода — все перечисленные ниже возможности доступны как обычные вызовы функций прямо в исходном коде QuakeC, если в проекте подключены соответствующие объявления (обычно они уже включены в стандартный заголовочный файл расширений, поставляемый вместе с компилятором — см. [«Стандартные заголовочные файлы»](./fteqcc-compiler.md#стандартные-заголовочные-файлы-для-quakec)).

### Битовые операции

**[`bitshift(number, count)`](../37-quakec-builtins-reference/01-math-vector-builtins.md#bitshift)** сдвигает биты числа: при положительном количестве — влево, при отрицательном — вправо. Позволяет компактно хранить наборы флагов в одном числовом поле вместо десятка отдельных полей:

```c
float flags = 0;
flags = bitshift(1, 3);   // 1 << 3 = 8
```

### Система «измерений» (раздельная видимость и столкновения)

Пара битовых масок `dimension_see`/`dimension_seen` на объектах определяет, кто кого видит: объект виден игроку, только если их маски совпадают (`player.dimension_see & other.dimension_seen`). Так можно сделать объекты, видимые только части игроков — например, отдельно для каждой команды:

```c
self.dimension_seen  = 2;   // объект принадлежит "измерению 2"
other.dimension_see  = 2;   // этот игрок видит объекты "измерения 2"
```

Похожая маска `dimension_send` применяется не к отдельным объектам, а к широковещательным сетевым сообщениям. Пара `dimension_ghost`/`dimension_ghost_alpha` — если у объекта установлен бит измерения, не входящий в `dimension_seen` наблюдателя, объект всё равно останется виден, но его прозрачность будет умножена на `dimension_ghost_alpha` (по умолчанию половина непрозрачности) — удобно для полупрозрачных «духов», видимых только части игроков. Наконец, `dimension_solid`/`dimension_hit` — раздельные маски для физических столкновений: объект А касается объекта Б, только если `A.dimension_hit & B.dimension_solid`, что позволяет одному объекту сталкиваться с миром, но проходить сквозь определённые другие объекты.

### Получение текущего времени суток

[`calltimeofday()`](../37-quakec-builtins-reference/11-server-browser-builtins.md#calltimeofday) — legacy-builtin, который немедленно вызывает в QC специальную функцию `timeofday(secs, mins, hour, day, mon, year, strvalue)` с текущим системным временем:

```c
void(float secs, float mins, float hour, float day, float mon, float year, string strvalue) timeofday =
{
	bprint(strvalue);   // строка вида "12:34:56"
};
```

Это старый совместимый механизм; для нового кода обычно удобнее пользоваться [`strftime`](../37-quakec-builtins-reference/02-string-builtins.md#strftime), но [`calltimeofday`](../37-quakec-builtins-reference/11-server-browser-builtins.md#calltimeofday) всё ещё встречается в старых модах.

### Скелетная анимация напрямую из кода

Группа функций позволяет программно управлять «скелетом» персонажа — костями и их поворотами — а не просто проигрывать готовые заранее анимации. Типичный сценарий — довернуть кости головы к цели поверх обычной анимации ходьбы:

```c
local float sk = skel_create(self.modelindex);
self.skeletonindex = sk;
skel_build(sk, self, self.modelindex, 1, 0, 0);   // подмешать текущую анимацию целиком

local float head = skel_find_bone(sk, "head");
skel_get_boneabs(sk, head);       // ориентация — в v_forward/v_right/v_up
// ...повернуть v_forward к цели и записать обратно...
skel_set_bone(sk, head, '0 0 0');
```

**[`skel_build(skeleton, entity, index_model, fraction_retain, first_bone, last_bone)`](../37-quakec-builtins-reference/10-skeletal-model-builtins.md#skel_build)** подмешивает анимацию модели `index_model` в существующий скелет с указанным весом сохранения (`fraction_retain`, 0 — полностью заменить, 1 — полностью сохранить прежнюю позу) в диапазоне костей от `first_bone` до `last_bone` (0 и -1 — все кости целиком).

### Работа с шейдерами Quake III прямо из кода

[`skinforname(index_model, "name_skin")`](../37-quakec-builtins-reference/07-precache-resources-builtins.md#skinforname) получает числовое значение скина по имени файла `.skin`; [`shaderforname("name_shader")`](../37-quakec-builtins-reference/07-precache-resources-builtins.md#shaderforname) аналогично возвращает индекс шейдера по его имени — оба билтина позволяют переключать скин/шейдер модели по имени файла прямо из кода, без привязки к порядковому номеру в файле модели.

### Проверка видимости и переполнения канала

[`checkpvs(view_point, entity)`](../37-quakec-builtins-reference/03-entity-world-builtins.md#checkpvs) проверяет, потенциально видна ли сущность из заданной точки взгляда по данным PVS (Potentially Visible Set) карты — быстрая приближённая проверка без трассировки лучей, обычно используемая для оптимизации AI/сетевой рассылки.

### Поиск игроков по имени

`matchclients("pattern", number_match)` ищет среди подключённых игроков тех, чьё имя соответствует шаблону (поддерживается `*` как маска); номер совпадения выбирает, какого по счёту из нескольких найденных вернуть (0 — первого). `matchclient("pattern")` — то же самое, но рассчитан ровно на одно совпадение и завершится ошибкой, если совпадений оказалось больше одного.

### Кооперативная многопоточность

Движок предоставляет псевдо-многопоточность прямо внутри игровой логики — код может «засыпать» и продолжать выполнение позже, без необходимости вручную хранить, на каком шаге он остановился. Это удобно, чтобы описать длинную сюжетную сценку одной линейной функцией вместо цепочки `think`-функций:

```c
void() Scripted_Sequence =
{
	bprint("The door starts opening...\n");
	sleep(2);
	bprint("Creak of hinges!\n");
	sleep(1);
	door.think = Door_Open;
};
```

[`sleep(seconds)`](../37-quakec-builtins-reference/06-files-database-builtins.md#sleep) приостанавливает выполнение текущего потока кода на заданное время (если движок в этот момент ожидал возвращаемое значение, оно временно станет нулевым/пустым). [`fork()`](../37-quakec-builtins-reference/06-files-database-builtins.md#fork) «расщепляет» выполнение на два продолжения — функция как бы возвращает управление дважды, с двумя разными результатами вызова — это основа для независимо «спящих» процессов внутри одной функции. [`abort(value)`](../37-quakec-builtins-reference/12-system-debug-builtins.md#abort) завершает текущий поток исполнения, возвращая управление движку.

Единственные переменные, которые остаются у каждого потока «свои» — это `self` и `other`; все остальные глобальные переменные общие для всех потоков и могут быть изменены другим потоком между переключениями. Поскольку объекты могут быть удалены, пока поток «спит», для проверки этого стоит использовать поле `uniquespawnid` — оно увеличивается на единицу при каждом создании нового объекта, гарантируя, что даже если два разных объекта используют одну и ту же ячейку памяти движка друг за другом, их можно отличить.

### Расширенная работа со строками

[`strstrofs(string, substring, start_position)`](../37-quakec-builtins-reference/02-string-builtins.md#strstrofs) ищет позицию вхождения подстроки начиная с указанного смещения и возвращает индекс найденного совпадения или -1, если подстрока не найдена.

### Готовые функции для классических визуальных эффектов

Набор готовых функций проигрывает знакомые по классическому Quake визуальные эффекты «временными объектами» без необходимости вручную формировать сетевое сообщение: [`te_gunshot`](../37-quakec-builtins-reference/08-csqc-rendering-builtins.md#te_gunshot), [`te_spike`](../37-quakec-builtins-reference/08-csqc-rendering-builtins.md#te_spike), [`te_superspike`](../37-quakec-builtins-reference/08-csqc-rendering-builtins.md#te_superspike), [`te_explosion`](../37-quakec-builtins-reference/08-csqc-rendering-builtins.md#te_explosion), [`te_tarexplosion`](../37-quakec-builtins-reference/08-csqc-rendering-builtins.md#te_tarexplosion), [`te_wizspike`](../37-quakec-builtins-reference/08-csqc-rendering-builtins.md#te_wizspike), [`te_knightspike`](../37-quakec-builtins-reference/08-csqc-rendering-builtins.md#te_knightspike), [`te_lavasplash`](../37-quakec-builtins-reference/08-csqc-rendering-builtins.md#te_lavasplash), [`te_teleport`](../37-quakec-builtins-reference/08-csqc-rendering-builtins.md#te_teleport), молния между двумя точками ([`te_lightning1`](../37-quakec-builtins-reference/08-csqc-rendering-builtins.md#te_lightning1)/[`te_lightning2`](../37-quakec-builtins-reference/03-entity-world-builtins.md#te_lightning2)/[`te_lightning3`](../37-quakec-builtins-reference/03-entity-world-builtins.md#te_lightning3)), [`te_lightningblood`](../37-quakec-builtins-reference/08-csqc-rendering-builtins.md#te_lightningblood) и [`te_bloodqw`](../37-quakec-builtins-reference/08-csqc-rendering-builtins.md#te_bloodqw) (с указанием количества частиц крови).

### Прочие расширения

Твёрдость `SOLID_LADDER` — legacy-вариант лестницы, ведущий себя как особый триггер; считается устаревшим и постепенно вытесняется способом через содержимое/`CONTENTS_LADDER`. Флаги трассировки `FL_FINDABLE_NONSOLID` (влияет на [`findradius`](../37-quakec-builtins-reference/03-entity-world-builtins.md#findradius), позволяя находить нетвёрдые объекты), `MOVE_TRIGGERS` (луч реагирует на триггеры) и `MOVE_EVERYTHING` (луч реагирует и на триггеры, и на нетвёрдые объекты). Разработчики также могут пользоваться значительно расширенным набором стандартных возможностей самого языка компилятора (необязательные параметры функций, более широкий набор системных функций для работы со строками и файлами — см. [«Чтение и запись файлов из игровой логики»](../18-data-access-from-scripts/file-read-write-from-scripts.md) и [«Встроенная база данных (SQLite/MySQL)»](../18-data-access-from-scripts/embedded-database-sql.md)).

## Модульные прогс-файлы и аддоны

Обычно вся игровая логика мода собирается в один большой файл. Но движок умеет **подгружать дополнительные независимые скрипты («аддоны») поверх уже загруженной основной логики**, не трогая и не пересобирая исходный код мода. Это открывает возможность распространять улучшения и дополнения к чужим модам как самостоятельные, отдельно устанавливаемые компоненты — например, добавить ботов-компаньонов в любую игру, даже если её автор этого не предусматривал, просто положив рядом ещё один скомпилированный файл.

### Как подключаются дополнительные скрипты

Дополнительные скрипты — это такие же скомпилированные файлы прогс-логики, как и основной (`progs.dat`), но подключаемые поверх него. Указать, какие именно аддоны загружать, можно тремя способами: через набор переменных **`addon0`**…**`addon15`**, каждая из которых явно называет файл дополнительного скрипта; через запись `extraprogs=`/`extraqwprogs=` в `mod.gam`, если мод хочет автоматически подтягивать набор модулей сам; либо сама игровая логика может подключить скрипт программно, во время своей инициализации, встроенной функцией **[`addprogs("filename")`](../37-quakec-builtins-reference/07-precache-resources-builtins.md#addprogs)**, которая возвращает номер подключённого скрипта.

### Две отдельные точки входа для инициализации аддона

У каждого подключаемого скрипта (в том числе у основного) может быть по две функции инициализации с разными возможностями:

```c
void(float prevprogs) init =
{
	// нельзя вызывать spawn() и трогать поля объектов
	// зато самое безопасное место для addprogs() и подмены функций других модулей
};

void() initents =
{
	// уже можно spawn(), но добавлять новые поля может быть поздно
};
```

**`init(prevprogs)`** вызывается ещё до того, как в мире можно создавать объекты: здесь **нельзя** пользоваться [`spawn()`](../37-quakec-builtins-reference/03-entity-world-builtins.md#spawn) или полями объектов, зато именно здесь безопаснее всего подключать другие аддоны через [`addprogs`](../37-quakec-builtins-reference/07-precache-resources-builtins.md#addprogs) и подменять функции уже загруженных модулей. **`initents()`** вызывается после финализации набора полей и непосредственно перед разбором объектов карты: здесь [`spawn()`](../37-quakec-builtins-reference/03-entity-world-builtins.md#spawn) уже работает, но добавлять новые поля через поздний [`addprogs`](../37-quakec-builtins-reference/07-precache-resources-builtins.md#addprogs) может оказаться слишком поздно.

### Общие и раздельные данные между скриптами

**Поля объектов (`.field`) — общие** для основной логики и всех аддонов: движок сам согласовывает и совмещает их набор при загрузке, поэтому добавлять новые аддоны с собственными полями уже после этого процесса (после `initents`) может не получиться. **Обычные глобальные переменные — НЕ общие**: у каждого подключённого прогс-файла своё пространство глобальных переменных. Чтобы объявить переменную «сквозной» (доступной во всех загруженных скриптах и синхронизируемой между ними), перед типом при объявлении ставится слово **`shared`**:

```c
shared float score;   // одинаковое объявление нужно повторить во всех скриптах
```

Важно объявлять такую переменную одинаково и в одном и том же месте во всех скриптах; задать ей начальное значение прямо в объявлении нельзя. Переменные `self`, `other`, `time` движок делает `shared` автоматически. Слово **`extern`** перед объявлением функции говорит компилятору, что тело будет предоставлено извне: в новом двоичном формате прогс-файлов (progs7) она подключается автоматически, в более старом — её нужно сначала объявить как обычную переменную (`var`) и явно связать через [`externvalue`](../37-quakec-builtins-reference/03-entity-world-builtins.md#externvalue) в одной из функций инициализации. Тип **`__variant`** («любой тип») отключает строгую проверку типов компилятором для такого значения — используется, чтобы [`externvalue`](../37-quakec-builtins-reference/03-entity-world-builtins.md#externvalue)/[`externset`](../37-quakec-builtins-reference/03-entity-world-builtins.md#externset) могли работать с данными произвольного типа.

### Обращение к данным другого скрипта

**[`addprogs("name")`](../37-quakec-builtins-reference/07-precache-resources-builtins.md#addprogs)** подключает ещё один прогс-файл (может завершиться неудачей, если это происходит слишком поздно и полей уже накопилось слишком много). **[`externvalue(number_script, "name")`](../37-quakec-builtins-reference/03-entity-world-builtins.md#externvalue)** читает значение переменной или функции из другого подключённого скрипта по имени; помимо обычных положительных номеров скриптов, параметр `number_script` поддерживает два специальных значения: **`0`** всегда означает основной прогс-файл, **`-1`** — «скрипт, из которого сейчас идёт вызов» (собственный), **`-2`** просит движок перебрать все подключённые скрипты и использовать первый, где найдётся переменная/функция с таким именем. **[`externset(number_script, value, "name")`](../37-quakec-builtins-reference/03-entity-world-builtins.md#externset)** записывает значение переменной или функции в другом скрипте по имени (для векторов надёжно работает только присвоение x-компоненты; для функций-констант запись надёжна, а для обычных числовых констант компилятор может «схлопнуть» одинаковые значения при сборке, что сделает подмену ненадёжной) и поддерживает те же значения `0`/`-1`/`-2`. **`thisprogs`** — номер текущего скрипта, который выставляет сам движок: у основной логики он всегда `0`, у каждого аддона — своё уникальное ненулевое значение.

### Пример: подмена (перехват) функции основного мода из аддона

Типичный сценарий использования — аддон незаметно «встраивается» в чужую логику, продолжая вызывать оригинальную функцию до или после своего кода:

```c
#pragma PROGS_DAT myaddon.dat
#include "defs.qc"

var void() real_myfunc;               // сюда будет записан адрес оригинальной функции

void() replacement_myfunc =
{
    dostuff_before();
    real_myfunc();                    // вызываем оригинальное поведение
    dostuff_after();
};

void() dohooks =
{
    real_myfunc = externvalue(0, "myfunc");           // запоминаем оригинал из основного мода (скрипт номер 0)
    externset(0, replacement_myfunc, "myfunc");       // подменяем его своей функцией
};
```

### Особенности и ограничения, которые стоит знать

Если несколько подключённых скриптов определяют функцию создания объекта для одного и того же [`classname`](../39-entity-keys-reference/01-worldspawn-common-keys.md#classname), объект создаст **первый** из них по порядку подключения (начиная с основного, номер 0). Аддоны, добавляющие ИИ монстрам, обычно должны также подменить функции атаки и уведомления о смерти (`CheckAttack`, `ClientObituary`), чтобы новое поведение полноценно работало. Нельзя смешивать скрипты, рассчитанные на разные, несовместимые семейства сетевого протокола (например, для классического Quake и для QuakeWorld). Оружие/инвентарь через аддоны дорабатывать сложнее, чем кажется: замена функции выстрела — это просто, а вот полноценное добавление нового оружия в инвентарь может потребовать более глубокой переработки логики, если мод не был изначально спроектирован с расчётом на расширение. Движок сам умеет подбирать некоторые аддоны автоматически в зависимости от формата загружаемой карты и всегда уведомляет о загрузке каждого аддона. Отдельный QuakeC-компилятор FrikQCC тоже поддерживает эту систему, но без удобных ключевых слов `shared`/`extern`/`__variant` — работать с ней придётся более многословно.

## Справочник синтаксиса

Ниже сведены **все** ключевые слова, литералы и элементы синтаксиса, которые распознаёт FTEQCC, включая уже упомянутые выше в примерах. Часть из них — редкие расширения для конкретных диалектов совместимости (Reacc, HexenC, C-стиль) и на практике почти не встречаются в обычных модах, но перечислены для полноты. Включение/выключение большинства из них регулируется флагами `-K`/`-F` или пресетом `-std=` — подробный список флагов в статье [«Компилятор FTEQCC»](./fteqcc-compiler.md#флаги-компилятора-и-ключевые-слова--f---k).

### Редкие ключевые слова потока управления

| Ключевое слово | Что делает | Пример | Когда доступно |
|---|---|---|---|

| Ключевое слово | Что делает | Пример | Статус |

| Переменное число аргументов | `...` в конце списка параметров | `void log(string fmt, ...);` |

## Примеры

- Мод использует битовые флаги ([`bitshift`](../37-quakec-builtins-reference/01-math-vector-builtins.md#bitshift)), чтобы компактно хранить в одном числовом поле сразу десяток независимых булевых состояний персонажа, вместо создания десяти отдельных полей.
- Скелетная анимация используется для того, чтобы голова NPC плавно поворачивалась вслед за игроком поверх обычной проигрываемой анимации ходьбы.
- Система измерений используется, чтобы игроки одной команды не видели заранее расставленные ловушки другой команды на одной и той же карте.
- Кооперативная многопоточность используется, чтобы описать длинную сюжетную сценку одной линейной функцией вместо цепочки `think`-функций.
- К классическому одиночному моду подключается готовый аддон с ботами-компаньонами, управляемыми простым ИИ, без внесения изменений в исходный код самого мода.
- Аддон перехватывает функцию нанесения урона основного мода, добавляя перед ней проверку на «дружественный огонь», не трогая исходный код самого мода.
