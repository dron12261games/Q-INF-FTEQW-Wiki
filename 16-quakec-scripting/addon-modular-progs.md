# Множественные аддон-скрипты и модульные прогс-файлы

> [⬅ Вернуться к оглавлению вики](../README.md)

> Раздел: [Игровая логика: язык QuakeC](./README.md)

## Что это даёт геймдизайнеру

Обычно вся игровая логика мода собирается в один большой файл. Но движок умеет **подгружать дополнительные независимые скрипты («аддоны») поверх уже загруженной основной логики**, не трогая и не пересобирая исходный код мода. Это открывает возможность распространять улучшения и дополнения к чужим модам как самостоятельные, отдельно устанавливаемые компоненты — например, добавить ботов-компаньонов в любую игру, даже если её автор этого не предусматривал, просто положив рядом ещё один скомпилированный файл.

## Интерфейс настройки

Дополнительные скрипты — это такие же скомпилированные файлы прогс-логики, как и основной (`progs.dat`), но подключаемые поверх него. Указать, какие именно аддоны загружать, можно двумя способами:

- через набор переменных **`addon0`**…**`addon15`** — каждая явно называет файл дополнительного скрипта, который нужно загрузить (эквивалентно тому, как если бы основная логика сама вызвала подключение этого аддона в момент своей инициализации);
- сама игровая логика может подключить дополнительный скрипт программно, во время своей собственной инициализации, встроенной функцией **`addprogs("имя_файла")`**, которая возвращает номер подключённого дополнительного скрипта (или неудачу, если полей данных уже стало слишком много для объединения).

### Две отдельные точки входа для инициализации аддона

У каждого подключаемого скрипта (в том числе у основного) может быть по две функции инициализации с разными возможностями:

- **`init()`** — вызывается ещё до того, как в мире можно создавать объекты: здесь **нельзя** пользоваться `spawn()` или полями объектов, зато можно подключать другие аддоны через `addprogs`. Эта функция предназначена для «перехвата» (подмены) важных функций основной логики (см. пример ниже).
- **`initents()`** — вызывается непосредственно перед созданием стартового объекта карты (`worldspawn`), уже после того, как создание объектов разрешено: здесь `spawn()` работает, но `addprogs` может уже не сработать, если новые поля данных добавлять поздно.

### Общие и раздельные данные между скриптами

- **Поля объектов (`.поле`) — общие** для основной логики и всех аддонов: движок сам согласовывает и совмещает их набор при загрузке. Из-за этого добавлять новые аддоны, вводящие собственные поля, уже после того, как этот процесс завершился (после `initents`), может не получиться — слишком поздно.
- **Обычные глобальные переменные — НЕ общие** между разными скриптами: у каждого подключённого прогс-файла своё пространство глобальных переменных. Чтобы явно объявить переменную «сквозной» (доступной во всех загруженных скриптах и синхронизируемой между ними), перед её типом при объявлении ставится специальное слово **`shared`** — важно объявлять такую переменную одинаково и в одном и том же месте во всех скриптах (обычно — в общем заголовочном файле, до каких-либо расхождений), иначе она попадёт на разные внутренние позиции и рассинхронизируется. Переменные `self`, `other`, `time` движок делает `shared` автоматически.
- **Слово `extern`** перед объявлением функции говорит компилятору, что тело функции будет предоставлено извне: в новом двоичном формате прогс-файлов (progs7) она подключается автоматически, в более старом — её нужно сначала объявить как обычную переменную (`var`) и явно связать через `externvalue` в одной из функций инициализации.
- **Тип `__variant`** — «любой тип», отключает проверки типов компилятором для такой переменной; используется, чтобы `externvalue`/`externset` могли работать с значением произвольного типа (с оговоркой, что с векторами могут быть нюансы).

### Обращение к данным другого скрипта

- **`addprogs("имя")`** — подключает ещё один прогс-файл (может завершиться неудачей, если это происходит слишком поздно и полей уже накопилось слишком много).
- **`externvalue(номер_скрипта, "имя")`** — читает значение переменной или функции из другого подключённого скрипта по её имени (работает и для переменных текущего скрипта — то есть эту же пару функций можно использовать, чтобы реализовать в собственном моде подобие массивов или мини-скриптовой системы, хотя для этого эффективнее пользоваться встроенными массивами компилятора). Помимо обычных положительных номеров скриптов, параметр `номер_скрипта` поддерживает два специальных значения: **`0`** всегда означает основной/главный прогс-файл, **`-1`** означает «скрипт, из которого сейчас идёт вызов» (то есть свой собственный), а **`-2`** просит движок самостоятельно перебрать все подключённые скрипты и использовать первый, где найдётся переменная/функция с таким именем.
- **`externset(номер_скрипта, значение, "имя")`** — записывает значение переменной или функции в другом скрипте по имени (для целых векторов надёжно работает только присвоение x-компоненты; для функций-констант такая запись работает надёжно, а вот для обычных числовых констант компилятор может «схлопнуть» одинаковые значения при сборке, что сделает такую подмену ненадёжной). Поддерживает те же специальные значения `0`/`-1`/`-2` для параметра `номер_скрипта`, что и `externvalue`.
- **`thisprogs`** — номер текущего скрипта, который выставляет сам движок: у основной логики он всегда `0`, у каждого аддона — своё уникальное ненулевое значение.

### Пример: подмена (перехват) функции основного мода из аддона

Типичный сценарий использования — аддон незаметно «встраивается» в чужую логику, продолжая вызывать оригинальную функцию до или после своего кода:

```
#pragma PROGS_DAT myaddon.dat
#include "defs.qc"

var void() real_myfunc;               // сюда будет записан адрес оригинальной функции

void() replacement_myfunc =
{
    dostuff_before();
    real_myfunc();                    // вызываем оригинальное поведение
    dostuff_after();
};

void() dohooks =
{
    real_myfunc = externvalue(0, "myfunc");           // запоминаем оригинал из основного мода (скрипт номер 0)
    externset(0, replacement_myfunc, "myfunc");       // подменяем его своей функцией
};
```

### Особенности и ограничения, которые стоит знать

- Если несколько подключённых скриптов определяют функцию создания объекта для одного и того же `classname`, объект создаст **первый** из них по порядку подключения (начиная с основного, номер 0).
- Аддоны, добавляющие ИИ монстрам, обычно должны также подменить функции атаки и уведомления о смерти (`CheckAttack`, `ClientObituary`), чтобы новое поведение полноценно работало.
- Нельзя смешивать скрипты, рассчитанные на разные, несовместимые семейства сетевого протокола (например, для классического Quake и для QuakeWorld).
- Оружие/инвентарь через аддоны дорабатывать сложнее, чем кажется: замена функции выстрела — это просто, а вот полноценное добавление нового оружия в инвентарь может потребовать более глубокой переработки логики, если мод не был изначально спроектирован с расчётом на расширение.
- Движок сам умеет подбирать некоторые аддоны автоматически в зависимости от формата загружаемой карты, и всегда уведомляет о загрузке каждого аддона (по запросу переменных `addon0`…`addon15` или по прямому запросу пользователя).
- Отдельный QuakeC-компилятор FrikQCC тоже поддерживает эту систему, но без удобных ключевых слов `shared`/`extern`/`__variant` — работать с ней придётся более многословно.

## Примеры

- К любому классическому одиночному моду подключается готовый аддон с ботами-компаньонами, управляемыми простым ИИ, — без внесения изменений в исходный код самого мода.
- Сообщество выпускает необязательное дополнение к популярному командному моду (например, статистику матчей или дополнительные звуковые оповещения), устанавливаемое как отдельный аддон-файл, который игрок либо подключает, либо нет.
- Аддон перехватывает функцию нанесения урона основного мода, добавляя перед ней проверку на «дружественный огонь», не трогая исходный код самого мода.
