# Альтернативный байт-код игровой логики (Q1QVM)

> [⬅ Вернуться к оглавлению вики](../README.md)

> Раздел: [Альтернативные языки и виртуальные машины игровой логики](./README.md)

## Что это даёт геймдизайнеру

Помимо классического формата скомпилированной игровой логики Quake, движок понимает и альтернативный, более современный формат исполняемого байт-кода — так называемый **QVM** (виртуальная машина, изначально пришедшая из технологий id Software для игр наподобие Quake III Arena). Такой формат даёт более строгую изоляцию исполняемого кода мода от самого движка (байт-код исполняется в собственной песочнице со своей отдельной областью памяти, а не как обычный машинный код), что удобно для площадок, которым важна дополнительная надёжность и предсказуемость выполнения стороннего игрового кода — например, публичные серверы, принимающие моды от множества независимых авторов, которым автор сервера не обязан доверять полностью.

## Интерфейс настройки

Для конечного игрока работа с этим форматом выглядит так же, как с обычной игровой логикой: если игровая логика мода скомпилирована именно в этом альтернативном формате байт-кода, движок автоматически распознаёт и загружает такой файл вместо привычного скомпилированного файла QuakeC — никаких дополнительных настроек в файлах мода для этого не требуется, файл просто кладётся в игровую директорию мода под тем же самым служебным именем, под которым движок обычно ищет скомпилированную логику. Разница касается в первую очередь инструментов, которыми пользуется автор мода при подготовке (компиляции) логики, а не самого способа её использования конечным игроком.

### Настройка загрузки

| Переменная | Тип / формат | Описание | Значение по умолчанию |
| :--- | :--- | :--- | :--- |
| `sv_progs` | Строка, базовое имя файла (без расширения) | Явно задаёт, какой файл игровой логики использовать на сервере. Если оставить пустым, движок сам определяет — обычно между `progs` и `qwprogs`, в зависимости от приоритета игровой папки и настроек deathmatch | пусто (автоопределение; при полном автоопределении, если ничего не найдено, используется базовое имя `qwprogs`) |
| `com_gamedirnativecode` | `0`/`1` | Разрешает ли движок вообще загружать логику в виде «родного» скомпилированного машинного кода (динамической библиотеки, `.dll`/`.so`) вместо песочницы байт-кода QVM. Так как родной код полностью выходит за пределы песочницы, по умолчанию это запрещено ради безопасности — включать стоит только для доверенных модов (например, Quake II, Quake III или KTX, которые исторически поставляются именно как родной код) | `0` (запрещено) |

### Как это устроено «под капотом» — без лишних технических деталей

Байт-код QVM выполняется не напрямую процессором компьютера, а прослойкой-интерпретатором внутри самого движка. У такого исполняемого кода есть собственный, изолированный от остального движка блок памяти, а обращение к «настоящим» возможностям движка (создание объектов, проигрывание звуков, чтение состояния игроков и так далее) происходит через строго определённый список вызовов — то есть мод физически не может напрямую вмешаться в работу движка за пределами этого списка. Это и обеспечивает ту самую дополнительную надёжность: даже написанная с ошибками или недобросовестно логика мода не может «уронить» или испортить память самого движка на сервере.

Важно не путать **Q1QVM** из этой статьи с произвольными `qagame.qvm`/`cgame.qvm`/`ui.qvm` из мира Quake III: в FTEQW это именно Quake‑1-ориентированный API gamecode, который исторически чаще всплывает у старых серверных модов вроде KTX. Движок понимает диапазон версий API 8–16; у очень старых вариантов лимит сущностей может быть жёстко ограничен, тогда как более новые сами сообщают свой допустимый максимум.

Помимо байт-кода QVM движок также умеет (при поддержке платформой и включённой переменной `com_gamedirnativecode`) загружать логику в виде родного скомпилированного машинного кода для данной операционной системы, без песочницы — это быстрее, но лишает сервер той самой дополнительной защиты, поэтому такой вариант обычно используется только доверенными или локально запускаемыми модами, а не публичными серверами со сторонним контентом. Именно поэтому переменная `com_gamedirnativecode` по умолчанию выключена: движок намеренно блокирует автозагрузку скачанных файлов с расширениями `.dll`/`.so`, чтобы недобросовестный автор мода не мог таким образом организовать удалённое выполнение произвольного кода на компьютере игрока.

## Примеры

- Автор мода, ранее работавший с движками линейки Quake III, компилирует уже существующую логику в знакомый ему формат байт-кода и подключает получившийся файл к игре так же, как подключался бы обычный скомпилированный файл QuakeC — задав его имя через `sv_progs`, если оно отличается от стандартного.
- Администратор строгого публичного сервера предпочитает моды, поставляемые именно в этом альтернативном формате байт-кода, ради дополнительной уверенности в безопасности исполнения стороннего кода — намеренно оставляя `com_gamedirnativecode 0`, даже если автор мода допустил ошибку в логике, она не затронет стабильность самого сервера.
- Разработчик, портирующий классический Quake II на движок, включает `com_gamedirnativecode 1` на своём локальном тестовом сервере, чтобы запустить историческую родную скомпилированную логику этой игры без песочницы, полностью отдавая себе отчёт в том, что делает это только с доверенным, собственноручно собранным кодом.
