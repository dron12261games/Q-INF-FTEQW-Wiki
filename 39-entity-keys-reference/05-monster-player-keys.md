# Монстры, NPC и точки появления игрока

> [⬅ Вернуться к оглавлению вики](../README.md)

> [Индекс справочника ключей сущностей](./README.md)

Монстры Quake в basemod — это обычные point-entity, чьё поведение задаётся сочетанием `classname`, стартовых полей сущности и общей AI-логики из `monsters.qc` и `ai.qc`. На практике карта чаще всего настраивает у них позицию, направление, здоровье, `spawnflags` и сценарные связи через `target`/`targetname`; всё остальное обычно назначается самими spawn-функциями конкретного класса. Точки появления игрока устроены ещё проще: `client.qc` выбирает подходящий `info_player_*`, после чего копирует из него координаты и углы в только что созданного игрока. Ниже собраны как реально читаемые ключи, так и несколько важных полей, которые в этом basemod для данных классов остаются неиспользованными, чтобы было проще отличать рабочие настройки от «шума» в `.map` или `.ent`.

- `monster_enforcer` — Enforcer; исходник: `quakec\basemod\enforcer.qc`.
- `monster_fish` — Rotfish; исходник: `quakec\basemod\fish.qc`.
- `monster_hell_knight` — Hell Knight; исходник: `quakec\basemod\hknight.qc`.
- `monster_knight` — Knight; исходник: `quakec\basemod\knight.qc`.
- `monster_ogre` — Ogre; исходник: `quakec\basemod\ogre.qc`.
- `monster_ogre_marksman` — алиас, вызывающий обычный `monster_ogre`; исходник: `quakec\basemod\ogre.qc`.
- `monster_oldone` — Shub-Niggurath / финальный Old One; исходник: `quakec\basemod\oldone.qc`.

## Ключи монстров

### classname
`тип значения: string`

* Применимо к: всем `monster_*` классам из списка выше.

#### Описание и логика работы
`classname` выбирает конкретную spawn-функцию монстра: `monster_army`, `monster_ogre`, `monster_wizard` и так далее. Именно по этому имени карта решает, какие модель, размеры, базовое здоровье, набор атак и тип старта будут назначены сущности. Если `classname` ошибочен, обычный монстр не появится как ожидаемый боевой NPC. Для `monster_ogre_marksman` важно помнить, что это не отдельный вид врага, а просто алиас, вызывающий обычный спаун огра.

#### Практические сценарии использования
```
{
"classname" "monster_army"
}
```
Такой блок создаёт обычного солдата Quake; все остальные боевые параметры подставит его spawn-функция.

### origin
`тип значения: vector`

* Применимо к: всем `monster_*` классам.

#### Описание и логика работы
`origin` задаёт стартовую позицию монстра на карте. Для ходячих врагов `walkmonster_start_go()` слегка приподнимает их и затем опускает на пол через `droptofloor()`, поэтому точку можно ставить немного выше поверхности, не боясь мелкой рассинхронизации. Для летающих (`monster_wizard`) и плавающих (`monster_fish`) монстров положение в пространстве важнее: оно используется почти как есть. Если координаты выбраны плохо, монстр может застрять в геометрии или стартовать в неудачной боевой зоне.

#### Практические сценарии использования
```
{
"classname" "monster_shambler"
"origin" "512 256 64"
}
```
Шамблер появится в заданных координатах; для ходячего класса движок затем аккуратно прижмёт его к полу.

### angle
`тип значения: float`

* Применимо к: всем `monster_*` классам.

#### Описание и логика работы
Классический одиночный `angle` задаёт стартовый yaw монстра. В общей логике старта это направление копируется в `self.angles`, а затем используется для начального `ideal_yaw`, то есть именно так монстр будет смотреть в момент спауна и с этого направления начнёт поворот к цели. Для засадных монстров угол особенно важен: если игрок подойдёт сзади, поле зрения сработает иначе, чем при взгляде прямо на коридор. Если ключ не задан, стартовое направление обычно остаётся нулевым (`0`).

#### Практические сценарии использования
```
{
"classname" "monster_enforcer"
"angle" "180"
}
```
Enforcer стартует лицом в сторону yaw `180`, например навстречу длинному коридору.

### angles
`тип значения: vector`

* Применимо к: всем `monster_*` классам.

#### Описание и логика работы
`angles` хранит полный вектор ориентации, но для обычной monster-AI в basemod практически значима только yaw-компонента. Общий стартовый код вычисляет `ideal_yaw` из текущих углов, а дальнейшее поведение поворота идёт уже через `self.angles_y` и `self.yaw_speed`. Для ходячих монстров pitch и roll обычно не играют роли в логике преследования, но сам ключ может быть полезен в `.ent`-файлах или при нестандартном редактировании карт, если нужно явно сохранить полный набор углов.

#### Практические сценарии использования
```
{
"classname" "monster_wizard"
"angles" "0 270 0"
}
```
Wizard стартует с yaw `270`; на практике для AI это почти эквивалентно `angle "270"`.

### health
`тип значения: float`

* Применимо к: всем `monster_*` классам.

#### Описание и логика работы
Каждая spawn-функция монстра записывает собственное базовое здоровье: например, солдат получает `30`, Ogre `200`, Demon `300`, Zombie `60`. Поэтому для id1-style карт `health` — рабочий override: если карта задаёт значение, а spawn-функция затем его не переписывает, кастомное здоровье сохранится; но в basemod почти все стандартные монстры явно присваивают своё `self.health`, так что ключ из карты фактически перекрывается кодом класса. Исключение возможны только в пользовательских модификациях QuakeC поверх этой базы. Для документации и диагностики важно помнить именно это: у стандартных `monster_*` начальный HP определяется кодом вида, а не mapper-friendly общим правилом.

#### Практические сценарии использования
```
{
"classname" "monster_army"
"health" "120"
}
```
В чистом basemod такое значение обычно будет перезаписано стандартными `30 HP`, поэтому это не надёжный способ усилить солдата без правки QuakeC.

### spawnflags
`тип значения: integer`

* Применимо к: всем `monster_*` классам; у `monster_zombie` есть дополнительная особая интерпретация битов.

#### Описание и логика работы
`spawnflags` — главное картографическое поле для особых режимов старта монстра. Самый важный бит — `AMBUSH`: такой монстр не просыпается от звуковой эстафеты соседних врагов и реагирует только на прямую видимость цели; в `ai.qc` это выражено проверкой, которая запрещает раннее «заражение агрессией» от уже встревоженного монстра. В классических `/*QUAKED*/` описаниях у большинства монстров `Ambush` сидит в первом бите (`1`). У `monster_zombie` есть историческое отличие: бит `1` занят флагом `Crucified`, а ambush для совместимости фактически проходит через маску `spawnflags & 3`, то есть засадный зомби обычно получает бит `2`, а распятый засадный — комбинацию `3`.

#### Практические сценарии использования
```
{
"classname" "monster_zombie"
"spawnflags" "3"
}
```
Зомби стартует распятым и одновременно в режиме ambush: не будет реагировать на шум и останется прибитым к стене, пока не увидит цель напрямую.

### target
`тип значения: string`

* Применимо к: всем стандартным walking/flying/swimming монстрам; практически особенно важно для `monster_army`, `monster_dog`, `monster_demon1`, `monster_enforcer`, `monster_fish`, `monster_hell_knight`, `monster_knight`, `monster_ogre`, `monster_shalrath`, `monster_shambler`, `monster_tarbaby`, `monster_wizard`, `monster_zombie`.

#### Описание и логика работы
Если у монстра задан `target`, общая стартовая логика ищет сущность с совпадающим `targetname` и сохраняет её как `movetarget`/`goalentity`. Если найден именно `path_corner`, монстр сразу начинает патруль по маршруту; если цель другая или не найдена, он остаётся стоять, а в консоль может уйти диагностическое сообщение. После потери или смерти врага монстр старается вернуться к своему маршруту, поэтому `target` — основной способ сделать не просто «охранника на месте», а движущийся патруль. Для `monster_boss` это правило не универсально: он использует отдельную логику и не проходит стандартный `walkmonster_start()`.

#### Практические сценарии использования
```
{
"classname" "monster_ogre"
"target" "patrol_ogre_1"
}
```
Ogre попытается найти `path_corner` с `targetname "patrol_ogre_1"` и начнёт маршрутный патруль.

### targetname
`тип значения: string`

* Применимо к: всем `monster_*` классам.

#### Описание и логика работы
`targetname` делает монстра адресуемой сущностью для остальной логики карты. В чистом basemod это полезно прежде всего для сценарных связей, выборки по имени и совместимости с внешними `.ent`-правками: монстра можно находить по имени так же, как любой другой point-entity. При этом стандартное поведение монстра не зависит от наличия `targetname` само по себе — без внешней логики он будет вести себя как обычный NPC. Проще говоря, `targetname` не меняет AI, а даёт карте возможность сослаться именно на этого монстра.

#### Практические сценарии использования
```
{
"classname" "monster_shalrath"
"targetname" "rear_guard"
}
```
Теперь карту можно строить так, чтобы другие сущности ссылались именно на эту Shalrath по имени `rear_guard`.

### yaw_speed
`тип значения: float`

* Применимо к: всем `monster_*` классам, использующим стандартный monster-start.

#### Описание и логика работы
`yaw_speed` задаёт скорость разворота монстра. В `walkmonster_start_go()`, `flymonster_start_go()` и `swimmonster_start_go()` это поле получает значение по умолчанию только если карта не поставила его заранее: `20` для ходячих и `10` для летающих/плавающих классов. Значит, это один из немногих действительно рабочих тонких тюнинговых ключей, который можно задать прямо картой без изменения QuakeC. Чем выше число, тем резче монстр доворачивает корпус к цели и маршруту.

#### Практические сценарии использования
```
{
"classname" "monster_knight"
"yaw_speed" "40"
}
```
Knight будет разворачиваться заметно быстрее стандартного, что делает его агрессивнее в тесных коридорах.

### items
`тип значения: integer`

* Применимо к: всем `monster_*` классам, но в рамках данного basemod как стартовый ключ фактически не используется.

#### Описание и логика работы
Поле `items` существует в общих entvars, поэтому его технически можно записать в сущность карты. Однако в исследованных monster-spawn функциях `quakec\basemod` стартовый инвентарь монстра через `self.items` не настраивается: выпадение боеприпасов задаётся непосредственно кодом класса через `ammo_shells_real`, `ammo_rockets_real` и `ammo_cells_real`, а не mapper-friendly флагами `items`. Поэтому для стандартных монстров этот ключ следует считать шумом или заделом под другой мод. Наличие `items` в `.ent` не превращает врага в носителя оружейного/ключевого инвентаря id1-правилами.

#### Практические сценарии использования
```
{
"classname" "monster_army"
"items" "32"
}
```
В обычном basemod солдат не начнёт иначе себя вести и не станет корректно «вооружённым предметом» только из-за этого поля.

### model
`тип значения: string`

* Применимо к: всем `monster_*` классам, но в стандартном basemod обычно перезаписывается spawn-функцией.

#### Описание и логика работы
Хотя `model` является обычным полем сущности, стандартные spawn-функции монстров почти всегда сами вызывают `setmodel()` и жёстко назначают нужный `.mdl`. Из-за этого попытка задать свой `model` прямо из карты для обычного монстра обычно бесполезна: код класса всё равно поставит штатную модель врага. Такой ключ имеет смысл только как сигнал, что карта рассчитана на другой QuakeC-мод, где spawn-функции уважают пользовательскую модель, либо как временная заметка в `.ent`-файле.

#### Практические сценарии использования
```
{
"classname" "monster_dog"
"model" "progs/customdog.mdl"
}
```
В чистом basemod это значение обычно будет перезаписано стандартным `progs/dog.mdl` во время спауна.

## Точки появления игрока

В `quakec\basemod\client.qc` прямо определены четыре id1-класса стартовых точек: `info_player_start`, `info_player_start2`, `info_player_deathmatch` и `info_player_coop`. Логика выбора проста: в coop первый игрок берёт `info_player_start`, остальные — цепочку `info_player_coop`; в обычной одиночной игре используется `info_player_start`, а на start-map при возвращении с руной — `info_player_start2`; в deathmatch выбирается случайный `info_player_deathmatch` с попыткой избегать занятых мест в радиусе 84 единиц. Классы `info_player_team1` и `info_player_team2` в basemod SSQC не объявлены, но в репозитории они используются как FTEQW-совместимое расширение на уровне карт и `.ent`-файлов, поэтому ниже они документируются только по общим позиционным ключам точки спауна.

- `info_player_start` — основная точка старта одиночной игры; исходник: `quakec\basemod\client.qc`.
- `info_player_start2` — стартовая точка возврата на start-map после эпизода; исходник: `quakec\basemod\client.qc`.
- `info_player_coop` — дополнительные точки спауна в coop; исходник: `quakec\basemod\client.qc`.
- `info_player_deathmatch` — случайные точки старта deathmatch; исходник: `quakec\basemod\client.qc`.
- `info_player_team1` — карта/`.ent`-конвенция FTEQW для первой команды; прямой spawn-функции в `quakec\basemod` не найдено.
- `info_player_team2` — карта/`.ent`-конвенция FTEQW для второй команды; прямой spawn-функции в `quakec\basemod` не найдено.

### classname
`тип значения: string`

* Применимо к: `info_player_start`, `info_player_start2`, `info_player_coop`, `info_player_deathmatch`, `info_player_team1`, `info_player_team2`.

#### Описание и логика работы
`classname` определяет, в какой пул попадёт точка спауна. Именно по этому имени `SelectSpawnPoint()` ищет первую одиночную точку, кооперативные старты и набор deathmatch-позиций. Для teamplay-конвенций `info_player_team1` и `info_player_team2` ключ столь же важен, потому что без точного имени внешняя логика карты или другой мод не смогут отличить одну командную точку от другой. Ошибка в `classname` чаще всего означает, что стартовая точка будет полностью проигнорирована.

#### Практические сценарии использования
```
{
"classname" "info_player_deathmatch"
}
```
Блок становится кандидатом для случайного старта в deathmatch.

### origin
`тип значения: vector`

* Применимо к: `info_player_start`, `info_player_start2`, `info_player_coop`, `info_player_deathmatch`, `info_player_team1`, `info_player_team2`.

#### Описание и логика работы
`origin` задаёт мировые координаты точки появления игрока. При реальном спауне `PutClientInServer()` переносит игрока в `spot.origin + '0 0 1'`, то есть на одну единицу выше самой точки, чтобы избежать залипания в полу. В deathmatch качество расстановки особенно важно, потому что код дополнительно пытается выбрать точку, рядом с которой нет других игроков в радиусе 84 единиц. Для `info_player_team1`/`team2` смысл тот же: это физическое место рождения игроков команды.

#### Практические сценарии использования
```
{
"classname" "info_player_start"
"origin" "128 64 80"
}
```
Игрок появится в этой зоне карты; фактическая позиция будет взята чуть выше исходной точки.

### angle
`тип значения: float`

* Применимо к: `info_player_start`, `info_player_start2`, `info_player_coop`, `info_player_deathmatch`, `info_player_team1`, `info_player_team2`.

#### Описание и логика работы
Для точек старта `angle` — практически обязательный ключ: он задаёт yaw, который затем попадает в `spot.angles`, а оттуда копируется в `self.angles` игрока. Если угол не указан, игрок появится с направлением по умолчанию, что часто неудобно и визуально ломает задуманный старт сцены. Особенно это заметно в одиночной игре, где автор уровня обычно точно рассчитывает, куда будет смотреть игрок в первый кадр. Для командных спаунов правило то же самое.

#### Практические сценарии использования
```
{
"classname" "info_player_team2"
"angle" "270"
}
```
Игрок второй команды появится лицом к yaw `270`, то есть сразу будет ориентирован в нужную сторону базы.

### angles
`тип значения: vector`

* Применимо к: `info_player_start`, `info_player_start2`, `info_player_coop`, `info_player_deathmatch`, `info_player_team1`, `info_player_team2`.

#### Описание и логика работы
`PutClientInServer()` копирует в игрока именно `spot.angles`, поэтому полный вектор углов у точки старта технически тоже является рабочим источником ориентации. На классических Quake-картах обычно используют только `angle`, но при ручном редактировании `.ent` можно сохранить и полный `angles`, если это поддерживает конкретный пайплайн редактора/компилятора. На практике pitch и roll для обычного старта почти не нужны, зато yaw-компонента работает так же, как и в одиночном `angle`. Если заданы оба ключа, итог зависит от того, какой формат реально сохранил парсер карты в entvars.

#### Практические сценарии использования
```
{
"classname" "info_player_coop"
"angles" "0 90 0"
}
```
Кооперативная точка направит игрока на yaw `90`; это альтернативная запись к обычному `angle`.

### target
`тип значения: string`

* Применимо к: `info_player_start`, `info_player_start2`, `info_player_coop`, `info_player_deathmatch`, `info_player_team1`, `info_player_team2`.

#### Описание и логика работы
В исследованном `quakec\basemod\client.qc` стартовые точки игрока не используют `target` при выборе места спауна: код опирается только на `classname`, позицию и углы. Поэтому для id1-style basemod `target` на `info_player_*` следует считать опциональным служебным ключом совместимости — он может быть полезен для внешней логики карты, ручного редактирования `.ent` или другого мода, но сам по себе не меняет стандартный выбор точки старта. Иначе говоря, наличие `target` у старта не делает его телепортом и не строит маршрут. Это просто дополнительная строка, которую текущий basemod игнорирует.

#### Практические сценарии использования
```
{
"classname" "info_player_start2"
"target" "episode_return_marker"
}
```
В чистом basemod эта строка не влияет на спаун, но может служить меткой для внешних правок карты или другого QuakeC-кода.

### targetname
`тип значения: string`

* Применимо к: `info_player_start`, `info_player_start2`, `info_player_coop`, `info_player_deathmatch`, `info_player_team1`, `info_player_team2`.

#### Описание и логика работы
`targetname` тоже не участвует в стандартной логике выбора игроком точки старта в `client.qc`. Тем не менее это нормальный entity-key, который иногда полезен как именованная метка в `.ent`-файле, особенно если карта адаптируется под другой мод или дополнительную серверную логику. Для обычного id1-подобного basemod наличие либо отсутствие `targetname` на `info_player_*` никак не меняет очередность, случайность или валидность выбора спауна. Это вспомогательное поле совместимости, а не обязательная настройка старта.

#### Практические сценарии использования
```
{
"classname" "info_player_deathmatch"
"targetname" "dm_upper_ring"
}
```
В стандартном basemod deathmatch-точка будет работать как обычно; имя `dm_upper_ring` пригодится только внешней логике или ручной навигации по `.ent`.

### spawnflags
`тип значения: integer`

* Применимо к: `info_player_start`, `info_player_start2`, `info_player_coop`, `info_player_deathmatch`, `info_player_team1`, `info_player_team2`.

#### Описание и логика работы
Для описанных в `client.qc` стартовых точек игрока `spawnflags` специальной логики не имеет. Код выбора точки не проверяет биты и не строит на них фильтрацию режима или команды. Поэтому в рамках basemod это поле безопасно считать неиспользуемым: если редактор карты или сторонний `.fgd` подсказывает какие-то флаги для `info_player_*`, нужно проверять уже другой мод, а не этот id1-style SSQC. Внутри рассматриваемого репозитория рабочим остаётся сам класс точки, а не её флаги.

#### Практические сценарии использования
```
{
"classname" "info_player_coop"
"spawnflags" "1"
}
```
В стандартном basemod это не меняет поведение кооперативной точки старта.

### mangle
`тип значения: vector`

* Применимо к: `info_player_start`, `info_player_start2`, `info_player_coop`, `info_player_deathmatch`, `info_player_team1`, `info_player_team2`.

#### Описание и логика работы
`mangle` в basemod используется у некоторых других сущностей, например intermission-камеры, но не у обычных `info_player_*` стартов. Логика появления игрока копирует `spot.angles`, а не `spot.mangle`. Поэтому переносить привычку из `info_intermission` на player spawns не стоит: если нужно задать направление старта, используйте `angle` или `angles`. Сам по себе `mangle` на этих классах остаётся неиспользованным полем.

#### Практические сценарии использования
```
{
"classname" "info_player_start"
"mangle" "0 180 0"
}
```
Такой ключ не развернёт игрока в стандартном basemod; для этого нужен `angle` или `angles`.

### health
`тип значения: float`

* Применимо к: `info_player_start`, `info_player_start2`, `info_player_coop`, `info_player_deathmatch`, `info_player_team1`, `info_player_team2`.

#### Описание и логика работы
`health` у стартовой точки игрока не читается. При создании игрока `PutClientInServer()` сам назначает ему стандартное здоровье (`100`) либо заменяет его специальными значениями в отдельных вариантах deathmatch. Поэтому попытка записать `health` прямо в `info_player_start` или `info_player_deathmatch` не работает как способ менять HP на старте карты. Управлять стартовым здоровьем нужно через QuakeC-логику игрока, а не через саму точку спауна.

#### Практические сценарии использования
```
{
"classname" "info_player_deathmatch"
"health" "250"
}
```
Обычный basemod проигнорирует это поле и всё равно выдаст игроку здоровье по правилам режима.

### model
`тип значения: string`

* Применимо к: `info_player_start`, `info_player_start2`, `info_player_coop`, `info_player_deathmatch`, `info_player_team1`, `info_player_team2`.

#### Описание и логика работы
Стартовая точка игрока — это логическая метка, а не самостоятельный визуальный объект, поэтому `model` для неё стандартной пользы не имеет. Во время реального спауна модель назначается уже самому игроку (`progs/eyes.mdl`, затем `progs/player.mdl`), а не сущности `info_player_*`. Если оставить `model` на точке старта, basemod не начнёт рисовать из неё отдельного персонажа и не поменяет вид появляющегося игрока. Такой ключ стоит считать нерабочим для стандартного SSQC.

#### Практические сценарии использования
```
{
"classname" "info_player_team1"
"model" "progs/player.mdl"
}
```
Для basemod это ничего не меняет: точка старта остаётся только координатной меткой.
