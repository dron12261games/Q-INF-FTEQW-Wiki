# Триггеры и логические сущности

> [⬅ Вернуться к оглавлению вики](../README.md)

> [Индекс справочника ключей сущностей](./README.md)

Карты Quake связывают сущности через пары `target` и `targetname`: одна сущность срабатывает, ищет все объекты с совпадающим `targetname` и вызывает их логику использования. Для триггеров это основной способ строить последовательности событий без написания дополнительного кода. В basemod общая логика такого связывания сосредоточена в `SUB_UseTargets`, которая также обрабатывает `delay`, `message` и `killtarget`. Поэтому даже простая цепочка из нескольких `trigger_*` может вести себя как полноценный сценарий уровня.

## Классы триггерных сущностей

- `trigger_multiple` — повторно срабатывающий brush-триггер по касанию, по `use` или по уничтожению.
- `trigger_once` — одноразовый вариант `trigger_multiple`.
- `trigger_relay` — логический ретранслятор; сам по себе не касается игрока, а только передаёт активацию дальше.
- `trigger_secret` — одноразовый триггер секрета, увеличивающий счётчик найденных секретов.
- `trigger_counter` — накапливает несколько входных срабатываний и только потом активирует цель.
- `trigger_teleport` — переносит подходящие объекты к `info_teleport_destination`.
- `trigger_push` — толкает игрока, монстров и гранаты в направлении `angle`/`angles`.
- `trigger_hurt` — наносит периодический урон при касании.
- `trigger_monsterjump` — задаёт прыжок для ходящих монстров.
- `trigger_setskill` — историческая id1-сущность; в этом basemod фактически удаляется на спауне и логики не выполняет.
- `trigger_onlyregistered` — пропускает дальше только зарегистрированную версию игры, иначе печатает сообщение.
- `trigger_changelevel` — id1-style триггер смены уровня; в репозитории есть в соседних SSQC-модулях с классической логикой Quake.
- `path_corner` — маршрутная точка для `func_train` и монстров.
- `info_notnull` — непустая точка-цель, остающаяся в мире как координатный маркер.
- `info_null` — служебная точка, которая удаляется на спауне.
- `target_speaker` — реализации в `quakec\basemod` не найдено, поэтому отдельные ключи для него здесь не документируются.

## Ключи

### classname
`тип значения: string`

* Применимо к: `trigger_multiple`, `trigger_once`, `trigger_relay`, `trigger_secret`, `trigger_counter`, `trigger_teleport`, `trigger_push`, `trigger_hurt`, `trigger_monsterjump`, `trigger_setskill`, `trigger_onlyregistered`, `trigger_changelevel`, `path_corner`, `info_notnull`, `info_null`.

#### Описание и логика работы
`classname` выбирает, какую spawn-логику выполнит SSQC. Для триггеров это критично: один и тот же brush-объём при `classname "trigger_hurt"` наносит урон, а при `classname "trigger_multiple"` запускает цели. Если ключ отсутствует или написан с ошибкой, сущность не получит ожидаемого поведения. Для логических point-entity вроде `trigger_relay`, `info_notnull` и `path_corner` именно `classname` определяет, будет ли объект участвовать в связях уровня.

#### Практические сценарии использования
```
{
"classname" "trigger_once"
"target" "open_exit"
}
```
Одноразовый триггер активирует цель `open_exit`.

### targetname
`тип значения: string`

* Применимо к: `trigger_multiple`, `trigger_once`, `trigger_relay`, `trigger_secret`, `trigger_counter`, `trigger_teleport`, `path_corner`, `info_notnull`.

#### Описание и логика работы
`targetname` — имя, по которому сущность могут найти другие объекты через их `target`. У триггеров это обычно означает «не работай сам по себе, пока кто-то тебя не активирует». Особенно заметно это у `trigger_teleport`: если у телепорта есть `targetname`, касание не сработает, пока телепорт не был заранее включён через `use`. У `path_corner` и `info_notnull` ключ делает точку адресуемой целью маршрута или сценария.

#### Практические сценарии использования
```
{
"classname" "trigger_teleport"
"targetname" "enable_exit_tele"
"target" "exit_pad"
}
```
Такой телепорт существует на карте, но начнёт реально переносить объекты только после внешней активации `enable_exit_tele`.

### target
`тип значения: string`

* Применимо к: `trigger_multiple`, `trigger_once`, `trigger_relay`, `trigger_secret`, `trigger_counter`, `trigger_onlyregistered`, `trigger_changelevel`, `trigger_teleport`, `path_corner`.

#### Описание и логика работы
Для большинства триггеров `target` — это имя всех получателей, которым будет отправлено событие через `SUB_UseTargets`. Для `trigger_teleport` смысл особый: здесь `target` должен указывать на `targetname` сущности `info_teleport_destination`, иначе телепорт завершится ошибкой. У `path_corner` поле образует цепочку маршрута: `func_train` приезжает в текущую точку, затем читает её `target` и едет к следующей. Пустой `target` допустим не всегда: для `trigger_teleport` и маршрута поезда он обязателен.

#### Практические сценарии использования
```
{
"classname" "trigger_multiple"
"target" "lift_start"
}
```
При срабатывании триггер вызовет все сущности с `targetname "lift_start"`.

### target2
`тип значения: string`

* Применимо к: в рамках данного basemod как рабочий ключ не применяется.

#### Описание и логика работы
В исследованных id1-подобных исходниках `quakec\basemod` поле `target2` не используется триггерной логикой как стандартный сценарный вход. Если оставить его в `.map`, basemod не построит на нём поведение: вызов пойдёт только по обычному `target`. Такой ключ можно встретить как редакторскую заметку, совместимость с другим модом или остаток чужой entity-definition, но в описанных здесь сущностях эффекта не будет.

#### Практические сценарии использования
```
{
"classname" "trigger_relay"
"target" "phase_1"
"target2" "ignored_here"
}
```
Сработает только `target`; `target2` будет проигнорирован basemod-логикой.

### killtarget
`тип значения: string`

* Применимо к: `trigger_multiple`, `trigger_once`, `trigger_relay`, `trigger_secret`, `trigger_counter`, `trigger_onlyregistered`, `trigger_changelevel`.

#### Описание и логика работы
Если `killtarget` задан, `SUB_UseTargets` сначала ищет все сущности, у которых `targetname` совпадает с этим значением, и удаляет их из мира. Только после этого продолжается остальная сценарная логика. Это полезно для отключения старых триггеров, уничтожения временных блокеров и очистки сценарных заглушек. Важно помнить, что удаление окончательное для текущей карты: повторно «включить» такую сущность уже нельзя.

#### Практические сценарии использования
```
{
"classname" "trigger_once"
"killtarget" "secret_hint"
"target" "open_secret"
}
```
После первого срабатывания триггер удалит все объекты `secret_hint`, а затем активирует `open_secret`.

### message
`тип значения: string`

* Применимо к: `trigger_multiple`, `trigger_once`, `trigger_relay`, `trigger_secret`, `trigger_onlyregistered`, `trigger_changelevel`.

#### Описание и логика работы
`message` — текст, который `SUB_UseTargets` печатает в центре экрана, если активатором был игрок. У `trigger_secret` без собственного значения автоматически подставляется строка `You found a secret area!`. У `trigger_onlyregistered` сообщение используется в отрицательной ветке: если игра не зарегистрирована, текст выводится игроку, а цели не срабатывают. Исторически `trigger_setskill` тоже связывали с `message`, но в этом basemod сама сущность удаляется сразу и поле не читает.

#### Практические сценарии использования
```
{
"classname" "trigger_relay"
"message" "Power restored"
"target" "unlock_door"
}
```
Игрок увидит надпись `Power restored`, после чего сработает `unlock_door`.

### sounds
`тип значения: integer`

* Применимо к: `trigger_multiple`, `trigger_once`, `trigger_secret`.

#### Описание и логика работы
`sounds` выбирает заранее прошитый звуковой вариант срабатывания. У `trigger_multiple` и `trigger_once` код понимает значения `1` (`misc/secret.wav`), `2` (`misc/talk.wav`) и `3` (`misc/trigger1.wav`); остальные значения фактически молчат. У `trigger_secret` по умолчанию ставится `1`, а поддерживаются варианты `1` и `2`. Это не громкость и не путь к файлу, а именно числовой селектор пресета.

#### Практические сценарии использования
```
{
"classname" "trigger_multiple"
"sounds" "3"
"target" "machinery_on"
}
```
Триггер проиграет характерный звук большого переключателя перед активацией цели.

### noise
`тип значения: string`

* Применимо к: `trigger_multiple`, `trigger_once`, `trigger_secret`, `trigger_relay`.

#### Описание и логика работы
В basemod `noise` чаще всего заполняется самой spawn-логикой на основе `sounds`, но поле также участвует в общем поведении сообщений. Если при срабатывании сущности `message` непустой, а `noise` пустой, `SUB_UseTargets` автоматически проиграет стандартный `misc/talk.wav`; если `noise` уже задан, этот автозвук подавляется. Для `trigger_secret` и `trigger_multiple` именно `noise` реально проигрывается в момент запуска. Практически это внутренний рабочий ключ, но его полезно понимать при разборе поведения карты.

#### Практические сценарии использования
```
{
"classname" "trigger_secret"
"sounds" "2"
"message" "Hidden archive"
}
```
Через `sounds` у секрета будет заполнен `noise`, поэтому вместо стандартного «секретного» звука прозвучит вариант `misc/talk.wav`.

### wait
`тип значения: float`

* Применимо к: `trigger_multiple`, `trigger_once`, `trigger_secret`, `trigger_counter`, `path_corner`.

#### Описание и логика работы
Для `trigger_multiple` стандартное значение — `0.2` секунды: после срабатывания триггер временно блокируется и затем активируется снова. Если `wait > 0`, восстановление происходит через указанное число секунд; если `wait <= 0`, триггер удаляется после первого срабатывания. Именно поэтому `trigger_once`, `trigger_secret` и `trigger_counter` принудительно ставят `wait = -1`, превращая себя в одноразовые логические узлы. У `path_corner` ключ читается уже не самой точкой, а поездом: `func_train`, прибыв в corner, копирует `wait` себе и стоит здесь указанное число секунд перед отправкой дальше.

#### Практические сценарии использования
```
{
"classname" "trigger_multiple"
"wait" "5"
"target" "alarm_loop"
}
```
Триггер можно будет повторно задействовать только через 5 секунд.

### delay
`тип значения: float`

* Применимо к: `trigger_multiple`, `trigger_once`, `trigger_relay`, `trigger_secret`, `trigger_counter`, `trigger_onlyregistered`, `trigger_changelevel`.

#### Описание и логика работы
`delay` откладывает не само касание и не вход игрока в brush, а момент вызова целей. `SUB_UseTargets` создаёт временную сущность `DelayedUse`, копирует туда `message`, `killtarget`, `target` и активатора, а затем запускает их через указанное число секунд. Пока задержка не истекла, исходный триггер уже может считаться использованным или даже быть удалённым, но отложенное событие всё равно доработает. Значение задаётся в секундах; ноль означает отсутствие задержки.

#### Практические сценарии использования
```
{
"classname" "trigger_once"
"delay" "2.5"
"target" "collapse_bridge"
}
```
Игрок входит в триггер сейчас, а обрушение моста происходит через 2.5 секунды.

### health
`тип значения: float`

* Применимо к: `trigger_multiple`, `trigger_once`.

#### Описание и логика работы
Если `health` задан у `trigger_multiple` или `trigger_once`, триггер перестаёт реагировать на касание и становится разрушаемым объектом: его нужно «убить», чтобы он сработал. При таком режиме basemod сохраняет исходное значение в `max_health`, переводит сущность в `SOLID_BBOX` и назначает специальную death-логику, которая запускает цели. Для повторно используемого `trigger_multiple` здоровье восстанавливается после `wait`. Комбинация `health` вместе с `NOTOUCH` запрещена и вызывает ошибку конфигурации.

#### Практические сценарии использования
```
{
"classname" "trigger_once"
"health" "50"
"target" "breakable_switch"
}
```
Триггер сработает только после того, как игрок нанесёт по нему суммарно 50 единиц урона.

### count
`тип значения: integer`

* Применимо к: `trigger_counter`.

#### Описание и логика работы
`count` задаёт, сколько входных активаций должен накопить `trigger_counter`, прежде чем он действительно вызовет свои цели. Если ключ отсутствует, используется значение `2`. Каждый `use` уменьшает счётчик на единицу; пока значение не дошло до нуля, триггер только печатает промежуточные сообщения игроку и ничего дальше не запускает. После достижения нуля срабатывает обычная цепочка `multi_trigger`, а сам counter больше не используется повторно.

#### Практические сценарии использования
```
{
"classname" "trigger_counter"
"count" "3"
"target" "boss_door"
}
```
Дверь босса откроется только после трёх отдельных событий, бьющих в этот counter.

### dmg
`тип значения: float`

* Применимо к: `trigger_hurt`.

#### Описание и логика работы
`dmg` определяет, сколько очков урона наносит `trigger_hurt` за одно касание-тик. По умолчанию используется `5`. После нанесения урона триггер на 1 секунду делает себя неактивным (`SOLID_NOT`), а затем включает обратно, поэтому на практике урон идёт импульсами примерно раз в секунду, а не каждый кадр. Значение измеряется в обычных хитпоинтах Quake.

#### Практические сценарии использования
```
{
"classname" "trigger_hurt"
"dmg" "20"
}
```
Кислотная яма будет снимать по 20 HP за каждый срабатывающий тик урона.

### speed
`тип значения: float`

* Применимо к: `trigger_push`, `trigger_monsterjump`, `path_corner`.

#### Описание и логика работы
У `trigger_push` `speed` задаёт силу толчка; если ключ отсутствует, используется `1000`. Код умножает направление на `speed * 10`, поэтому большие значения дают очень сильный launch-эффект. У `trigger_monsterjump` по умолчанию применяется `200`, и это уже горизонтальная составляющая скорости монстра. У `path_corner` собственная spawn-логика ключ не читает, но для `func_train` это традиционный редакторский спутник corner-маршрутов; в конкретном basemod скорость у поезда задаётся в основном на самом `func_train`, а не на `path_corner`.

#### Практические сценарии использования
```
{
"classname" "trigger_push"
"speed" "1200"
"angle" "90"
}
```
Такой объём будет резко уносить игрока в сторону yaw `90`.

### height
`тип значения: float`

* Применимо к: `trigger_monsterjump`.

#### Описание и логика работы
`height` определяет вертикальную скорость, которую `trigger_monsterjump` придаёт монстру при успешном касании. По умолчанию это `200`. Горизонтальный вектор задаётся отдельно через `speed` и направление `angle`/`angles`, а `height` отвечает только за подъём по оси Z. Если монстр касается триггера в воздухе, горизонтальная скорость всё равно обновится, но вертикальный импульс не будет выдан до тех пор, пока существо не считается стоящим на земле.

#### Практические сценарии использования
```
{
"classname" "trigger_monsterjump"
"height" "320"
"speed" "180"
}
```
Монстр получит более высокий прыжок, сохранив умеренный горизонтальный разгон.

### map
`тип значения: string`

* Применимо к: `trigger_changelevel`.

#### Описание и логика работы
`map` содержит имя следующей карты, на которую должен перевести игрока `trigger_changelevel`. При касании игроком код сохраняет это значение в глобальный `nextmap`, затем выполняет `SUB_UseTargets`, а после этого либо сразу меняет уровень, либо запускает интермиссию. Если `map` не задан, id1-style логика считает это ошибкой карты. Здесь нужен именно внутренний name карты, без расширения `.bsp`.

#### Практические сценарии использования
```
{
"classname" "trigger_changelevel"
"map" "e1m2"
}
```
После входа игрока в объём уровень переключится на `e1m2`.

### angle
`тип значения: float`

* Применимо к: `trigger_multiple`, `trigger_once`, `trigger_push`, `trigger_monsterjump`.

#### Описание и логика работы
`angle` — классический однокомпонентный Quake-ключ для задания yaw-направления. В trigger-логике он часто преобразуется в внутренний вектор `movedir`. Для `trigger_multiple` и `trigger_once` это направление используется как фильтр: игрок должен смотреть примерно в нужную сторону, иначе касание игнорируется. Для `trigger_push` и `trigger_monsterjump` тот же вектор задаёт направление импульса. Значение `360` традиционно используют как эквивалент нулевого yaw там, где нельзя оставлять полный нулевой вектор углов.

#### Практические сценарии использования
```
{
"classname" "trigger_multiple"
"angle" "180"
"target" "backtrack_warning"
}
```
Триггер сработает только когда игрок входит в него, глядя примерно назад по yaw `180`.

### angles
`тип значения: vector`

* Применимо к: `trigger_push`, `trigger_monsterjump`, `trigger_teleport` (через точку назначения).

#### Описание и логика работы
`angles` нужен там, где одних yaw-углов мало или где редактор/мод уже работает с полным вектором ориентации. У `trigger_push` и `trigger_monsterjump` итоговая логика всё равно приходит к направляющему вектору толчка. Для телепортов более важен полный поворот точки назначения: `info_teleport_destination` сохраняет свои `angles` во внутреннее поле и разворачивает прибывшего игрока именно так. Нулевой вектор обычно означает отсутствие дополнительного наклона; для `trigger_monsterjump` при полностью нулевых углах код подставляет безопасный вариант `0 360 0`.

#### Практические сценарии использования
```
{
"classname" "info_teleport_destination"
"targetname" "exit_pad"
"angles" "0 90 0"
}
```
Игрок после телепорта окажется повёрнут лицом по yaw `90`.

### origin
`тип значения: vector`

* Применимо к: `trigger_relay`, `path_corner`, `info_notnull`, `info_null`, `info_teleport_destination`.

#### Описание и логика работы
`origin` задаёт мировые координаты point-entity. Для `path_corner` это фактическая точка, к которой поедет `func_train` или к которой будут привязаны маршрутные монстры. Для `info_notnull` и `info_teleport_destination` это чистый маркер положения в мире. У `info_null` координаты существуют только до момента spawn-удаления: basemod эту сущность сразу убирает, так что она полезна скорее как редакторская или движковая вспомогательная точка.

#### Практические сценарии использования
```
{
"classname" "path_corner"
"targetname" "train_a"
"origin" "512 256 64"
}
```
Это создаёт маршрутную точку поезда в координатах `(512 256 64)`.

### model
`тип значения: string`

* Применимо к: brush-сущности `trigger_multiple`, `trigger_once`, `trigger_secret`, `trigger_teleport`, `trigger_push`, `trigger_hurt`, `trigger_monsterjump`, `trigger_onlyregistered`.

#### Описание и логика работы
У brush-триггеров `model` — это внутренний BSP-модельный объём, который компилятор карты создаёт для каждой brush-сущности. `InitTrigger` вызывает `setmodel(self, self.model)`, чтобы получить размер, связаться с миром и превратить brush в рабочую trigger-область, а затем очищает визуальную модель, чтобы она не отображалась. Ручное прописывание `model` в текстовом `.ent` без соответствующей brush-модели обычно бесполезно. Для чисто логических point-entity этот ключ не нужен.

#### Практические сценарии использования
```
{
"classname" "trigger_hurt"
"model" "*12"
"dmg" "10"
}
```
Внешне это означает: триггер использует brush-модель карты `*12` как область урона.

### spawnflags
`тип значения: integer`

* Применимо к: `trigger_multiple`, `trigger_once`, `trigger_counter`, `trigger_teleport`, `trigger_push`, `trigger_changelevel`.

#### Описание и логика работы
`spawnflags` — битовая маска дополнительных режимов поведения. Один и тот же числовой ключ может включать несколько опций сразу, если сложить их значения. Сами биты зависят от `classname`: например, `1` у `trigger_counter` означает `NOMESSAGE`, а у `trigger_teleport` — `PLAYER_ONLY`. Поэтому интерпретировать `spawnflags` всегда нужно только в контексте конкретной сущности.

#### Практические сценарии использования
```
{
"classname" "trigger_teleport"
"spawnflags" "3"
"target" "arena_exit"
}
```
Здесь число `3` одновременно включает `PLAYER_ONLY` и `SILENT`.

### spawnflags (NOTOUCH)
`тип значения: integer`

* Применимо к: `trigger_multiple`, `trigger_once`.

#### Описание и логика работы
Бит `NOTOUCH` имеет значение `1` и отключает реакцию на прямое касание. Такой триггер можно будет активировать только через внешнее `use`-событие или, если у него есть `health`, через уничтожение. В старых комментариях к коду этот режим назван устаревшим по сравнению с `trigger_relay`, потому что для чистой логической пересылки удобнее именно relay. Если одновременно выставить `health` и `NOTOUCH`, basemod посчитает карту ошибочной.

#### Практические сценарии использования
```
{
"classname" "trigger_once"
"spawnflags" "1"
"target" "remote_step"
}
```
Игрок не сможет включить этот триггер телом; нужен внешний импульс от другой сущности.

### spawnflags (NOMESSAGE)
`тип значения: integer`

* Применимо к: `trigger_counter`.

#### Описание и логика работы
У `trigger_counter` бит `NOMESSAGE` также равен `1`, но смысл уже другой: suppress промежуточных и финального сообщений игроку. Без этого флага counter печатает `There are more to go...`, `Only 2 more to go...` и `Sequence completed!`, если активатором был игрок. Сценарная логика при этом не меняется: скрывается только текстовый фидбек.

#### Практические сценарии использования
```
{
"classname" "trigger_counter"
"spawnflags" "1"
"count" "4"
"target" "silent_unlock"
}
```
Счётчик молча накопит четыре события и откроет `silent_unlock` без подсказок на экране.

### spawnflags (PLAYER_ONLY)
`тип значения: integer`

* Применимо к: `trigger_teleport`.

#### Описание и логика работы
У `trigger_teleport` бит `PLAYER_ONLY` имеет значение `1` и разрешает перенос только сущностям с `classname "player"`. Монстры, предметы, трупы и другие подходящие объекты будут проигнорированы даже при контакте с триггерным объёмом. Это полезно там, где телепорт должен работать как чисто игроковый выход, не ломая бой и патрули монстров.

#### Практические сценарии использования
```
{
"classname" "trigger_teleport"
"spawnflags" "1"
"target" "secret_exit"
}
```
Через такой телепорт сможет пройти только игрок.

### spawnflags (SILENT)
`тип значения: integer`

* Применимо к: `trigger_teleport`.

#### Описание и логика работы
Бит `SILENT` у `trigger_teleport` имеет значение `2` и отключает постоянный эмбиентный гул телепорта в месте самого триггера. Визуальные вспышки и звуки прибытия/отбытия при фактическом переносе остаются, но фоновое `ambience/hum1.wav` не ставится. Это удобно для скрытых или «магических» телепортов, которые не должны выдавать себя заранее по звуку.

#### Практические сценарии использования
```
{
"classname" "trigger_teleport"
"spawnflags" "2"
"target" "ambush_pad"
}
```
Телепорт будет работать, но без постоянного фонового гула в комнате.

### spawnflags (PUSH_ONCE)
`тип значения: integer`

* Применимо к: `trigger_push`.

#### Описание и логика работы
Бит `PUSH_ONCE` у `trigger_push` имеет значение `1`. После первого успешного толчка триггер немедленно удаляет себя из мира. Это позволяет делать одноразовые launch-pad-события, обвалы, выбросы воздуха или scripted-подбрасывания, которые не должны повторяться при повторном проходе игрока.

#### Практические сценарии использования
```
{
"classname" "trigger_push"
"spawnflags" "1"
"speed" "800"
"angle" "0"
}
```
Игрок получит один импульс вперёд, после чего объём исчезнет.

### spawnflags (NO_INTERMISSION)
`тип значения: integer`

* Применимо к: `trigger_changelevel`.

#### Описание и логика работы
У id1-style `trigger_changelevel` бит `NO_INTERMISSION` имеет значение `1`. Если он включён и игра не в deathmatch, после касания карта переключится сразу, без показа интермиссии через `info_intermission`. При выключенном флаге движок сначала показывает стандартный экран завершения уровня и статистику. В кооперативе и deathmatch перед этим всё равно может выводиться сообщение о выходе игрока с уровня.

#### Практические сценарии использования
```
{
"classname" "trigger_changelevel"
"spawnflags" "1"
"map" "start"
}
```
Уровень немедленно сменится на `start`, минуя экран интермиссии.

### path_corner
`тип значения: string`

* Применимо к: `func_train`, монстры с маршрутами.

#### Описание и логика работы
Хотя `path_corner` — это `classname`, его стоит воспринимать и как специальный тип целевой точки. `func_train` ищет первую точку по своему `target`, затем на каждой остановке читает у текущего corner его следующий `target` и `wait`. Монстры также могут начинать движение к `path_corner`, если их собственный `target` указывает на такую точку. На практике цепочка `path_corner` формирует рельсы сценария, а не выполняет видимое действие сама по себе.

#### Практические сценарии использования
```
{
"classname" "path_corner"
"targetname" "route_1"
"target" "route_2"
}
```
Поезд или монстр, пришедший в `route_1`, затем продолжит движение к `route_2`.

### info_notnull
`тип значения: string`

* Применимо к: сценарные точки-цели, в том числе замены вроде `target_position`.

#### Описание и логика работы
`info_notnull` — простая point-entity без собственной активной логики, но в отличие от `info_null` она не удаляется на спауне. Поэтому её удобно использовать как физически существующую координатную цель для лучей, молний, кастомных эффектов или любых сущностей, которым нужен адресуемый маркер в мире. Обычно ей дают `targetname`, чтобы на неё можно было ссылаться из других объектов.

#### Практические сценарии использования
```
{
"classname" "info_notnull"
"targetname" "beam_end"
"origin" "768 64 128"
}
```
Эта сущность остаётся в мире и может служить конечной точкой для другого сценарного объекта.

### info_null
`тип значения: string`

* Применимо к: служебные позиционные маркеры, если логика читает их ещё до удаления или обрабатывает их вне basemod SSQC.

#### Описание и логика работы
`info_null` в исследованной id1-логике немедленно удаляет себя при спауне. Внутри basemod это значит, что рассчитывать на неё как на долго живущую адресуемую цель нельзя. Её используют как «пустую точку» для редакторских и некоторых движковых задач, где нужен сам факт координаты в данных карты, но не нужна активная сущность в runtime. Если требуется стойкий маркер, безопаснее брать `info_notnull`.

#### Практические сценарии использования
```
{
"classname" "info_null"
"origin" "128 128 256"
}
```
Такой объект хранит координату в исходных данных карты, но после спауна сам исчезает.
