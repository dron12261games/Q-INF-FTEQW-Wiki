# Общие ключи, worldspawn и глобальные настройки уровня

> [⬅ Вернуться к оглавлению вики](../README.md)

> [Индекс справочника ключей сущностей](./README.md)

Сущности в картах Quake описываются как текстовые блоки из пар `"ключ" "значение"`, хранящиеся внутри `.map`, а после компиляции — и внутри блока сущностей `.bsp`. При загрузке карты basemod читает эти пары в поля `self.<field>` и затем использует их в логике спауна, активации, движения и взаимодействия. Сущность `worldspawn` — это первый блок карты: она представляет сам уровень и содержит его глобальные параметры. Ниже собран справочник по наиболее общим ключам, которые встречаются у множества классов, а также по специальным ключам `worldspawn`, которые важны именно для карты целиком.

## Ключи, общие для всех сущностей

### classname
`тип значения: string`

* Применимо к: все сущности.

#### Описание и логика работы
Главный идентификатор класса сущности. Именно по строке `classname` basemod выбирает, какую spawn-логику выполнять: `trigger_multiple`, `func_door`, `light`, `monster_ogre`, `worldspawn` и так далее. Если ключ отсутствует, сущность не может быть корректно распознана как игровой объект. Пустая строка практически равносильна ошибке конфигурации: логика мода не получит ожидаемого класса.

#### Практические сценарии использования
```
{
"classname" "trigger_once"
"target" "open_secret"
}
```
Этот блок создаёт одноразовый триггер; без `classname` он не превратился бы в рабочую сущность.

### origin
`тип значения: vector("x y z")`

* Применимо к: почти все точечные сущности, а также служебно ко многим brush-сущностям.

#### Описание и логика работы
Координаты сущности в мире. Для точечных объектов это их фактическая позиция; для многих brush-сущностей это опорная точка, вокруг которой уже существует скомпилированная геометрия модели. Нулевой вектор `"0 0 0"` допустим и просто помещает объект в начало карты. Пустое значение обычно трактуется как отсутствие ключа, а отсутствие ключа чаще всего означает исходное положение из карты или внутреннее значение по умолчанию.

#### Практические сценарии использования
```
{
"classname" "info_player_start"
"origin" "256 128 64"
"angle" "90"
}
```
Точка старта игрока будет размещена в координатах `(256 128 64)`.

### angle
`тип значения: float`

* Применимо к: многие point- и brush-сущности, особенно двери, кнопки, триггеры, точки старта и телепорты.

#### Описание и логика работы
Классический однокомпонентный Quake-ключ для задания yaw-направления. На практике редактор записывает одно число, а игровая логика затем работает уже с итоговым направлением сущности: для дверей и кнопок это направление движения, для стартовых точек — поворот игрока, для некоторых триггеров — проверка, смотрит ли активатор в нужную сторону. В комментариях `subs.qc` отдельно отмечено, что специальные значения для вертикали кодируются как особые углы: `-1` означает вверх, `-2` вниз. Значение `360` нередко используют там, где нужен нулевой yaw, но при этом нельзя оставлять все углы равными нулю.

#### Практические сценарии использования
```
{
"classname" "func_button"
"angle" "90"
"target" "lift_start"
}
```
Кнопка будет утапливаться по направлению yaw `90`, а затем активирует цель `lift_start`.

### angles
`тип значения: vector("x y z")`

* Применимо к: сущности, которым нужен полный поворот по pitch/yaw/roll, либо внутренняя ориентация в логике.

#### Описание и логика работы
Полный трёхкомпонентный поворот сущности. В basemod это поле особенно важно там, где одного `angle` недостаточно: например, при сохранении ориентации телепортационного назначения или межуровневой камеры. Нулевой вектор `"0 0 0"` обычно означает отсутствие ограничений по направлению либо «смотреть как есть». Для некоторых классов после чтения карта может копировать `angles` в `mangle`, а само `angles` затем сбрасывается, чтобы brush-модель не вращалась визуально.

#### Практические сценарии использования
```
{
"classname" "info_teleport_destination"
"origin" "1024 64 128"
"angles" "0 180 0"
"targetname" "exit_pad"
}
```
Телепорт прибудет в эту точку и развернёт игрока лицом назад по yaw `180`.

### targetname
`тип значения: string`

* Применимо к: почти все активируемые сущности и все сущности-цели.

#### Описание и логика работы
Имя, по которому сущность может быть найдена и активирована другой сущностью через её `target`. В `SUB_UseTargets` поиск выполняется по совпадению `self.target` у активатора с `targetname` у получателя. Если ключ отсутствует, сущность нельзя вызвать как цель по имени, но она всё ещё может работать сама по себе. Пустая строка эквивалентна отсутствию именованной цели.

#### Практические сценарии использования
```
{
"classname" "func_door"
"targetname" "silver_exit"
"angle" "0"
}
```
Дверь не будет найдена автоматически кем-либо, кроме сущностей, которые указывают `target "silver_exit"`.

### target
`тип значения: string`

* Применимо к: триггеры, кнопки, двери, платформы, поезда, changelevel и многие прочие активаторы.

#### Описание и логика работы
Имя цели, которое активатор ищет среди чужих `targetname`. Это базовый способ «проводки» логики карты в basemod: триггер нашёлся, кнопка нажалась, дверь открылась — затем вызываются все сущности с совпавшим `targetname`. Если ключ отсутствует, `SUB_UseTargets` просто не найдёт никого для вызова. Пустая строка работает так же, как отсутствие цели.

#### Практические сценарии использования
```
{
"classname" "trigger_once"
"target" "silver_exit"
}
```
При срабатывании этот триггер активирует все сущности с `targetname "silver_exit"`.

### target2
`тип значения: string`

* Применимо к: в basemod SSQC не используется как общее поле.

#### Описание и логика работы
В классическом `quakec\basemod\defs.qc` поле `target2` не объявлено и стандартная логика basemod его не читает. Это значит, что такой ключ может присутствовать в `.map` как редакторский запас или как совместимый маркер для другого мода, но именно этот id1-подобный basemod не строит на нём поведение. Отсутствие и наличие `target2` в рамках данного мода одинаковы: эффекта не будет. Для практической работы в basemod используйте обычный `target` либо промежуточные `trigger_relay`.

#### Практические сценарии использования
```
{
"classname" "trigger_relay"
"target" "first_step"
"target2" "unused_in_basemod"
}
```
Сработает только обычный `target`; `target2` в basemod останется неиспользованным.

### target3
`тип значения: string`

* Применимо к: в basemod SSQC не используется как общее поле.

#### Описание и логика работы
Аналогично `target2`, поле `target3` не входит в набор читаемых полей basemod и не обслуживается его стандартными вспомогательными функциями. Ключ можно встретить в картах, ориентированных на более расширенные QC-базы, но для данной модификации он фактически инертен. Пустая строка, отсутствие ключа и произвольное значение дают один и тот же результат: никакой стандартной реакции со стороны basemod.

#### Практические сценарии использования
```
{
"classname" "func_button"
"target" "main_chain"
"target3" "unused_in_basemod"
}
```
Кнопка активирует только `main_chain`; третья цель стандартной логикой не вызывается.

### killtarget
`тип значения: string`

* Применимо к: любые сущности, которые используют `SUB_UseTargets` — прежде всего триггеры, кнопки, двери и некоторые служебные объекты.

#### Описание и логика работы
Имя набора сущностей, которые должны быть удалены в момент активации. В `SUB_UseTargets` удаление по `killtarget` выполняется раньше, чем активация обычного `target`, поэтому этим ключом удобно отключать старые триггеры, секреты, ловушки или временные декорации. Если ключ отсутствует, ничего не удаляется. Пустая строка не даёт эффекта; совпадение с несколькими сущностями удаляет все найденные объекты.

#### Практические сценарии использования
```
{
"classname" "trigger_once"
"target" "open_exit"
"killtarget" "ambush_once"
}
```
Триггер откроет выход и одновременно удалит все сущности с `targetname "ambush_once"`.

### spawnflags
`тип значения: integer`

* Применимо к: многие классы сущностей.

#### Описание и логика работы
Битовое поле флагов, которое один и тот же класс интерпретирует по-своему. Важно, что одно и то же числовое значение для разных классов означает разное: у `trigger_multiple` бит `1` — это `notouch`, у `light` — `START_OFF`, у `func_door` — уже другой набор флагов. Значение `0` означает «никакие специальные режимы не включены». Отрицательные значения не имеют полезного смысла для стандартных карт и только запутают разбор битов.

#### Практические сценарии использования
```
{
"classname" "light"
"style" "32"
"spawnflags" "1"
"targetname" "lamp_toggle"
}
```
Для `light` бит `1` означает `START_OFF`: лампа появится выключенной и сможет включаться по цели.

### model
`тип значения: string`

* Применимо к: worldspawn, почти все brush-сущности, часть point-сущностей с собственными моделями.

#### Описание и логика работы
Путь или внутренний идентификатор модели сущности. Для `worldspawn` это путь вида `maps/<имя>.bsp`, для brush-сущностей — обычно внутренние модели вида `*1`, `*2` и так далее, назначенные при компиляции карты, а для некоторых point-объектов — путь к `.mdl` или `.spr`. В большинстве случаев маппер не правит это поле вручную у brush-объектов: оно генерируется автоматически. Пустое значение допустимо только у тех сущностей, которым модель не нужна или которые сами её очищают.

#### Практические сценарии использования
```
{
"classname" "light_globe"
"origin" "320 64 128"
"model" "progs/s_light.spr"
}
```
У point-сущностей с собственной графикой `model` задаёт, что именно будет отображаться в мире.

### wait
`тип значения: float`

* Применимо к: триггеры, двери, кнопки, платформы, поезда и другие повторно используемые активаторы/механизмы.

#### Описание и логика работы
Интервал ожидания между срабатыванием и повторной готовностью либо временем возврата в исходное состояние — точная семантика зависит от класса. В `trigger_multiple` по умолчанию это `0.2`, у `func_button` — `1`, у `func_door` — `3`, у секретной двери — `5`; у `trigger_once` и `trigger_counter` поле принудительно становится `-1`, делая объект одноразовым. Ноль обычно означает «используй классический default данного класса», а отрицательное значение для многих активаторов означает отсутствие повторного возврата. Поэтому при ручной правке важно смотреть не только на сам ключ, но и на конкретный класс сущности.

#### Практические сценарии использования
```
{
"classname" "trigger_multiple"
"target" "alarm_loop"
"wait" "2.5"
}
```
Триггер сможет срабатывать повторно, но не чаще одного раза в 2.5 секунды.

### delay
`тип значения: float`

* Применимо к: сущности, вызывающие `SUB_UseTargets`, прежде всего триггеры и часть кнопок/дверей.

#### Описание и логика работы
Задержка перед реальным вызовом целей. Если `delay` ненулевой, `SUB_UseTargets` не активирует цели сразу, а создаёт временную сущность `DelayedUse`, которая перенесёт тот же `message`, `killtarget` и `target` на несколько секунд вперёд. Ноль означает мгновенное срабатывание. Отрицательные значения стандартной картографической практики не имеют: логика ожидает обычную неотрицательную задержку.

#### Практические сценарии использования
```
{
"classname" "trigger_once"
"target" "boss_door"
"delay" "4"
}
```
После входа игрока в триггер дверь откроется не сразу, а через 4 секунды.

### message
`тип значения: string`

* Применимо к: триггеры, двери, секреты, worldspawn и многие служебные сущности.

#### Описание и логика работы
Текстовое сообщение, показываемое игроку, либо строковое значение специального назначения для конкретного класса. В `SUB_UseTargets` сообщение выводится в [`centerprint`](../37-quakec-builtins-reference/12-system-debug-builtins.md#centerprint), если активатор — игрок и строка не пуста; у `trigger_secret` при отсутствии ключа подставляется стандартная строка `You found a secret area!`; у дверей сообщение может служить подсказкой для закрытой/ключевой двери до её открытия. Пустая строка означает отсутствие текста. Для `worldspawn` этот же ключ имеет отдельный смысл заголовка уровня и описан ниже отдельно.

#### Практические сценарии использования
```
{
"classname" "trigger_once"
"target" "lift01"
"message" "Platform activated"
}
```
При срабатывании игрок увидит центральную надпись `Platform activated`.

### noise
`тип значения: string`

* Применимо к: триггеры и некоторые механизмы, которые проигрывают одиночный звук при срабатывании.

#### Описание и логика работы
Путь к звуковому файлу, который сущность проигрывает в момент активации. В `trigger_multiple` и родственных ему классах `self.noise` воспроизводится в `multi_trigger`, поэтому ключ часто заполняется не вручную, а автоматически через числовой `sounds`. Если в `SUB_UseTargets` выводится `message`, а `noise` не задан, basemod использует стандартный `misc/talk.wav` как звук оповещения. Пустая строка или отсутствие ключа просто убирают пользовательский звук.

#### Практические сценарии использования
```
{
"classname" "trigger_multiple"
"target" "secret_chain"
"noise" "misc/secret.wav"
}
```
Триггер вручную получает собственный звук срабатывания, независимо от presets через `sounds`.

### sounds
`тип значения: integer`

* Применимо к: worldspawn, триггеры, двери, кнопки, платформы, поезда и другим классам с набором звуковых пресетов.

#### Описание и логика работы
Числовой селектор звукового режима, но его конкретный смысл жёстко зависит от класса. У `trigger_multiple` и `trigger_secret` это выбор заранее заданного сигнала, у `func_button`, `func_door`, `func_plat` и `func_train` — банк звуков механизма, а у `worldspawn` — номер музыкального CD-трека карты. Значение `0` в одних классах значит «без звука», а в других активирует стандартный default, поэтому переносить числа между сущностями нельзя. При отсутствии ключа объект либо берёт собственный default, либо остаётся без дополнительного звука.

#### Практические сценарии использования
```
{
"classname" "func_door"
"targetname" "vault"
"sounds" "2"
}
```
Для двери будет выбран второй набор механических звуков, а не каменный вариант по умолчанию.

### count
`тип значения: integer`

* Применимо к: `trigger_counter` и отдельным специализированным классам.

#### Описание и логика работы
Счётчик требуемых активаций до выполнения действия. В классическом basemod он напрямую используется `trigger_counter`: значение уменьшается при каждом использовании, а при достижении нуля вызываются цели и сущность удаляется. Если `count` не задан, `trigger_counter` получает default `2`. Ноль или отрицательное число для карты почти всегда означает мгновенное либо уже исчерпанное состояние и обычно не имеет смысла как нормальная настройка.

#### Практические сценарии использования
```
{
"classname" "trigger_counter"
"target" "seal_open"
"count" "3"
}
```
Цепочка сработает только после трёх отдельных активаций.

### dmg
`тип значения: float`

* Применимо к: двери, платформы, поезда, `trigger_hurt` и другим наносящим урон сущностям.

#### Описание и логика работы
Величина урона, которую сущность наносит при блокировке или касании. У `func_door`, `func_train` и `func_plat` default обычно `2`, у `trigger_hurt` — `5`. Ноль почти всегда заменяется классическим значением по умолчанию данного класса. Отрицательные числа для стандартной логики не имеют полезного значения и могут приводить к неочевидному поведению карты.

#### Практические сценарии использования
```
{
"classname" "trigger_hurt"
"dmg" "20"
}
```
Каждое касание этого объёма будет наносить заметно более сильный урон, чем стандартный `5`.

### health
`тип значения: float`

* Применимо к: монстры, игроки, а также damage-активируемые триггеры, кнопки и двери.

#### Описание и логика работы
Количество здоровья или порог прочности, которое требуется снять, чтобы сущность умерла либо активировалась как «простреливаемая». В `trigger_multiple`, `func_button` и `func_door` наличие `health` меняет сам способ использования: вместо обычного касания объект приходится разрушать или простреливать. Если ключ отсутствует, такие сущности обычно остаются touch/use-активируемыми. Ноль равносилен отсутствию специальной прочности, а положительные значения делают поведение явным.

#### Практические сценарии использования
```
{
"classname" "func_button"
"target" "trap_start"
"health" "10"
}
```
Кнопка станет «простреливаемой»: её нужно повредить на 10 единиц, чтобы она сработала.

### style
`тип значения: integer`

* Применимо к: в первую очередь `light`, `light_fluoro`, `light_fluorospark` и родственным световым сущностям.

#### Описание и логика работы
Номер lightstyle-анимации. Значение `0` означает обычный постоянный свет; в `world.qc` заранее настраиваются стандартные таблицы стилей `0`–`11`, а комментарии в `misc.qc` показывают, что для переключаемых ламп значимы стили `32+`. У `light_fluorospark`, если `style` не задан, по умолчанию ставится `10` — мерцающий флуоресцентный свет. Для большинства несветовых сущностей этот ключ не имеет смысла.

#### Практические сценарии использования
```
{
"classname" "light"
"style" "32"
"targetname" "hall_lamp"
}
```
Такой источник света можно будет переключать как отдельную лампу через цель `hall_lamp`.

### skin
`тип значения: integer`

* Применимо к: сущности с моделью, у которой есть несколько skins; фактически — только там, где класс или модель это поддерживает.

#### Описание и логика работы
Номер скина модели. Поле существует у всех entvars, но практический смысл имеет только для тех сущностей, чья модель действительно содержит несколько вариантов внешнего вида. Если класс сам никогда не обращает внимания на `skin`, а модель однокожная, ключ не даст видимого эффекта. При отсутствии ключа используется skin `0`.

#### Практические сценарии использования
```
{
"classname" "misc_model"
"model" "progs/custom.mdl"
"skin" "1"
}
```
Если модель поддерживает несколько skins, будет показан вариант с индексом `1`; иначе сущность останется внешне обычной.

### mangle
`тип значения: vector("x y z")`

* Применимо к: `info_intermission`, `info_teleport_destination`, `func_door_secret`, `func_plat` и другим классам, сохраняющим исходный поворот отдельно.

#### Описание и логика работы
Служебное поле для хранения «настоящих» углов там, где обычное `angles` потом сбрасывается или переиспользуется. В basemod его применяют для межуровневой камеры, телепортационных точек и части движущихся brush-сущностей: сначала карта задаёт `angles`, затем класс копирует их в `mangle`, а `angles` обнуляет. Это позволяет иметь логическое направление без визуального вращения BSP-модели. Пустой или нулевой вектор означает отсутствие специальной ориентации.

#### Практические сценарии использования
```
{
"classname" "info_intermission"
"origin" "2048 512 160"
"mangle" "15 270 0"
}
```
Камера интермиссии будет смотреть с небольшим наклоном вниз и в сторону yaw `270`.

### light
`тип значения: integer`

* Применимо к: световые сущности и компиляционные инструменты освещения.

#### Описание и логика работы
Интенсивность статического источника света, которую обычно читает не игровой рантайм, а lighting stage при подготовке карты. В `defs.qc` это представлено как служебное поле `light_lev` с пометкой, что игра его не использует, а комментарии в `misc.qc` дают привычные defaults: для обычного `light` типично `300`, для некоторых факелов — `200`. Отсутствие ключа означает, что берётся стандартная яркость конкретного класса либо default lighting tool. Отрицательные значения обычно бессмысленны для нормального освещения.

#### Практические сценарии использования
```
{
"classname" "light"
"origin" "128 128 192"
"light" "450"
}
```
При компиляции освещения этот источник обычно даст более яркое пятно света, чем стандартные `300`.

### speed
`тип значения: float`

* Применимо к: двери, кнопки, платформы, поезда, `trigger_push`, `trigger_monsterjump`, `misc_fireball` и другим движущимся/толкающим классам.

#### Описание и логика работы
Скорость движения или импульса, но единицы и смысл зависят от класса. У `func_button` default `40`, у `func_door` — `100`, у `func_plat` — `150`, у `trigger_push` и `misc_fireball` — `1000`, у `trigger_monsterjump` — `200`. Ноль почти всегда заменяется классическим значением по умолчанию. Отрицательные значения для стандартных карт нежелательны: они ломают ожидаемое направление или делают настройку нечитабельной.

#### Практические сценарии использования
```
{
"classname" "trigger_push"
"angle" "90"
"speed" "1600"
}
```
Такой push-триггер будет швырять игрока сильнее, чем обычный вариант со `speed 1000`.

### map
`тип значения: string`

* Применимо к: прежде всего `trigger_changelevel` и редким межуровневым служебным сущностям.

#### Описание и логика работы
Имя следующей карты без расширения, куда должна вести сущность смены уровня. В `trigger_changelevel` отсутствие `map` считается ошибкой конфигурации: без него невозможно выбрать следующую карту. Пустая строка практического смысла не имеет. Для большинства остальных классов этот ключ просто не нужен.

#### Практические сценарии использования
```
{
"classname" "trigger_changelevel"
"map" "e1m2"
}
```
При касании игроком уровень завершится переходом на карту `e1m2`.

### lip
`тип значения: float`

* Применимо к: `func_button`, `func_door`.

#### Описание и логика работы
Остаток brush-геометрии, который не доходит до конечной точки хода и остаётся «снаружи». Для кнопок default `4`, для дверей `8`. Ноль обычно заменяется стандартом класса. Слишком большое значение уменьшает фактический ход, а отрицательное делает настройку нелогичной и может увести объект дальше ожидаемого положения.

#### Практические сценарии использования
```
{
"classname" "func_door"
"angle" "0"
"lip" "16"
}
```
Дверь откроется не полностью, оставив видимую кромку в 16 юнитов.

### height
`тип значения: float`

* Применимо к: `func_plat`, `trigger_monsterjump`.

#### Описание и логика работы
Высота перемещения или вертикальная составляющая импульса. У `func_plat` ключ задаёт, насколько далеко вниз уходит платформа, вместо автоматического расчёта по размеру brush-модели. У `trigger_monsterjump` default `200` и означает вертикальную скорость прыжка монстра вверх. Ноль у платформы обычно ведёт к расчёту по модели, а у monsterjump — к подстановке default `200`.

#### Практические сценарии использования
```
{
"classname" "func_plat"
"height" "96"
"speed" "200"
}
```
Платформа будет опускаться ровно на 96 юнитов, а не на автоматически вычисленную величину.

## Ключи сущности worldspawn

### message
`тип значения: string`

* Применимо к: `worldspawn`.

#### Описание и логика работы
Название уровня, которое карта сообщает игроку как заголовок. В комментарии к `worldspawn` в `world.qc` прямо указано: `message` следует использовать как level name. В отличие от обычного `message` у триггеров, здесь это не реакция на активацию, а глобальная строка карты. Если ключ отсутствует, уровень остаётся без собственного текстового заголовка.

#### Практические сценарии использования
```
{
"classname" "worldspawn"
"message" "The Drowned Vault"
}
```
Карта получит читаемое имя уровня `The Drowned Vault`, а не только имя файла BSP.

### sounds
`тип значения: integer`

* Применимо к: `worldspawn`.

#### Описание и логика работы
Номер музыкального CD-трека уровня. Комментарий к `worldspawn` в `world.qc` прямо связывает этот ключ с музыкой карты. Важна именно числовая ссылка на трек, а не путь к файлу. Если ключ не задан, карта не задаёт собственный номер трека через этот механизм.

#### Практические сценарии использования
```
{
"classname" "worldspawn"
"sounds" "4"
}
```
При старте уровня будет использоваться музыкальный трек номер 4 по классической схеме Quake.

### worldtype
`тип значения: integer`

* Применимо к: `worldspawn`.

#### Описание и логика работы
Тип мира, который выбирает тематические наборы ресурсов для части объектов. В `defs.qc` заданы три значения: `0` — medieval, `1` — metal, `2` — base; затем `func_door` и некоторые предметы подбирают звуки и оформление, опираясь на `world.worldtype`. Если ключ отсутствует, логика всё равно ожидает его наличие и в некоторых ветках может писать диагностическое `no worldtype set!`. Для обычных карт следует задавать одно из трёх классических значений.

#### Практические сценарии использования
```
{
"classname" "worldspawn"
"worldtype" "2"
}
```
Мир будет считаться base-тематикой, и двери/часть объектов выберут соответствующие звуковые наборы.

### wad
`тип значения: string`

* Применимо к: `worldspawn`.

#### Описание и логика работы
Список WAD-архивов, использованных редактором карты. В basemod это поле объявлено у `worldspawn`, но помечено скорее как совместимое/служебное: сама игровая логика не строит на нём поведение уровня. Тем не менее ключ полезен для `.map`-исходников и внешних `.ent`, потому что фиксирует ожидаемый текстурный набор и сохраняет привычную редакторскую метаинформацию. Пустая строка допустима, но обычно нежелательна для нормального обмена исходниками карты.

#### Практические сценарии использования
```
{
"classname" "worldspawn"
"wad" "gfx/base.wad;gfx/medieval.wad"
}
```
Для gameplay это ничего не меняет, но карта сохраняет информацию о подключённых текстурных WAD-пакетах.

### model
`тип значения: string`

* Применимо к: `worldspawn`.

#### Описание и логика работы
Путь к BSP самой карты, доступный в логике как `world.model`. В `world.qc` basemod использует его как минимум для специального случая `maps/e1m8.bsp`, где гравитация карты принудительно меняется на `100`; на прочих картах ставится обычное `800`. Обычно этот ключ назначается автоматически при загрузке карты, а не руками маппера. Изменять его вручную в энтити-списке смысла почти нет.

#### Практические сценарии использования
```
{
"classname" "worldspawn"
"model" "maps/e1m8.bsp"
}
```
На практике `model` worldspawn приходит автоматически; именно по нему basemod узнаёт особый финальный уровень `e1m8`.

### gravity
`тип значения: float`

* Применимо к: `worldspawn` только как совместимый, но не рабочий ключ для basemod.

#### Описание и логика работы
Хотя поле `gravity` существует в `defs.qc`, в данном basemod оно является общим entvar-полем и не используется `worldspawn()` как читаемый map-key для глобальной настройки карты. Вместо этого `world.qc` жёстко выставляет [`sv_gravity`](../38-cvars-reference/05-physics-gameplay-cvars.md#sv_gravity): для `maps/e1m8.bsp` ставит `100`, для остальных карт — `800`. Поэтому строка `"gravity" "600"` внутри `worldspawn` в этом конкретном моде не переопределит гравитацию уровня. Если нужен иной режим, его придётся менять логикой мода, а не только ключом карты.

#### Практические сценарии использования
```
{
"classname" "worldspawn"
"gravity" "400"
}
```
В basemod этот ключ сам по себе не сработает: карта всё равно останется на штатной гравитации, назначенной кодом `worldspawn()`.

### sky
`тип значения: string`

* Применимо к: `worldspawn` как совместимый редакторский/движковый ключ, но не как ключ логики basemod.

#### Описание и логика работы
В `quakec\basemod\defs.qc` и `world.qc` нет поля или отдельной обработки `sky` для `worldspawn`, поэтому стандартная SSQC-логика basemod не принимает решений на основе этого ключа. Он может быть полезен для других модов, движковых расширений или внешнего пайплайна, но не участвует в поведении классического id1-подобного basemod. Отсутствие `sky` ничего не ломает именно в его QuakeC-логике. Иными словами, это не рабочий gameplay-key для данной QC-базы.

#### Практические сценарии использования
```
{
"classname" "worldspawn"
"sky" "dusk"
}
```
Такой ключ может иметь смысл в расширенных конфигурациях движка, но basemod SSQC не использует его для игровой логики.

### MaxRange
`тип значения: float`

* Применимо к: `worldspawn` только как потенциальный совместимый ключ, но не как стандартное поле basemod.

#### Описание и логика работы
В классическом наборе полей `basemod\defs.qc` ключ `MaxRange` не объявлен, а в `world.qc` и связанных общих скриптах он не читается. Следовательно, basemod не привязывает к нему ни глобальную дальность звука, ни видимости, ни иной системный параметр карты. Если редактор или другой мод добавит такой ключ в блок `worldspawn`, стандартная логика этого мода просто его проигнорирует. Для справочника важно понимать: `MaxRange` здесь не активный ключ, а только совместимый маркер для чужих расширений.

#### Практические сценарии использования
```
{
"classname" "worldspawn"
"MaxRange" "4096"
}
```
В рамках `quakec\basemod` эта строка не изменит поведение уровня, пока мод сам не научится её читать.
