# Свет и освещение

> [⬅ Вернуться к оглавлению вики](../README.md)

> [Индекс справочника ключей сущностей](./README.md)

Свет на карте Quake задаётся прежде всего точечными сущностями `light` и их производными `light_*`: они формируют запечённое освещение, могут участвовать в lightstyle-анимации и в FTEQW дополнительно служат исходными точками для генерации статичных реалтайм-светильников. Базовая игровая логика `quakec\basemod\misc.qc` определяет, какие классы света существуют, какие из них умеют включаться по событию и какие звуки/модели они добавляют в мир. Сами значения ключей затем подхватываются разными подсистемами: lightstyle и переключение света — QuakeC, перерасчёт baked lightmaps — `engine\gl\ltface.c`, импорт статичных realtime-lights из BSP-энтити — `engine\gl\gl_rlight.c`. Отдельно от этого эффекты, частицы, взрывы и вспышки создают временный динамический свет (`dlight`), но он уже относится к программным игровым эффектам, а не к map-ключам обычной сущности `light`.

В проверенных `quakec\basemod`, `engine\gl\ltface.c` и `engine\gl\gl_rlight.c` отдельные ключи `_sky` и `_distance` для light-сущностей не обнаружены, поэтому ниже они не описываются как подтверждённо рабочие ключи текущего дерева исходников.

## Классы сущностей света

- `light` — невидимый точечный источник света. В комментарии QuakeEd указан стандартный `light` = `300`, `style` = `0`. Если у него есть `targetname`, базовый QuakeC-код позволяет переключать его между включённым и выключенным состоянием.
- `light_fluoro` — невидимый люминесцентный светильник. По умолчанию тоже рассчитывается как `light 300`, `style 0`, но дополнительно проигрывает постоянный гул `ambience/fl_hum1.wav`.
- `light_fluorospark` — невидимая «сломанная» люминесцентная лампа. По умолчанию получает `style 10` (fluorescent flicker) и проигрывает `ambience/buzz1.wav`.
- `light_globe` — видимый шарообразный светильник со спрайтом `progs/s_light.spr`. В комментарии QuakeEd указан `light 300`, `style 0`; при realtime-импорте ему дополнительно подмешивается тёплый оттенок.
- `light_torch_small_walltorch` — короткий настенный факел с моделью `progs/flame.mdl`, постоянным огненным ambient-звуком и комментарием QuakeEd `light 200`, `style 0`. При realtime-импорте получает тёплый оранжевый оттенок.
- `light_flame_large_yellow` — большая жёлтая огненная сфера с моделью `progs/flame2.mdl`. В QuakeC это статическая декоративная модель с огненным ambient-звуком; при realtime-импорте ей назначается тёплый жёлто-оранжевый tint.
- `light_flame_small_yellow` — маленькая жёлтая огненная сфера. В `misc.qc` создаётся как статическая модель пламени с ambient-звуком.
- `light_flame_small_white` — маленькая белая огненная сфера. В `misc.qc` создаётся аналогично `light_flame_small_yellow`, но как отдельный classname.

## Ключи

### classname
`тип значения: string`

* Применимо к: всем световым entity-классам (`light`, `light_fluoro`, `light_fluorospark`, `light_globe`, `light_torch_small_walltorch`, `light_flame_large_yellow`, `light_flame_small_yellow`, `light_flame_small_white`).

#### Описание и логика работы
`classname` выбирает сам тип сущности и тем самым определяет, какая логика спауна будет выполнена. В `quakec\basemod\misc.qc` обычный `light` является невидимым логическим светом, `light_fluoro` и `light_fluorospark` добавляют статический ambient-звук, `light_globe` и flame/torch-варианты спаунят видимую статическую модель или спрайт. В `gl_rlight.c` classname также влияет на автоматически подмешиваемый оттенок для realtime-импорта: torch/flame-варианты становятся теплее, `light_globe` — слегка янтарным, а `light_fluoro` остаётся нейтральным.

#### Практические сценарии использования
```
{
"classname" "light_fluorospark"
}
```
Такой объект создаёт источник света класса «сломанная люминесцентная лампа»: для baked/lightstyle это обычный light-entity, а на стороне QuakeC дополнительно запускается характерный гул/треск.

### origin
`тип значения: vector("x y z")`

* Применимо к: всем световым entity-классам.

#### Описание и логика работы
`origin` задаёт точку, из которой исходит свет. Обычно этот ключ проставляет сам редактор карт по положению точечного объекта, и вручную его редактируют редко. И `ltface.c`, и `gl_rlight.c` читают `origin` напрямую: от него зависят положение baked-света, вычисление направления к `target`, а также точка, в которой создаётся статичный realtime-светильник. Если координаты не заданы, свет остаётся в начале координат карты, что почти всегда означает ошибку разметки.

#### Практические сценарии использования
```
{
"classname" "light"
"origin" "512 128 96"
}
```
Полезно в `.ent`-патчах или при ручной правке entity lump, когда нужно сдвинуть уже существующий свет без перекомпоновки остальной карты.

### light
`тип значения: integer или string из четырёх чисел "R G B brightness"`

* Применимо к: всем `light*`-сущностям.

#### Описание и логика работы
Это главный ключ яркости. В классическом Quake-формате задаётся одним числом: `300`, `600` и т. п. Тогда свет считается белым, а число одновременно используется как базовая сила и ориентир для радиуса. В `gl_rlight.c` поддержан и HL-стиль из четырёх чисел: `R G B brightness`, где первые три компоненты нормализуются как цвет, а четвёртая задаёт мощность. В `ltface.c` для перерасчёта baked lightmaps понимаются обе записи `light` и `_light`; если ключ отсутствует у classname, начинающегося с `light`, туда подставляется fallback `300`. Для статичных realtime-lights импортёр `gl_rlight.c` тоже принимает `_light`, потому что перед разбором отбрасывает один ведущий `_`.

#### Практические сценарии использования
```
{
"classname" "light"
"light" "450"
}
```
Классический белый источник средней силы.

### style
`тип значения: integer`

* Применимо к: `light`, `light_fluoro`, `light_fluorospark`, `light_globe`, flame/torch-вариантам и любым другим `light*`, если их ключи импортируются в baked или realtime-подсистему.

#### Описание и логика работы
`style` привязывает источник к таблице lightstyle-анимации. В базовом `world.qc` инициализируются стандартные стили `0`–`11` и тестовый `63`: `0` — ровный постоянный свет (`"m"`), `1` — flicker, `2` — slow strong pulse, `3` — candle, `4` — fast strobe, `5` — gentle pulse, `6` — второй вариант flicker, `7` и `8` — дополнительные candle-варианты, `9` — slow strobe, `10` — fluorescent flicker, `11` — slow pulse без полного ухода в чёрный, `63` — `"a"` (полностью выключено). Комментарий в `world.qc` отдельно отмечает, что стили `32`–`62` назначаются light-компилятором/переливкой для переключаемых светов. В `misc.qc` `light_use` меняет активный стиль между `"m"` и `"a"`, то есть фактически включает и выключает такой свет. Сама строка анимации может быть полностью переопределена во время игры builtin-функцией `lightstyle(style, "строка" [, rgb])`: буква `a` означает полную темноту, `z` — максимум яркости; все сущности с тем же номером стиля меняются синхронно. Хотя стандартный набор Quake традиционно описывают как `0`–`63`, движок внутренне умеет хранить больше lightstyles, но совместимые baked lightmaps обычно опираются именно на классические первые 64 номера.

#### Практические сценарии использования
```
{
"classname" "light"
"style" "10"
}
```
Такой свет будет использовать анимацию broken fluorescent из стандартной таблицы и мерцать без дополнительного QuakeC-кода.

### targetname
`тип значения: string`

* Применимо к: в первую очередь `light` и `light_fluoro`; как адрес логической связи может присутствовать и на других `light*`, но код переключения в `misc.qc` реализован именно для этих двух классов.

#### Описание и логика работы
`targetname` — имя, по которому другие сущности карты могут обратиться к свету. Для обычного `light` это принципиально важно: если `targetname` не задан, `misc.qc` удаляет сущность как «инертную», потому что после запекания она больше не нужна игровому миру. Если же `targetname` есть и `style >= 32`, объект получает `use`-обработчик `light_use` и может быть включён/выключен кнопкой, триггером или другой логикой. В `ltface.c` у `light` с `targetname`, но без явного стиля, автоматически подбирается/резервируется переключаемый стиль начиная с `32`, чтобы все источники с одинаковым `targetname` реагировали как одна группа.

#### Практические сценарии использования
```
{
"classname" "light"
"targetname" "lab_power"
"style" "32"
}
```
Такой свет получает логический адрес `lab_power`: любая кнопка или trigger с `target "lab_power"` сможет его переключить.

### target
`тип значения: string`

* Применимо к: направленным светам (`light` и другие `light*`), когда вы хотите превратить их в spotlight через цель-указатель.

#### Описание и логика работы
На световых сущностях `target` используется не как «кого включить», а как ссылка на отдельную entity-точку с совпадающим `targetname` — обычно `info_null`. И `ltface.c`, и `gl_rlight.c` сначала собирают координаты всех `targetname`, а затем, если у света заполнен `target`, рассчитывают направление луча от источника к этой точке. Именно эта связка превращает обычный point light в направленный конусный свет. Для ширины конуса при этом используется `angle` или значение FOV по умолчанию `40`, если явный угол не задан. Это другой механизм, чем переключение света по `targetname`.

#### Практические сценарии использования
```
{
"classname" "light"
"target" "spot_entrance"
"angle" "35"
}
```
Такой источник станет прожектором, если на карте есть отдельный `info_null` с `targetname "spot_entrance"`.

### spawnflags
`тип значения: integer`

* Применимо к: практически значимо для `light` и `light_fluoro`; в комментариях QuakeEd флаг также помечен у некоторых flame-вариантов, но проверенная логика включения/выключения есть именно у этих двух классов.

#### Описание и логика работы
Для обычного basemod-света подтверждён флаг `START_OFF = 1`. В `light_use` он трактуется как «сейчас свет выключен»: когда флаг установлен, стиль переключается на `"a"`; когда снят — на `"m"`. При спауне `light` и `light_fluoro` с `style >= 32` сразу выставляют исходное состояние по `spawnflags`, поэтому один и тот же стиль можно начинать как включённым, так и погашенным. Если вы делаете переключаемый свет, именно этот флаг управляет стартовым состоянием группы.

#### Практические сценарии использования
```
{
"classname" "light"
"style" "32"
"targetname" "secret_room_lights"
"spawnflags" "1"
}
```
Флаг `1` (`START_OFF`) заставляет комнатный свет стартовать погашенным и включаться только после активации переключателя.

### angle
`тип значения: float`

* Применимо к: направленным `light*`, прежде всего прожекторам с `target` или при релайте baked lightmaps.

#### Описание и логика работы
`angle` — одиночное числовое поле для упрощённой ориентации/угла. В `ltface.c` оно используется как внешний угол конуса spotlight, если у света есть `target`; при отсутствии значения берётся эквивалент примерно `40` градусов. В `gl_rlight.c` это же поле сначала попадает в упрощённый `angles`, а затем, когда свет становится направленным через `target` или `mangle`, значение используется как FOV конуса. Практически это означает: чем меньше `angle`, тем уже пятно прожектора. Запись `_angle` работает в тех путях, где парсер специально понимает подчёркнутый alias (`ltface.c`) или отбрасывает лидирующий `_` (`gl_rlight.c`).

#### Практические сценарии использования
```
{
"classname" "light"
"target" "guard_spot"
"angle" "20"
}
```
Узкий угол делает прожектор более сфокусированным; без `target` такой ключ сам по себе не создаёт направленный луч.

### mangle
`тип значения: vector("pitch yaw roll")`

* Применимо к: статичным realtime-lights, импортируемым из entity lump в `gl_rlight.c`.

#### Описание и логика работы
`mangle` задаёт полную трёхосевую ориентацию света без отдельной цели-указателя. Если поле заполнено, realtime-импортёр строит локальные оси света именно по `mangle` и рассматривает источник как направленный. Это удобнее, чем связывать каждый прожектор с отдельным `info_null`, когда направление уже известно заранее. Если при этом не указан `angle`, FTEQW подставляет стандартный FOV `40`. Для обычного QuakeC-спауна `misc.qc` это поле не используется, но для realtime-освещения оно является самым прямым способом задать направление.

#### Практические сценарии использования
```
{
"classname" "light"
"mangle" "-45 90 0"
"angle" "30"
}
```
Такой объект работает как наклонённый прожектор, направленный без вспомогательной `info_null`-цели.

### angles
`тип значения: vector("pitch yaw roll")`

* Применимо к: статичным realtime-lights, а также к случаям, где нужен полноценный трёхкомпонентный угол вместо одиночного `angle`.

#### Описание и логика работы
`angles` — более богатая версия ориентации, чем классический одиночный `angle`. В `gl_rlight.c` это поле заполняет все три угла сразу и используется для ориентации cubemap/projected light; при направленном свете вторая компонента также служит значением FOV, если свету затем назначено направление через `target` или `mangle`. На baked-стороне `ltface.c` этот ключ не обрабатывается: там важны `target` и `angle`. Поэтому `angles` стоит считать прежде всего ключом realtime-импорта, а не универсальным способом задать прожектор для всех подсистем сразу.

#### Практические сценарии использования
```
{
"classname" "light"
"angles" "0 180 0"
"skin" "16"
}
```
Полезно для статичного realtime-прожектора с проекционной маской, когда нужно задать ориентацию сразу по трём осям.

### cone
`тип значения: float`

* Применимо к: baked-пересчёту света через `engine\gl\ltface.c`.

#### Описание и логика работы
`ltface.c` действительно читает `cone` и `_cone` в структуру map-entity, поэтому такой ключ синтаксически распознаётся. Однако в проверенном коде текущего дерева дальше это значение не участвует в расчёте светового пятна: фактическая ширина spotlight в `ltface.c` по-прежнему берётся из `angle`, когда у света есть `target`. То есть `cone` сейчас выглядит как задел под расширенный или старый формат, но не как подтверждённо рабочая настройка с видимым эффектом. Если нужна гарантированная ширина луча, используйте `angle`.

#### Практические сценарии использования
```
{
"classname" "light"
"target" "test_spot"
"cone" "15"
}
```
Такую запись можно встретить в старых схемах, но в текущем исходнике FTEQW рассчитывать на изменение пятна только от `cone` не стоит.

### color
`тип значения: vector("r g b")`

* Применимо к: всем `light*`-сущностям в baked/realtime-подсистемах; разные spelling-варианты подтверждены по-разному в разных файлах.

#### Описание и логика работы
Этот ключ задаёт цвет света отдельно от яркости. Для baked-релайта `ltface.c` явно понимает все варианты написания: `color`, `colour`, `_color`, `_colour`. Для realtime-импорта `gl_rlight.c` гарантированно распознаёт `color`, а вариант `_color` тоже работает, потому что ведущий `_` отбрасывается до сравнения имени ключа. Если компоненты больше либо равны `16`, импортёр трактует их как диапазон `0..255` и автоматически нормализует; значения в пределах `0..1` воспринимаются как уже нормализованный цвет. Есть ещё одно тонкое место: когда цвет получается строго серым (`r = g = b`), realtime-импортёр умножает его на classname-specific tint, чтобы torch/flame-классы автоматически оставались тёплыми. Если же вы зададите явный несерый RGB, этот ручной оттенок будет важнее автотоновой подкраски.

#### Практические сценарии использования
```
{
"classname" "light_globe"
"color" "255 220 160"
}
```
Такой светильник получает явный тёплый оттенок; из-за несерого RGB авто-подкраска classname уже не является главным источником цвета.

### delay
`тип значения: integer`

* Применимо к: статичным realtime-lights, импортируемым из обычных map-энтити в `gl_rlight.c`.

#### Описание и логика работы
`delay` в этом контексте не имеет отношения к задержке включения и не управляет миганием. Здесь это код модели затухания света по расстоянию. В импортёре перечислены несколько legacy-режимов: `0`/по умолчанию — базовое Quake-подобное затухание, `1` — reciprocal, `2` и `5` — варианты reciprocal squared, `3` — бесконечный источник, `4` — localmin-совместимость, `6` — sun. На практике это compatibility-key для realtime-генератора, и чаще всего левелдизайнеры оставляют `0`. Но если вы вручную доводите `maps\имя_карты.rtlights` или entity lump под конкретный look, значение `delay` заметно меняет воспринимаемую дальность и характер падения света.

#### Практические сценарии использования
```
{
"classname" "light"
"light" "300"
"delay" "2"
}
```
Такой вариант просит realtime-импортёр использовать более агрессивную модель затухания, чем классическая по умолчанию.

### wait
`тип значения: float`

* Применимо к: статичным realtime-lights, импортируемым через `gl_rlight.c`.

#### Описание и логика работы
В realtime-импорте `wait` — это множитель/делитель, влияющий на фактический радиус света, а не таймер и не скорость мигания. После чтения `light` движок вычисляет итоговый радиус как базовую мощность, умноженную на глобальный коэффициент импорта и `scale`, а затем делённую на `wait` (точнее, на внутренний fade-scale). Поэтому большее `wait` делает свет короче и «собраннее», а значения меньше `1` увеличивают охват. Если число не задано или меньше либо равно нулю, движок заменяет его на `1`.

#### Практические сценарии использования
```
{
"classname" "light"
"light" "400"
"wait" "2"
}
```
Такой источник остаётся ярким, но получает меньший эффективный радиус в realtime-представлении, чем аналогичный свет без `wait`.

### fade
`тип значения: float`

* Применимо к: статичным realtime-lights, импортируемым через `gl_rlight.c`.

#### Описание и логика работы
`fade` в текущем импортёре работает как альтернативное имя для той же fade-scale-настройки, что и `wait`. Иными словами, для обычных map-светов `fade` и `wait` фактически синонимичны: оба ключа сводятся к одному коэффициенту, влияющему на итоговый радиус/скорость затухания. Запись `_fade` тоже воспринимается, потому что импортёр снимает один ведущий символ `_` перед разбором имени ключа. Использовать одновременно `wait` и `fade` не стоит: последнее считанное значение просто станет активным.

#### Практические сценарии использования
```
{
"classname" "light"
"light" "400"
"fade" "0.5"
}
```
Такой вариант даёт более дальний realtime-охват, чем `fade 1`, потому что внутренний делитель становится меньше.

### scale
`тип значения: float`

* Применимо к: статичным realtime-lights, импортируемым через `gl_rlight.c`.

#### Описание и логика работы
`scale` — дополнительный множитель радиуса света при realtime-импорте. В отличие от `light`, этот ключ не меняет базовый цвет и не обозначает самостоятельную яркость; он именно масштабирует уже вычисленную мощность источника. Значения меньше либо равные нулю игнорируются и заменяются на `1`. Это удобный ключ, когда вы хотите сохранить baked-интенсивность по `light`, но в realtime-слое сделать источник шире или уже без перенастройки остальных параметров.

#### Практические сценарии использования
```
{
"classname" "light"
"light" "300"
"scale" "1.5"
}
```
Хорошо подходит для широких потолочных светильников: базовая яркость остаётся прежней, а realtime-пятно расширяется.

### skin
`тип значения: integer`

* Применимо к: статичным realtime-lights, импортируемым через `gl_rlight.c`.

#### Описание и логика работы
`skin` у световой сущности используется не для замены модели, а для выбора numbered light texture — проекционной маски светильника. Импортёр подгружает такую маску только если значение `skin >= 16`; меньшие числа не активируют numbered light texture в этой ветке кода. Это полезно для прожекторов, оконных решёток и любых эффектов, где свет должен не просто освещать пространство, а проецировать рисунок. Для baked lightmaps этот ключ в проверенном `ltface.c` не участвует.

#### Практические сценарии использования
```
{
"classname" "light"
"skin" "16"
"mangle" "-90 0 0"
}
```
Такой свет готовится к projected/gobo-проекции в realtime-режиме; конкретный рисунок зависит от набора numbered light textures движка.

### pflags
`тип значения: integer`

* Применимо к: статичным realtime-lights и программно создаваемым dlight/rtlight-источникам, где движок интерпретирует битовые флаги поведения.

#### Описание и логика работы
`pflags` — битовая маска дополнительных свойств realtime-света. В проверенном коде map-импорта подтверждены как минимум `1` = `PFLAGS_NOSHADOW` (не отбрасывать тени) и `2` = `PFLAGS_CORONA` (разрешить корону/flashblend-представление источника). Для очень маленьких светов движок и сам может принудительно добавить режим без теней ради производительности. Этот ключ не влияет на baked lightmaps и не нужен обычному статичному `light`, если вы не используете FTEQW как движок с realtime-world lighting.

#### Практические сценарии использования
```
{
"classname" "light"
"pflags" "3"
}
```
Значение `3` объединяет `NOSHADOW` и `CORONA`: свет рисуется быстрее, без теней, но с заметной светящейся короной.

### light_radius
`тип значения: float`

* Применимо к: статичным realtime-lights, импортируемым через `gl_rlight.c`.

#### Описание и логика работы
`light_radius` — специальный override для realtime-импортёра. Если ключ задан, он перезаписывает радиус напрямую и одновременно сбрасывает базовый цветовой множитель света к белому, после чего уже поверх могут действовать `color` и classname-тон. Это удобно, когда у автора карты уже есть внешний инструмент или `.ent`-патч, который хочет задавать именно радиус, не подбирая его косвенно через классический `light`. Для baked-освещения этот ключ в проверенных путях не участвует.

#### Практические сценарии использования
```
{
"classname" "light"
"light_radius" "512"
"color" "0.8 0.9 1.0"
}
```
Здесь радиус задаётся напрямую, а цвет отдельно смещается в холодный голубоватый тон.
