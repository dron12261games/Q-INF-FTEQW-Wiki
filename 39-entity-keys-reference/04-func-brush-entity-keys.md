# Двери, платформы и подвижная геометрия

> [⬅ Вернуться к оглавлению вики](../README.md)

> [Индекс справочника ключей сущностей](./README.md)

Подвижные brush-сущности Quake — это BSP-модели, которые серверная логика переводит в `MOVETYPE_PUSH` и двигает между заранее вычисленными положениями. В исследованном basemod основные классы такого типа реализованы в `doors.qc`, `plats.qc`, `buttons.qc`, а общая математика линейного перемещения находится в `subs.qc`. `func_door` умеет автоматически объединять соприкасающиеся створки в один узел, `func_plat` создаёт собственный внутренний триггер, а `func_train` ездит по цепочке `path_corner`. Отдельного флага `DOOR_SILENT` в этом basemod не найдено: бесшумный режим для дверей и поездов достигается через `sounds "0"`.

## Классы func-сущностей

- `func_door` — обычная сдвижная дверь, которая открывается касанием, выстрелом или внешним `use`.
- `func_door_secret` — секретная дверь с двухфазным движением: сначала назад, затем вбок.
- `func_plat` — вертикальная платформа-лифт.
- `func_train` — подвижная платформа, следующая по маршруту из `path_corner`.
- `path_corner` — маршрутная точка для `func_train`; также используется монстрами.
- `func_button` — нажимаемая brush-кнопка.
- `func_wall` — обычный твёрдый bmodel-объект; классическая реализация найдена в соседних id1-style SSQC-модулях репозитория.
- `func_illusionary` — нетвёрдый декоративный bmodel-объект; классическая реализация также найдена в соседних SSQC-модулях.
- `func_breakable` — в `quakec\basemod` и соседних id1-style QC-модулях репозитория не найден, поэтому отдельные ключи для него здесь не документируются.

## Ключи

### classname
`тип значения: string`

* Применимо к: `func_door`, `func_door_secret`, `func_plat`, `func_train`, `path_corner`, `func_button`, `func_wall`, `func_illusionary`.

#### Описание и логика работы
`classname` выбирает spawn-логику сущности. Один и тот же brush-комплект при `classname "func_door"` получит расчёт направления, автолинковку створок и возврат назад по таймеру, а при `classname "func_button"` станет короткоходным нажимным элементом. Для point-сущности `path_corner` это имя определяет, будет ли её искать `func_train` как узел маршрута. Ошибка в `classname` обычно означает, что brush останется без ожидаемого поведения.

#### Практические сценарии использования
```
{
"classname" "func_plat"
"speed" "200"
}
```
Этот brush будет заспаунен именно как платформа, а не как дверь или кнопка.

### targetname
`тип значения: string`

* Применимо к: `func_door`, `func_door_secret`, `func_plat`, `func_train`, `path_corner`, `func_button`, `func_wall`.

#### Описание и логика работы
`targetname` делает сущность адресуемой для чужого `target`. У `func_door` наличие `targetname` отключает автоматическое широкое proximity-срабатывание через вспомогательное trigger-поле: дверь остаётся в мире, но ожидает внешнюю активацию, если не используется режим открытия выстрелом или ключевая логика. У `func_plat` такой ключ переводит платформу в стартовое верхнее состояние и не даёт ей работать как обычному лифту, пока её кто-то не активирует. У `func_train` без `targetname` поезд стартует сам почти сразу после спауна, а с `targetname` ждёт внешнего запуска.

#### Практические сценарии использования
```
{
"classname" "func_train"
"targetname" "start_cart"
"target" "cart_node_1"
}
```
Такой поезд не поедет сам по себе: его должен запустить другой триггер или кнопка через `target "start_cart"`.

### target
`тип значения: string`

* Применимо к: `func_door`, `func_door_secret`, `func_train`, `path_corner`, `func_button`.

#### Описание и логика работы
У `func_door`, `func_door_secret` и `func_button` ключ `target` обрабатывается общей процедурой `SUB_UseTargets`: при срабатывании сущность находит все объекты с совпадающим `targetname` и вызывает их логику использования. Для `func_train` смысл другой и обязательный: это имя первого `path_corner`, в котором поезд должен появиться и откуда начнёт маршрут. После прибытия в corner поезд читает уже `target` самой маршрутной точки и едет дальше по цепочке. Если оставить `target` пустым у `func_train` или обрубить цепочку `path_corner`, маршрут завершится ошибкой конфигурации.

#### Практические сценарии использования
```
{
"classname" "func_door"
"target" "ambush_start"
}
```
Когда дверь начнёт открываться, она одновременно активирует все сущности с `targetname "ambush_start"`.

### message
`тип значения: string`

* Применимо к: `func_door`, `func_door_secret`, `func_button`.

#### Описание и логика работы
`message` — текстовое сообщение для игрока, но точный момент его показа зависит от класса. У `func_door` сообщение рассчитано на касание: код печатает его игроку, если дверь ещё не открыта, после чего при настоящем открытии очищает строку, чтобы она не повторялась бесконечно. У `func_door_secret` сообщение также выводится по касанию brush-а до фактического запуска секрета. У `func_button` ключ проходит через общую систему `SUB_UseTargets`, поэтому сообщение показывается активатору в момент, когда кнопка дошла до конечного положения и запустила свои цели.

#### Практические сценарии использования
```
{
"classname" "func_door"
"message" "Maintenance access locked"
"targetname" "service_door"
}
```
Игрок увидит подсказку при касании двери, пока та ещё не была открыта внешним событием.

### killtarget
`тип значения: string`

* Применимо к: `func_door`, `func_door_secret`, `func_button`.

#### Описание и логика работы
Если задан `killtarget`, при срабатывании сущность сначала удаляет из мира все объекты с соответствующим `targetname`, а уже потом продолжает остальную цепочку событий. Для дверей и кнопок это удобно, когда нужно выключить старый trigger, убрать временную заглушку или уничтожить вспомогательный блокер в тот же момент, когда началось движение brush-а. Учитывайте, что удаление окончательное до конца уровня. Если одновременно задан `delay`, удаление произойдёт не мгновенно, а в отложенный момент вместе с остальными целями.

#### Практические сценарии использования
```
{
"classname" "func_button"
"killtarget" "hint_panel"
"target" "reactor_start"
}
```
После нажатия кнопка сначала удалит все сущности `hint_panel`, а затем запустит `reactor_start`.

### delay
`тип значения: float`

* Применимо к: `func_door`, `func_door_secret`, `func_button`.

#### Описание и логика работы
`delay` откладывает не само движение brush-сущности, а момент передачи событий через `target` и `killtarget`. У `func_door` задержка ставится в ту фазу, когда дверь уже начала открываться; у `func_door_secret` — в начало сложной секретной анимации; у `func_button` — после того, как кнопка дошла до нажатого положения. Значение задаётся в секундах. Ноль означает немедленное срабатывание, положительное число — отложенный запуск через временную служебную сущность.

#### Практические сценарии использования
```
{
"classname" "func_door_secret"
"delay" "1.5"
"target" "spawn_guard"
}
```
Секретная дверь начнёт открываться сразу, а `spawn_guard` сработает через 1.5 секунды.

### angle
`тип значения: float`

* Применимо к: `func_door`, `func_door_secret`, `func_button`.

#### Описание и логика работы
`angle` задаёт направление движения в редакторном формате Quake: обычно это yaw в градусах, а специальные значения `-1` и `-2` обозначают движение строго вверх и строго вниз. Для `func_door` и `func_button` по этому направлению вычисляется вектор линейного хода. Для `func_door_secret` `angle` определяет «вперёд» двери: сначала секретный brush отъезжает назад или в сторону относительно этой ориентации, затем едет вдоль неё. Если ключ не задан, используется дефолтная редакторная ориентация, что часто означает движение по мировому `+X`.

#### Практические сценарии использования
```
{
"classname" "func_button"
"angle" "-1"
"lip" "2"
}
```
Кнопка будет вжиматься вверх, а не вбок.

### angles
`тип значения: vector`

* Применимо к: `func_door`, `func_door_secret`, `func_button`, `func_wall`, `func_illusionary`.

#### Описание и логика работы
Некоторые редакторы или внешние `.ent`-файлы записывают ориентацию не через одиночный `angle`, а через полный вектор `angles`. Внутренняя логика подвижных brush-сущностей читает именно это векторное поле: `func_door`, `func_button` и `func_door_secret` преобразуют его в направление движения, а затем сбрасывают собственные углы к `0 0 0`, чтобы корректно двигать BSP-модель как push-объект. Для `func_wall` и `func_illusionary` в найденных классических реализациях углы тоже принудительно обнуляются, поэтому этот ключ не даёт им самостоятельной анимации. Практически `angles` нужен там, где редактор отдаёт полную ориентацию вместо обычного `angle`.

#### Практические сценарии использования
```
{
"classname" "func_door_secret"
"angles" "0 90 0"
"t_length" "96"
}
```
Секретная дверь будет считать направлением движения ось, соответствующую yaw `90` градусов.

### speed
`тип значения: float`

* Применимо к: `func_door`, `func_plat`, `func_train`, `func_button`.

#### Описание и логика работы
`speed` задаёт скорость линейного перемещения в units per second. Значения по умолчанию различаются по классам: `func_door` — `100`, `func_plat` — `150`, `func_train` — `100`, `func_button` — `40`. Если оставить `speed "0"`, spawn-код подставит дефолт; отдельный ноль как «стоять на месте» не поддерживается. Для `func_door_secret` пользовательский `speed` в исследованном basemod не читается: класс принудительно работает со скоростью `50`.

#### Практические сценарии использования
```
{
"classname" "func_plat"
"speed" "300"
}
```
Платформа будет перемещаться вдвое быстрее стандартного режима.

### wait
`тип значения: float`

* Применимо к: `func_door`, `func_door_secret`, `func_train`, `path_corner`, `func_button`.

#### Описание и логика работы
`wait` почти везде измеряется в секундах, но смысл зависит от класса. У `func_door` это пауза в открытом состоянии перед возвратом; по умолчанию `3`, а `-1` означает «никогда не закрываться автоматически». У ключевых дверей этот режим ставится принудительно. У `func_door_secret` стандарт — `5` секунд перед обратным ходом, а флаг `open_once` отключает возврат независимо от `wait`. У `func_train` само поле обычно задают не поезду, а `path_corner`: прибыв в узел маршрута, поезд копирует оттуда `wait`; если corner не задаёт паузу, поезд продолжит путь почти сразу. У `func_button` это время возврата после нажатия; entity-definition id1 традиционно документирует `-1` как режим без автоматического возврата, а сам basemod просто передаёт это значение дальше в таймер возврата.

#### Практические сценарии использования
```
{
"classname" "func_door"
"wait" "-1"
}
```
Такая дверь откроется и останется открытой, пока что-то внешнее не изменит её состояние.

### lip
`тип значения: float`

* Применимо к: `func_door`, `func_button`.

#### Описание и логика работы
`lip` — это часть brush-а в units, которая остаётся видимой после завершения движения. У `func_door` по умолчанию сохраняется `8` units, у `func_button` — `4`. Чем больше `lip`, тем короче ход: сущность вычисляет полную длину по своей геометрии и вычитает это значение из итогового смещения. `lip "0"` заставляет объект уехать на полную толщину вдоль направления движения. Отрицательные значения теоретически увеличивают ход сверх габарита и обычно приводят к неудачной геометрии, поэтому использовать их не стоит.

#### Практические сценарии использования
```
{
"classname" "func_door"
"angle" "90"
"lip" "16"
}
```
После открытия в проёме останется видимая полоска двери толщиной 16 units.

### dmg
`тип значения: float`

* Применимо к: `func_door`, `func_door_secret`, `func_train`.

#### Описание и логика работы
`dmg` определяет, сколько урона сущность наносит при блокировке своего движения. Для `func_door` и `func_door_secret` дефолт — `2` HP за срабатывание логики раздавливания. У `func_train` тот же дефолт `2`, но удар ограничен внутренним кулдауном примерно в полсекунды, чтобы поезд не наносил урон каждый кадр. `func_plat` использует фиксированный урон `1` и отдельного пользовательского ключа для этого в basemod не имеет.

#### Практические сценарии использования
```
{
"classname" "func_train"
"target" "crusher_path_1"
"dmg" "20"
}
```
Если поезд прижмёт игрока или монстра, удар будет значительно опаснее стандартного.

### sounds
`тип значения: integer`

* Применимо к: `func_door`, `func_door_secret`, `func_plat`, `func_train`, `func_button`.

#### Описание и логика работы
`sounds` — это числовой селектор заранее прошитых звуковых наборов, а не путь к аудиофайлу. У `func_door` доступны варианты `0` (тишина), `1` (stone), `2` (base), `3` (stone chain), `4` (screechy metal). У `func_door_secret`: `1` (medieval), `2` (metal), `3` и `0` (base). У `func_plat` логика понимает `1` (base fast) и `2` (chain slow), причём значение `0` автоматически заменяется на `2`, так что полностью бесшумной платформы этим ключом не сделать. У `func_train` есть `0` (тишина через `misc/null.wav`) и `1` (ratchet metal). У `func_button` варианты `0`-`3` выбирают один из четырёх щелчков/клацаний.

#### Практические сценарии использования
```
{
"classname" "func_door"
"sounds" "0"
}
```
Дверь будет двигаться без собственного звукового набора открытия/закрытия.

### health
`тип значения: float`

* Применимо к: `func_door`, `func_button`.

#### Описание и логика работы
Если `health` задан, сущность перестаёт быть обычным touch-активатором и становится shootable-объектом. У `func_door` код запоминает число как `max_health`, включает получение урона и открывает дверь только после её «убийства»; при возврате вниз здоровье восстанавливается. У `func_button` логика аналогична: кнопку нужно разрушить выстрелами, после чего она нажмётся, а при возвращении снова станет уязвимой. Ноль или отсутствие ключа оставляет обычный режим касания/использования.

#### Практические сценарии использования
```
{
"classname" "func_button"
"health" "30"
"target" "vault_unlock"
}
```
Игроку придётся нанести кнопке 30 HP урона, чтобы она сработала.

### height
`тип значения: float`

* Применимо к: `func_plat`.

#### Описание и логика работы
`height` задаёт, на сколько units платформа должна опуститься от верхней позиции к нижней. Если ключ не задан, код вычисляет ход автоматически из высоты brush-а по формуле «полная высота минус 8 units». Это позволяет делать стандартные лифты без ручных расчётов. Если `height` указан, именно он становится авторитетным значением хода, независимо от фактической геометрической толщины платформы.

#### Практические сценарии использования
```
{
"classname" "func_plat"
"height" "128"
}
```
Платформа будет опускаться ровно на 128 units от верхнего положения.

### t_width
`тип значения: float`

* Применимо к: `func_door_secret`.

#### Описание и логика работы
`t_width` переопределяет первую фазу движения секретной двери. Обычно `func_door_secret` сама вычисляет это расстояние по размеру brush-а: если первый ход идёт вбок, берётся ширина по оси `right`; если вниз — высота по оси `up`. При заданном `t_width` автоматический расчёт отключается, и дверь отъезжает на строго указанное число units. Это удобно для нестандартных secret-панелей, у которых реальная геометрическая ширина не совпадает с желаемой глубиной ухода назад.

#### Практические сценарии использования
```
{
"classname" "func_door_secret"
"t_width" "24"
"spawnflags" "4"
}
```
Флаг `4` включает первый ход вниз, а `t_width "24"` заставляет дверь сначала опуститься ровно на 24 units.

### t_length
`тип значения: float`

* Применимо к: `func_door_secret`.

#### Описание и логика работы
`t_length` переопределяет вторую фазу движения секретной двери — боковое или продольное скольжение после первого шага. Без этого ключа код берёт длину хода из размера brush-а по направлению `forward`, то есть по оси, которую задаёт `angle`/`angles`. При ручном значении можно заставить секретную дверь открываться короче или длиннее собственной толщины/длины. Единицы измерения — обычные world units.

#### Практические сценарии использования
```
{
"classname" "func_door_secret"
"t_length" "128"
"angles" "0 180 0"
}
```
После первого отъезда дверь проскользит ещё на 128 units вдоль направления, противоположного мировому `+X`.

### spawnflags (START_OPEN)
`тип значения: integer`

* Применимо к: `func_door`.

#### Описание и логика работы
Флаг `START_OPEN` имеет числовое значение `1`. При спауне дверь сначала вычисляет обычные `pos1` и `pos2`, затем мгновенно ставится в открытую позицию и меняет местами начальную и конечную точки. В результате она выглядит как уже открытая, но при активации работает «в обратную сторону» — закрывает проход, а следующая активация снова открывает его. Это особенно полезно для сценарных перекрытий, которые должны блокировать путь только после события. Для обычных touch-дверей и shootable-дверей режим традиционно считается неудобным.

#### Практические сценарии использования
```
{
"classname" "func_door"
"spawnflags" "1"
"targetname" "seal_corridor"
}
```
Дверь стартует в открытом состоянии и по внешнему сигналу сможет сначала закрыть коридор.

### spawnflags (DOOR_DONT_LINK)
`тип значения: integer`

* Применимо к: `func_door`.

#### Описание и логика работы
Флаг `DOOR_DONT_LINK` имеет значение `4`. Без него соприкасающиеся `func_door` автоматически объединяются в общую цепочку и открываются как единый блок, а также могут получить общий trigger-объём. С этим битом конкретная дверь исключается из автолинковки: она остаётся самостоятельной сущностью даже вплотную к соседним створкам. Такой режим нужен для сложных механик, где brushes касаются геометрически, но должны жить по разным сценариям.

#### Практические сценарии использования
```
{
"classname" "func_door"
"spawnflags" "4"
"targetname" "left_leaf"
}
```
Эта створка не сольётся автоматически с соседней дверью, даже если brushes соприкасаются.

### spawnflags (GOLD_KEY)
`тип значения: integer`

* Применимо к: `func_door`.

#### Описание и логика работы
Флаг `GOLD_KEY` имеет значение `8` и делает дверь ключевой. Код помечает её как требующую золотой ключ/рунический ключ/ключ-карту в зависимости от `worldtype`, печатает соответствующее сообщение при нехватке предмета и, после успешного открытия, списывает ключ у игрока. Дополнительно такая дверь всегда получает `wait -1`, то есть не закрывается сама автоматически. Если одновременно задать сообщение `message`, оно будет показываться на касании до проверки ключа.

#### Практические сценарии использования
```
{
"classname" "func_door"
"spawnflags" "8"
"message" "A gold lock bars the passage"
}
```
Дверь потребует золотой ключ и после открытия останется открытой.

### spawnflags (SILVER_KEY)
`тип значения: integer`

* Применимо к: `func_door`.

#### Описание и логика работы
Флаг `SILVER_KEY` имеет значение `16` и работает так же, как золотой вариант, но требует серебряный ключевой предмет. Как и любой key-door в этом basemod, такая дверь принудительно переводится в режим `wait -1`. Логика проверки ключа срабатывает именно при касании игроком самой двери. После успешного открытия ключ снимается с инвентаря.

#### Практические сценарии использования
```
{
"classname" "func_door"
"spawnflags" "16"
}
```
Откроется только игроку с серебряным ключом и не станет закрываться автоматически.

### spawnflags (TOGGLE)
`тип значения: integer`

* Применимо к: `func_door`.

#### Описание и логика работы
Флаг `TOGGLE` имеет значение `32`. Когда дверь доходит до открытого состояния, она не ставит таймер автозакрытия, а ждёт следующего события `use`/trigger, чтобы поехать обратно. Если дверь уже открыта и снова получает команду, мастер-створка разворачивает всю связанную цепочку и закрывает её. Это стандартный режим для шлюзов, заслонок и любых дверей, которые должны жить как переключатель, а не как одноразовый проход.

#### Практические сценарии использования
```
{
"classname" "func_door"
"spawnflags" "32"
"targetname" "blast_shutter"
}
```
Каждый внешний сигнал будет поочерёдно открывать и закрывать ставню.

### spawnflags (open_once)
`тип значения: integer`

* Применимо к: `func_door_secret`.

#### Описание и логика работы
У `func_door_secret` флаг `open_once` имеет значение `1`. После завершения двухфазного открытия дверь остаётся открытой и не запускает обратный ход, даже если `wait` задан. Это самый удобный режим для классических секретов, которые должны навсегда открыть проход к тайнику. Если флаг не установлен, дверь постоит `wait` секунд и затем уедет назад в закрытое положение.

#### Практические сценарии использования
```
{
"classname" "func_door_secret"
"spawnflags" "1"
"wait" "10"
}
```
Несмотря на `wait "10"`, дверь не станет закрываться, потому что режим `open_once` сильнее.

### spawnflags (1st_left)
`тип значения: integer`

* Применимо к: `func_door_secret`.

#### Описание и логика работы
Флаг `1st_left` имеет значение `2` и меняет знак первого бокового смещения секретной двери. Без него первый ход идёт вправо относительно направления `angle`/`angles`, с ним — влево. Это важно для двусторонних стеновых секретов, где одинаковая геометрия должна открываться в разные стороны без разворота brush-а. На второй фазе дверь всё равно поедет вдоль своего `forward`.

#### Практические сценарии использования
```
{
"classname" "func_door_secret"
"spawnflags" "2"
"angles" "0 90 0"
}
```
При такой ориентации дверь сначала уйдёт влево относительно стрелки редактора.

### spawnflags (1st_down)
`тип значения: integer`

* Применимо к: `func_door_secret`.

#### Описание и логика работы
Флаг `1st_down` имеет значение `4` и заменяет первый боковой шаг вертикальным ходом вниз. Если `t_width` не задан, глубина этого шага вычисляется по вертикальному размеру brush-а, а не по его ширине. Этот режим полезен для книжных шкафов, ниш и колонн, которые должны сначала чуть просесть, а уже потом отъехать в сторону. Дальнейшее продольное скольжение по `t_length` работает как обычно.

#### Практические сценарии использования
```
{
"classname" "func_door_secret"
"spawnflags" "4"
"t_width" "32"
}
```
Секретная панель сперва опустится на 32 units, а затем начнёт второй этап открытия.

### spawnflags (no_shoot)
`тип значения: integer`

* Применимо к: `func_door_secret`.

#### Описание и логика работы
Флаг `no_shoot` имеет значение `8` и отключает открытие секретной двери уроном. Это особенно важно, если секрет должен срабатывать только через внешний trigger или кнопку, а не от случайного выстрела игрока. После активации такая дверь также снимает с себя shootable-поведение и работает чисто как сценарный механизм. Если вместе с этим у двери есть `targetname`, получается полностью удалённый секрет без возможности открыть его простым обстрелом.

#### Практические сценарии использования
```
{
"classname" "func_door_secret"
"spawnflags" "8"
"targetname" "open_hidden_panel"
}
```
Игрок не сможет открыть эту дверь выстрелами; нужен внешний вызов `open_hidden_panel`.

### spawnflags (always_shoot)
`тип значения: integer`

* Применимо к: `func_door_secret`.

#### Описание и логика работы
Флаг `always_shoot` имеет значение `16` и делает секретную дверь shootable даже в том случае, когда у неё задан `targetname`. Без этого бита наличие `targetname` обычно превращает дверь в чисто trigger-driven объект. С `always_shoot` маппер получает гибрид: секрет можно открыть и сценарно, и прямым нанесением урона. Внутри логики это достигается тем, что дверь после завершения цикла снова получает большое `health` и обработчик боли/смерти.

#### Практические сценарии использования
```
{
"classname" "func_door_secret"
"spawnflags" "16"
"targetname" "optional_secret"
}
```
Секрет можно активировать внешним событием, но игрок всё равно сумеет выбить его выстрелами.

### spawnflags (PLAT_LOW_TRIGGER)
`тип значения: integer`

* Применимо к: `func_plat`.

#### Описание и логика работы
Для `func_plat` флаг `PLAT_LOW_TRIGGER` имеет значение `1` и меняет форму внутреннего trigger-объёма платформы. В обычном режиме платформа создаёт высокий центральный trigger, который тянется почти на весь вертикальный ход, поэтому игрок может активировать подъём, находясь внутри шахты лифта. С этим флагом trigger становится низким, фактически тонкой зоной у нижнего положения. Такой вариант полезен, когда нужно избежать ложных срабатываний сверху или сбоку и заставить игрока именно зайти на платформу снизу.

#### Практические сценарии использования
```
{
"classname" "func_plat"
"spawnflags" "1"
"height" "96"
}
```
Платформа будет ждать касания в нижней зоне, а не реагировать на широкий центральный объём.
